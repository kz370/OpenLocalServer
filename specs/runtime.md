- [2026-10-01] feat(sites): sites can be exported to and imported from a bundle file, and the work of doing it is something you can watch. Three requirements, and each one had a decision in it that was not the obvious one. (1) **Selective and batch export.** One zip per export holding any mix of four things — settings, `.env` files, database dumps, project files — for any number of sites at once. They are four independent switches because they differ by orders of magnitude, and the default is settings + `.env` on, data off: a "site export" that quietly includes 4 GB of `node_modules` is not an export anyone asked for, and an all-off selection is refused rather than written as a zip holding nothing but a manifest. The grouping decision is the one worth recording: sites are keyed by the **project** behind them, not one entry per site, so exporting `shop.test` and `blog.test` of one project gives one entry with two sites and imports back as one project with two sites instead of two projects that have to be reconciled by hand. A site with no project behind it has nothing to describe and is reported as such rather than exported half-way, which is the same shape as the existing "project row with no domain" case. (2) **Password encryption, as a user choice.** When the export is encrypted, the `.env` files and the database dumps are sealed — those are the two places passwords actually live — under Argon2id then ChaCha20-Poly1305. Two things are deliberately *not* sealed and the dialog says so: project files and settings stay readable, because they are source code and configuration the user can read anyway and sealing them would make the bundle impossible to review before importing it. The zip crate's own AES scheme is ZipCrypto-derived and weak, which is the second reason sealing is per entry rather than per file. The key is derived **once per bundle** (the salt lives in the manifest, every entry carries its own fresh 96-bit nonce) rather than per entry: per-file derivation would cost ~60 ms times the file count for no additional safety, while a *reused nonce under one key* would break ChaCha20-Poly1305 outright, so the nonce must be new every time and the derivation must not be. A wrong password and a damaged file are indistinguishable to an AEAD and the Diagnostic says exactly that, with the two ways out, rather than guessing which one it was. The app never stores the password, so the generated one (20 characters from an alphabet without `0 O 1 l I`, built in the page from `crypto.getRandomValues`) is shown once in monospace next to a "write it down" hint, and losing it is stated as the consequence rather than discovered at import time. (3) **The update-or-rename choice, and the snapshot.** A hostname that already exists is never overwritten silently: `preview_site_bundle` reads only the manifest and reports per site which hostnames already exist and which free name a rename would take, so the choice is made on facts and a damaged or future-format bundle is refused *before* anything is created. An update **takes a snapshot of the current state first**, labelled "Before import", through the same `create_snapshot` a manual backup uses, and names it in `BundleSiteResult.safety_snapshot` — so "update" is a step the user can undo rather than a leap of faith, which is the whole difference between the two options being equally choosable. A rename registers a new project folder and adjusts everything the collision would have made ambiguous (hostname, database, port) through the same `Adjust` a clone uses, so both copies run. That reuse is deliberate: the stored configuration is a `SnapshotContent` document with `env_files` cleared and every `dump` set to `None`, so the manifest itself never holds a secret, and `content_of` puts both back on read — meaning every import path downstream is code a snapshot restore already runs, rather than a second implementation that can disagree with the first. Per-site failures land in `problems` and never abort the batch: an export of twenty sites must not cost the user all twenty because one database was down. The zip is written through a `.part` file and renamed on success with the manifest **last**, and the name takes a suffix rather than overwriting — the same two rules `snapshots.rs` already follows, for the same reason. The destination defaults to the app's own `backups` folder (resolved by the core as `paths.backups_dir`, computed like `paths.sites_dir` and never stored, so a moved or portable install is followed) and is prefilled rather than blank, because a field that opens asking "where?" for a choice that has a right answer is a question, not a setting; it is filled once per open so clearing the box to retype a path does not snap the default back under the cursor.
