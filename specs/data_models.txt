Data models (SQLite app.db: settings table + docs collections holding JSON blobs).

Entities:
- Project {id: sha256(path)[..16], name, path, framework, created_at, updated_at}
- `WpProject {project_id, name, hostname: Option<String>, url: Option<String>, pending_until: Option<u64>}` (tag `wp_projects`) — a registered project that is a WordPress install, as `Inner::wp_projects` reports it. `hostname`/`url` are the project's first enabled site and are `None` when it has no domain yet (a sign-in link needs a URL; the action says so instead of failing later). `pending_until` is the Unix second a one-time sign-in link stops working, and `None` when nothing is pending — so a bridge left behind by a crash is removed by the `sweep` the same listing runs, rather than being kept because it happened to exist.
- `WpSignIn {url: String, expires_at: u64}` (tag `wp_sign_in`) — the one-time link to open in the browser. `url` carries a 128-bit token and is therefore never logged, cached or persisted by the app; it is a bearer capability, not an identifier. Neither model holds, references or derives from a WordPress password: sign-in happens inside WordPress through `wp_set_auth_cookie`, and nothing OLS stores can be used to sign in again after the file is gone.
- Domain {id, project_id, hostname, root, kind: Php{version}|Proxy{host,port,https}|Static, https, redirect_https, wildcard, enabled, ownership: Managed|Advanced|Manual, app:{executable,args,cwd,runtime}, blocks:{headers,redirects,mappings,upstreams,includes}, generated_hashes, public_domain, tunnel_id, server: nginx|apache|caddy|null, path_prefix: string|null}
  server null = served by the default web server; a set id pins the site to that one server. Exclusive: a site is rendered on exactly one server, never mirrored. An id that is no longer a known server is kept in the file and falls back to the default with a warning, never dropped (validate_domain_server rejects one on add/update).
  path_prefix = also serve the site at localhost/<path_prefix>, in addition to its own domain. One segment, 1-40 chars, lowercase letters/digits/-/_ only; "." and ".." and any "/" or "\" are refused (validate_path_prefix). Blank stores None. Unique across sites: a second site claiming one is refused naming the holder, because both would answer on the same path and only one could win.
- `BulkOutcome {changed: usize, skipped: Vec<String>}` is the answer to every bulk site edit (`CoreResponse::Bulk`, tag `bulk`). `changed` counts the sites that took the edit; `skipped` holds one line per site that did not, written as `<hostname> <reason>` so it reads as a sentence ("shop.test is not a known domain", "openlocalserver.test is the built-in home site, which stays on"). It exists because a batch is partial by contract: a stale hostname in a selection must not cost the user the other twenty-nine changes, and a batch that landed on twenty of twenty-five sites has to say which five it left alone rather than reporting plain success.
- Fresh install seeds Domain openlocalserver.test (Static, managed, https, root data-dir/home + welcome index.html + exact logo.svg brand bytes); always ensured on load (legacy home.test auto-renamed), hidden from Sites list, remove/rename refused. Its root is re-anchored to `<data>/home` on every load, since that folder belongs to the app and not to the install path it was first written at. The seeded logo.svg/logo-dark.svg are generated bytes, so a copy that differs from the shipped favicon is rewritten while the page is still stock, and kept once the page has been hand-edited.
- `CustomInstall {id, label, path}` (user-pinned tool/runtime locations, always winning over detection) stores `path` under the same rule: relative when the executable is inside the app (a managed runtime under `<install>\runtimes`), absolute when the user installed it elsewhere, expanded to a full path on load. A moved install therefore keeps its own runtimes; a tool the user pinned on their own drive keeps the path they gave it.
- `Domain.root` is stored relative when the folder is one of the app's own (`sites/<name>` or `data/<name>`, forward slashes) and absolute otherwise, translated only at the `DomainStore` boundary (`AppPaths::encode_root` / `decode_root`). So a site under the app's own folders travels with a renamed or relocated install, while a real project folder keeps the path its owner gave it and is never rewritten. A root stored absolute by an older build that no longer exists is re-anchored from its trailing `sites`/`data`/`home` segment when that folder exists under the current install, and left untouched otherwise so a genuinely deleted site still reports as missing. Every in-memory consumer — renderers, diagnostics, search, snapshots, the API — sees a full path.
- Runtime {id, type: php|node|python|composer|mariadb|postgres|mongo|redis|mailpit|nginx|apache|caddy|sqlite|git|k6, version, path, arch, installed_at}
- RuntimeEvent = Progress{id, version, state: Downloading|Paused|Verifying|Extracting, downloaded, total} | Installed{id, version, path} | Failed{id, version, message} | Cancelled{id, version}
  InstallState (the `state` map) additionally carries Installed|Cancelled|Failed. Cancelled is a user stop, not a failure: it produces its own terminal event and no Diagnostic, and it never reaches Failed.
- InstallControl {paused, cancelled}, one per in-flight id@version, live only while that install runs. Pause holds the transfer (partial file kept, resume continues it); cancel deletes the partial download and installs nothing.
- DatabaseInstance {id, engine, version, host, port, data_path, status}
- Database {engine, name, owner} + DbUser {name, host, password_ref}
- WebConfig {default_server: nginx|apache|caddy, servers:{server_id -> ServerPorts{http, https}}, php_workers, dns_port}
  Settings keys: web.default_server, web.servers.<id>.http_port, web.servers.<id>.https_port (legacy web.server / web.http_port / web.https_port migrate into the default server's entry on load).
  effective_ports(id) = 80/443 when id == default_server, else the stored pair; stored pairs are never rewritten just because a server becomes the default. First-time pairs: apache 8080/8443, caddy 8081/8444, nginx 8082/8445.
  resolve_server(override) = override when it is a known id, else default_server.
- WebServerConfig {id, project_id, server: nginx|apache|caddy, path, managed, hash, updated_at} + ConfigHistory {hostname, timestamp, content}
- Certificate {hostname, cert.pem, key.pem, meta.json{sans, expiry}} + CaInfo {cn: OpenLocalServer Local CA, valid 2024-2044}
- Tunnel {id, project_id, provider: cloudflare|ngrok|localtunnel|mock, target, public_url, status, created_at}
- QuickApp {id, name, source: Builtin|Local|Imported, version, definition_path, trusted, favorite} + QuickRun {id, app_id, status, logs[4000 cap]}
- QuickCommand {id, name, command:{executable,arguments}|action, working_directory, source, trusted} + CommandHistory {line, exit_code, timestamp}
- Plugin {id, name, version, permissions[], enabled, path} + CatalogSource {name, url, pubkey, last_verified}
- Profile {id, name, environment, builtin} + EnvironmentManifest {runtime, web, domain, database, services, workers, scheduler, tunnel}
- Worker {id, project_id, command, count[1..16], timeout, memory} + WorkerStatus {pid, state}
- ScheduledTask {id, project_id|global, cron|every_*, command, last_run, next_run}
- ServiceStatus {id: mailpit|mariadb|postgres|mongodb|redis|nginx|apache|caddy, state, port, pid, kind: mail|sql|document|cache|custom|web, healthy, log_source}
  Web servers are proxied entries: WebManager owns the process, ServiceManager only lists and probes them (kind web, port = that server's effective HTTP port, healthy = TCP probe). + ConnectionInfo {host, port, user, password_ref}
  `log_source` names the log source holding that service's own output: `service:<id>` for a process-backed service (its stdout/stderr buffer, empty while stopped), `web:<id>:error` for a web server. It is what the UI opens Logs on, so "View logs" shows the service that was clicked instead of the app log.
- LogSource {id, name, kind: app|web|service|process|run}. Web ids are per server (`web:nginx:error`, `web:nginx:access`); the bare `web:error`/`web:access` still read the configured default server.
- ProcessInfo {id, pid, exe, args, cwd, env, state: Starting|Running|Stopping|Stopped|Crashed|Restarting|Failed, cpu, mem, exit_code}
- Settings (key-value JSON): runtime.php.global, runtime.node.global, paths.sites_dir, quickapps.projects_dir (blank = <install>\sites; blank/whitespace falls back to sites_dir), projects.roots, projects.removed (folders removed from list; rescans skip them), domains.auto, domains.auto_skip (deleted auto sites), web.*, database.default_tool.*, diagnostics.auto_fix, startup.*, notifications.enabled, api.*, updater.*, db.last_writer
  - `projects.removed` and `domains.auto_skip` are the two deletion skip lists, and together they are the deletion history the Settings → Excluded sites card reads. Entries are objects `{value, deleted_at}` where `deleted_at` is Unix milliseconds; lists written before that (plain strings) are still read and surface as `deleted_at: 0` ("date unknown"), so an existing skip is never lost. Same value twice keeps the newest timestamp instead of duplicating the row.
  - `DeletedItem {value, deleted_at, kind: project|domain}` is the read model: both lists merged and sorted newest-first. `kind` is derived from which list the entry came from and is not stored.
  - `db.last_writer` holds the process id of whoever committed to `app.db` last, written by every `save_setting`/`save_docs`/`save_values`. It is the cross-process change marker: the app caches its stores in memory, but the Explorer right-click menu (`shell_menu` → `olsc project add`) and the command line write the same database from a *separate* process, so without it a site added that way stayed invisible until a restart. The writer is identified by process id rather than by file time on purpose — under WAL a commit lands in `app.db-wal` and a later checkpoint moves `app.db` again, so the file timestamps do not line up with the writes and comparing them reported the app's own saves as outside changes. A run that has never written leaves the key absent, which reads as "nothing changed".
  - `quickapps.projects_dir` is stored the same way (relative when it points inside the app, absolute otherwise) and `get_setting` always answers the resolved full path, because the UI shows it in a text input and offers it as the parent folder for a new project. Blank/whitespace still means unset and falls back to the sites folder.
  - `startup.minimized` (bool, default true) is the sole authority on startup visibility for every launch, not just the Windows startup entry; `startup.close_to_tray` (bool, default true) governs the close button separately. The startup entry is written without `--minimized` so the two never disagree. The entry holds the absolute exe path, so it is rewritten at startup when that path no longer exists (a renamed or moved install would otherwise leave a valid-looking command pointing at nothing, and the app would silently never autostart). A *missing* entry is left alone, so autostart is never turned on behind the user's back.
- `HelperService {installed, version, outdated}` (read model, not stored): `version` is what the resident service reports over its pipe, and `outdated` compares it against the running app. The service is a copy of the helper in an admin-only folder, so an update or a move leaves it running the version it was installed with. `version: null` / `outdated: null` means the service is not answering at all — that is "not installed", not "out of date", and the two need different words on screen.
  - `startup.services` (list of service ids) is the only auto-start setting. Web servers are ordinary entries in it: one is applied (config rendered and validated) before it starts, so the user's sites answer. The former `startup.web` switch is read once for migration only -- a user who had it on gets the default web server appended to the list -- and is never written again.
- Secrets (OS keyring, never files): tunnel tokens, db passwords, api bearer hash, git per-host creds.
- Operation journal: Operation {id, kind, CoreCommand JSON, status: Running|Done|Interrupted, retry_hint}
- Snapshot zip: manifests + sites + cert meta + workers + schedules (+ optional .env/dumps/files; skips node_modules/vendor/.venv).
- Site bundle zip (§165, `*.olsbundle.zip`), format 1, written through `<name>.part` and renamed on success, manifest last:
  - `BundleManifest {format, app_version, created_ms, label, encrypted: bool, salt: Option<String>, options: BundleOptions, sites: Vec<BundleSite>, sha256: Option<String>}`. **`encrypted` means the `.env` files and the database dumps are sealed**, not the whole file: project files and settings stay readable so the bundle can still be reviewed, and the manifest is never sealed so a reader can see what is inside without the password. `salt` is the hex Argon2id salt, needed to derive the key before a single entry is opened; `None` when unencrypted. `sha256` is recorded so a copy can be checked on the way back in. A `format` above 1 is refused before anything is created.
  - `BundleSite {dir, project_id, project_name, project_path, hostnames: Vec<String>, settings: String, env_files: Vec<BundleEnvFile>, databases: Vec<DatabaseMeta>, file_count}`. **One entry per project, not per site**: sites sharing a project travel together and import back as one project, and a site with no project behind it is reported rather than exported half-way. `settings` is the site's configuration as a serialized `SnapshotContent` **with `env_files` cleared and `databases` reduced to the ones this bundle actually carries** (dump names are not in it at all), which is what keeps the manifest free of secrets; `content_of` puts the `.env` contents and the dump names back on read, so every import path downstream is the code a snapshot restore already runs. A database the export did not dump is therefore **absent from the bundle rather than present and empty** — the project's manifest lists every database it has, and importing a name with no data behind it would register a database that does not exist, which reads as a broken import rather than as a bundle that was asked to leave it out.
  - `BundleEnvFile {name, entry, sealed}` — `name` is the file's name in the project folder (`.env`, `.env.local`), `entry` its path inside the zip, `.enc`-suffixed when sealed. `sealed` is read per entry rather than assumed from the manifest, so a bundle whose manifest was edited cannot make a reader skip the key.
  - `BundleOptions {settings, env, databases, files}` — the selective choice, with `settings` and `env` defaulting on (small, and what "the site's configuration" means to most people) and `databases`/`files` off. All four off is refused rather than written as a zip holding nothing but a manifest.
  - `BundleSummary {path, size_bytes, sha256, sites, databases, env_files, file_count, encrypted, problems}` — what an export produced. `problems` is per site: one bad database must not cost the user the rest of the batch.
  - `BundlePreview {source, label, created_ms, encrypted, options, sites: Vec<BundlePreviewSite>, problems}` with `BundlePreviewSite {project_name, hostnames, existing, suggested, summary}`. **`existing` and `suggested` are what make the update/rename choice a decision rather than a guess**: `existing` is the hostnames already taken, `suggested` the free hostname each would get on a rename import. A site whose configuration document is damaged reports that here instead of silently offering suggestions that cannot be honoured.
  - `BundleImportResult {sites: Vec<BundleSiteResult>, unlocked: bool}` with `BundleSiteResult {project_name, action: created|updated|skipped, hostnames, safety_snapshot: Option<String>, changes, problems}`. `safety_snapshot` is the snapshot taken *before* an update, named so it can be put back; it is `None` for a created site, which is why an update is reversible and a create needs nothing.
  - Sealed entry = `nonce(12) || ciphertext + tag`, with the entry name's format as AAD. The key is derived **once per bundle** and every entry carries its own fresh nonce — a reused nonce under one key would break ChaCha20-Poly1305 outright, which is the one thing a per-file KDF would have made worse rather than better.
- `TaskView {id, kind, title, target, state: running|succeeded|failed|cancelled, steps: Vec<TaskStep>, progress: TaskProgress, results, problems, error: Option<Diagnostic>, started_ms, finished_ms: Option<u64>, cancel_requested}` (§164), with `TaskStep {label, state: running|done|failed|skipped, detail: Option<String>}` and `TaskProgress {done, total, bytes, bytes_total: Option<u64>}`. Linear in its steps: a task names the step it begins rather than carrying a list of states to keep in step with itself. `total: 0` means "not counted", so a bar is **indeterminate rather than full** — a task that has not said how much work it has must not look finished. `results` holds what each item contributed and `problems` what could not be done; they are separate because one bad database must not cost the user the rest of the export, so a problem is collected and never raised. `cancelled` is a state of its own, not a failure: a stop the user asked for is deliberate, and dressing it up as an error would be a lie about what happened. Tasks are in memory only; a task interrupted by a crash is reported by the Journal, which is the record that survives a restart.

- web.yaml {server}
- domain.yaml {hostname, https, wildcard}
- database.yaml {engine, version, host, port, database, username}
- services.yaml {redis, mailpit}
- environment.yaml (merged) + environment.lock {resolved versions}
- commands.yaml (merged QuickCommands)

Plugin (plugin.yaml):

QuickApp recipe YAML:
- {id, name, description, category, requirements{}, variables[]{id,label,type,required,default,validation,options,show_if,runtime}, steps[]{if, run/cwd/allow_failure | action + with}, files[], env_vars[], post_create[], install[], domain{}, environment{}}
- Variable types: text, number, boolean, select, multiselect, path, directory, file, password, secret, port, domain, runtime-version, database-version.

Schemas/interfaces (TypeScript core.ts mirrors Rust):
- CoreCommand (tagged union, ~200 variants), CoreResponse, Diagnostic{problem,cause,fix}, DashboardData, DomainSummary, HealthItem, WebStatus, CertInfo, ServiceStatus, ProjectDetail.
- ResourceLimits (settings key `resources`, all fields optional/null = the program's own default): mariadb_buffer_pool_mb, postgres_shared_buffers_mb, redis_maxmemory_mb, memcached_max_memory_mb, mongodb_cache_mb, cpu_percent, cpu_threads, cpu_limiter_path, node_max_old_space_mb, max_worker_count, max_processes, k6_max_vus.
  cpu_percent is 1-100 and is a share of *all* logical cores, matching `cpulimit`'s own meaning. cpu_threads is 1..=available_parallelism and is converted to that percentage, rounded up. Exactly one of the two may be set — validate refuses both — because two statements of the same limit is a setting the app would have to guess between.   cpu_limiter_path overrides the search for cpulimit.exe when the app has no copy beside it: the running exe's directory is checked first (where the installer puts it), then this field, then OLS_CPULIMIT_PATH, then the repo's vendor/cpulimit/cpulimit.exe (a compile-time path, so it only ever exists inside a checkout — what a dev build from target\ resolves), then %LOCALAPPDATA%\Programs\cpulimit, then PATH. A non-file value is skipped rather than ending the search. The binary itself is vendored at vendor/cpulimit/cpulimit.exe with a pinned SHA-256 checked on every build.
  CpuCapStatus {wanted, limiter_path, logical_cores, effective_percent, hint} rides on the `resources` response: the UI states a wanted cap and the tool that applies it separately, so it never claims a limit that is not in force.
- AutoBackupSettings (settings key `auto_backup`): enabled, scope: app|site, schedule (cron expression or a scheduler name, default `daily`), keep (1..=200, default 7), snapshots, include_env, include_files, databases.
  This is the app-wide plan. `validate` refuses an unparseable schedule, a `keep` outside 1..=200, and both `snapshots` and `databases` off, each naming the way out.
   - AutoBackupSiteSettings (settings key `auto_backup.sites`, keyed by hostname): enabled, schedule: Option<String>, keep: Option<u32>, include_files: Option<bool>, include_env: Option<bool>, databases: Option<bool>. **The period, the keep count and the choice of what gets copied all belong to the site when the plan is scoped to chosen sites**, because not every site is equally worth an hourly backup and one site's `.env` files are not every site's business; `None` means the site follows the plan, and `effective_schedule` / `effective_keep` / `effective_include_files` / `effective_include_env` / `effective_databases` on the read model say what actually runs. When the plan covers everything all five are dropped on save rather than stored, so there is never a second answer to a question the plan already answers. A site is covered through the project behind it, because a snapshot records the project, so a project with three sites is one backup. `validate` refuses three explicit `false` answers while the site is on — a site that copies nothing would take a config-only snapshot every period and call it a backup — and names the way out; `None` is "follow the plan", never "copy nothing".
   - AutoBackupSite (read model on the `auto_backup` response): hostname, project_id, project_name, enabled, schedule, keep, include_files, include_env, databases, effective_schedule, effective_keep, effective_include_files, effective_include_env, effective_databases, managed_by_plan. `managed_by_plan` is what lets a site's own page show the period, keep count and contents in force without offering an edit that would not be read.
- AutoBackupState (settings key `auto_backup_state`): buckets: map<string, AutoArtifact[]> + last_run. A bucket is one thing being backed up — `snapshot:<project_id>`, `sql:<engine>/<database>`, `sqlite:<path>` — and holds `AutoArtifact{path, created_ms}` newest-first. This record is what makes retention safe: only recorded paths are ever deleted, so a backup the user took by hand, however old, survives every pass.
- AutoBackupRun {started_ms, finished_ms, created[], removed[], problems[]} is one pass in words the UI shows verbatim. AutoBackupStatus {settings, description, next_run_ms, running, last_run, kept: map<string, usize>, sites} is the whole read. Under the `site` scope `description` says "each site's own period" and `next_run_ms` is the soonest of the sites' own next runs, because there is no single period left to describe.
- SettingsService and CustomInstallStore derive Clone. A read that must do slow work clones the store and releases its lock rather than holding it across that work, so lock scope is part of the model's contract, not just of the call site.
