# OLS — Full Documentation

## 1. Introduction
olsc is a Windows-local development environment manager. It downloads and runs PHP, Node, databases, caches, mail, and web servers, gives each project isolated runtimes plus own `.test` domain with trusted local HTTPS, without manual system edits. Pre-release, stage 15/20. Portable `data/` beside exe; `OLS_HOME` overrides paths.

Scope: runtimes (PHP/Node/Python/Composer), databases (MariaDB/Postgres/Mongo/Redis/SQLite), web (Nginx/Apache/Caddy), projects (detect/setup/env/git/workers/scheduler/snapshots), domains + TLS + DNS, tunnels, diagnostics/doctor, plugins, quick-apps/commands, AI assist, local API, CLI, updater.

The app database retains its existing `docs` and `settings` tables. Before stores load, additive `PRAGMA user_version` migrations back up app.db and present WAL/SHM sidecars; version 1 adds six JSON read views and expression indexes, and version 2 prunes/collapses only operation records. Each migration is transactional. A failure rolls back, logs a `Diagnostic{problem,cause,fix}`, and lets startup continue with the old records. `list_projects` optionally returns view-derived unconnected project IDs for Add Site and the Projects create-site guard; clients keep the legacy matching path if the view is unavailable.

Version: 1.1.0 (workspace `Cargo.toml` and `src-tauri/tauri.conf.json`; release notes in `release-notes/v1.1.0.md`, change summary in `CHANGELOG.md`). `ui/package.json` stays at 0.0.0 — it is a private workspace root and never shipped.

## 2. Architecture
One core, many front doors. `ols-core` holds all logic behind `Core::dispatch(CoreCommand)`. Tauri shell exposes single IPC `run_command`; CLI talks over named-pipe control channel (auto-spawns daemon); HTTP API posts same JSON to `127.0.0.1:7420/v1/command`.

See `architecture_overview.md` and diagrams:
- `diagrams/architecture.mmd` — system context
- `diagrams/dataflow.mmd` — setup-to-healthy flow
- `diagrams/classes.mmd` — core classes
- `diagrams/sequence.mmd` — domain + apply sequence

State: `Arc<Inner>` shared across threads; lock order domains-first. ProcessSupervisor owns Tokio runtime + all children. Managers communicate via broadcast events (`process-event`, `terminal-event`, `runtime-event`). Core state locks are taken through `app::lock`, which recovers a poisoned guard instead of unwrapping it: a `std::sync::Mutex` stays poisoned for the process after any panic while held, so the old `.lock().unwrap()` turned one failure into every later read panicking too — and a page waiting on such a read waits for the rest of the session. No store lock is held across blocking work; `project_detail` clones the settings and custom-install stores and drops the guards before `build_detail` does its file I/O and version probes.

Privilege model: main app never elevated. `ols-helper` closed set (hosts-apply/remove, nrpt-add/remove, install-service) via UAC (direct Win32 `ShellExecuteExW` with `runas`) or LocalSystem pipe service with SDDL lock. Elevation runs natively without invoking PowerShell, eliminating process overhead, argument quoting discrepancies, and PATH lookup failures. System binaries (powershell.exe, cmd.exe, netstat, tasklist, taskkill, netsh) resolve directly via `GetSystemDirectoryW` (%SystemRoot%\System32).

Helper pipe calls are bounded: a request waits at most 10s for the service's reply, then falls back to running the change un-elevated/elevated. A wedged or killed `ols-helper` must never block the caller indefinitely — `apply_web` waits on the helper, and an unbounded wait there froze the web state lock and with it every command in the app.

## 3. Modules
### 3.1 System core
Dispatch, state, IPC, infra. `lib.rs` re-exports; `app/` Inner state + modular impls (domains, projects, web, quickapp, system); `command/` modular dispatcher and types (types.rs, dispatch.rs); `control.rs` named-pipe RPC with token; `api.rs` localhost HTTP with bearer + allowlists; `paths.rs` resolution; `settings.rs` atomic JSON; `secrets.rs` keyring; `process.rs` supervisor; `port.rs` conflict reporter; `exec.rs` capture helper; `error.rs` Diagnostic shape; `logging.rs` + `redact.rs`; `diagnostics.rs` findings engine; `repair.rs` doctor; `search.rs` global search; `support.rs` bundle; `network.rs` probe; `journal.rs` op log; `resources.rs` caps; `elevate.rs` helper runner (pipe reply bounded to 10s; fast single-attempt status check without sleep loop; direct Win32 `ShellExecuteExW` `runas` elevation avoiding PowerShell and PATH lookup; helper freshness uses independent `ADMIN_HELPER_VERSION`, so app-only updates do not ask to reinstall the elevated service).

### 3.2 Runtime
`detection.rs` takes the project PHP requirement from `composer.json` and raises it to the version in `vendor/composer/platform_check.php` when that is higher (auto-fix and project commands use the resolved PHP);
`catalog.rs` pinned HTTPS+SHA256 manifests; `catalogs.rs` minisign-signed remotes; `runtime.rs` download-verify-extract + probe; `php.rs` per-version php-cgi pools + extensions (PECL builds only when `catalog/pecl-pins.json` pins their SHA-256, verified before extraction; unpinned matches are refused with the reason); `nodepm.rs` lockfile/corepack; `composer.rs` reader; `venv.rs` finder; `custom_install.rs` pinned paths win; `resolver.rs` manifest>detected>global; `detection.rs` marker scan; `plugin.rs` declarative plugins (wasm refused); `updater.rs` signed self-update.

### 3.3 Services
`service.rs` DB/cache/mail lifecycle + TCP probe; `custom_service.rs` user procs (custom- prefix, no shell); `dbtools.rs` external GUI detect + unified External Tools gallery with presets, JSON import/export, args/clipboard launchMode, unavailable state, and test launch; `mail.rs` per-framework Mailpit planner with diff; `monitor.rs` sysinfo CPU/mem/disk + per-PID rollup + site cost; `workers.rs` up to 16 copies; `scheduler.rs` 1-min cron tick, no overlap. ServiceManager owns `Starting|Stopping|Restarting|Running|Stopped|Error` per-service state, `desired_state` (`DesiredState::Running | DesiredState::Stopped`), and emits batched `service-status-event` updates. Desired state changes only via explicit start/stop commands across all front doors (GUI buttons, Start all / Stop all, tray menu, CLI, API) inside core command handlers; unexpected process exits leave `desired_state = Running`. Diagnostics and environment health report stopped services (`web_stopped`, `web_running`) only when `desired_state == Running` and the service is not currently transitioning or startup-settling. Core dispatch begins transitions before work starts and publishes the resulting state at completion; failed starts settle in Error. Auto-start services initialize `desired_state = Running` and register startup settling that suppresses stopped findings until autostart completes or 30s passes. `ApplyWeb` and "Fix all" never start a server whose desired state is `Stopped`. The UI initializes its event subscription and status snapshot at app mount, regardless of the active page, so service changes are reflected when navigating to a service page. Start/stop are verified, not fire-and-forget: `start` waits for the spawn to be decided (`ProcessSupervisor::wait_for_spawn`) and returns the OS error if the process never existed, keeping the reason in `start_failures` so it survives the dead process record; `stop` waits for exit and says so when a kill was ignored. Every service start goes through `ServiceManager::start_capped`, which is where the Resources CPU cap (§129, `resources.rs`) is applied; web servers are capped the same way in `web/manager.rs`. Auto-start reads one list (`startup.autostart_services`) for every service, web servers included, dispatches each through `CoreCommand::StartService`, and applies a web server's config before starting it rather than only spawning the process.

### 3.4 Web
`web/mod.rs` trait + SiteSpec; `web/manager.rs` render-validate-backup-apply-reload-health + rollback + drift (error-log tails read at most the last 4 MB); `web/nginx.rs`, `web/apache.rs` (foreground httpd, no service), `web/caddy.rs` (auto-HTTPS off, local CA, stable per-install localhost admin endpoint shared by run/reload/stop); `domain.rs` validation; `ca.rs` deterministic root 2024-2044 via rcgen; `certs.rs` per-domain reuse unless SAN/<30d; `hosts.rs` idempotent block; `dns.rs` UDP wildcard; `health.rs` 5-step chain; `tunnel.rs` provider abstraction + confirm gate + port blocklist + one start per tunnel at a time (`begin_start` guard: a concurrent start waits, then reports the live tunnel); `inspector.rs` forwarding proxy, 500 req, redacted. Each renderer also emits the per-server `localhost/<prefix>` routes file, one block holding a proxy location per routed site.

### 3.5 Data
`dbbackup.rs` mysqldump/pg_dump with safety copy; `sqlite.rs` WAL-safe .backup + integrity_check; `migrate.rs` (which never offers the current import-target MariaDB data folder as a source, whether detected or browsed) auto-detects Laragon/XAMPP/Wamp and installed OLS MariaDB series, validates manually selected data folders and nearby binaries, then imports selected source batches in order. The Import button remains visible while scanning and becomes enabled after every selected folder is scanned and at least one database is selected. Conflict policy is explicit and defaults to Skip Existing; Replace Existing flushes and atomically finalizes a SQL safety backup before writing a durable recovery record and dropping the target; interrupted replacements restore from that backup on startup. New imports write a recovery record after destination creation; interrupted partial schemas are removed on startup. Completed imports atomically record their commit before recovery data is cleaned, and failures retain pending recovery records for retry. Rename Incoming rewrites the dump's CREATE/USE statements and creates a unique `<name>_imported[_N]` database. Destination names are refreshed between source batches so duplicates across sources resolve under the same selected policy. Stopped sources are read from temporary copies; source folders are not changed. `auto_backup.rs` §130 scheduled snapshots + database dumps, with per-item retention that only ever deletes files it recorded (the running flag is a drop guard, so a panicking pass releases it); `sitebundle.rs` §165 site bundles (selective + batch export, encrypted secrets, import with a snapshot before any update); `crypto.rs` the Argon2id + ChaCha20-Poly1305 sealing a bundle's `.env` files and dumps; `tasks.rs` §164 the background task registry the Processes page lists.

### 3.7 CLI / Helper / Shell / UI
CLI `olsc` (`crates/ols-cli`) never manages directly; modularized into clean submodules (`args.rs`, `ctx.rs`, `commands/system.rs`, `commands/projects.rs`, `commands/services.rs`, `commands/extensions.rs`, `commands/ai.rs`, `commands/docker.rs`, `tests.rs`); daemon mode runs core headless + scheduler clock. Helper validates ip=127.0.0.1/::1 and suffix leading-dot. Tauri shell builds tray from domains/services, single-instance, close-to-tray. Status icon: the official mark is the green 3D server-stack circular mark (`src-tauri/icons/*`, generated from `src-tauri/icons/source/icon-light-running.png`); the red twin (`src-tauri/icons/red/`) is painted on the tray icon, the main window (taskbar) and the in-app sidebar mark whenever no service and no supervised process is running, and forced while the app is shutting down. The decision lives in `status_mark` (lock-only checks, no port probes) and is applied by `sync_status_icon` after every IPC command, from the tray menu, on every process event, after autostart, and on a 2s clock so `olsc stop` over the control channel, the scheduler and crashes are covered too. `status_mark` asks `ServiceManager::any_running` and then `ProcessSupervisor::is_alive` per snapshot record — the same rule `any_running` and `prune_finished` use, because a hand-written `Running | Starting` filter disagreed with `is_alive` on `Restarting` and so could call a process both alive and dead in the same tick. `Mutex<Option<bool>>` makes it repaint only on a real change, but the state is cached *after* the repaint is confirmed rather than before: a mark that raced the tray's own creation (the process-event subscriber is registered before `build_tray`) is retried by the next 2s tick instead of being frozen for the session, and every `set_icon` error is logged rather than dropped. It is emitted to the UI as `ols:status-icon` (ui `useServerStopped`) on every repaint *and* on every `show_main_window` reveal, because that channel is push-only and a webview mounting after the last state change would otherwise never learn the mark. `ui/public/favicon-stopped.svg` is the in-app red twin of `favicon.svg`. UI `core.ts` sole IPC wrapper, modularized into `core/` submodules (`core/types/*`, `core/commands.ts`, `core/responses.ts`, `core/client.ts`, `core/index.ts`); no router, page state + `ols:navigate` events; `Sidebar` provides persistent navigation with static non-collapsible category groups; `useWeb` shared poll 4s; pages per concern (see catalog.txt).

### Rust core essentials
- `lib.rs`: Purpose: crate root + re-exports. Key exports Core/CoreCommand/CoreResponse. Depends on command/paths/process/project/runtime/service/settings.
- `app/`: Purpose: shared Inner state + modular impls (domains, projects, web, quickapp, system). Holds supervisor/runtimes/services/certs/php/web/terminals/journal/workers/tunnels/api/ai. Lock order domains-first; every core lock goes through `lock()` (poisoned guards recovered) and is released before any blocking I/O. In `sync_auto_domains`, checks whether any domain already serves a project (the `has_any_domain` guard: a domain matched by `project_id`, by site folder/root path, or by a hostname containing the project name — any TLD) before creating the `<folder>.<default-tld>` domain, so changing the default TLD in Settings never renames or duplicates an existing site; auto-links project IDs by folder/root match, strips default TLD suffixes, and auto-links project IDs in `add_domain`. After re-reading the stores in `reload_external_changes`, adopts the writer marker (`db::adopt_ownership`) only when both stores loaded cleanly, so one foreign write costs one re-read, not one per subsequent list command (a failed load keeps retrying). The non-recursive project watcher compares immediate directory snapshots before calling the full auto-domain sync, so file-level root events still notify project subscribers without repeatedly scanning every project and domain.

- `runtime.rs`: Purpose: verified installs only. Zip root-strip, PATH probe 60s cache, temp version probe, broadcast Installed/Failed. One `InstallControl` per in-flight `id@version` carries the pause/cancel flags the Runtimes page drives; `install_one` returns `InstallOutcome::{Done,Failed,Cancelled}` so a user stop is never reported as an error, and the control is dropped with the install so a late pause cannot address a finished one. If static checksum verification fails (or cache-hit hash mismatches), `install_one` queries `resolve_online_manifest` to verify against live upstream vendor sidecars or API release digests (Apache Lounge `.txt`, Node `SHASUMS256.txt`, PHP `releases.json`, MariaDB API, Composer `.sha256sum`, MongoDB `current.json`, Python `index-windows.json`, and GitHub release asset digests for Redis, Memcached, Mailpit, Caddy, k6, Git). When the online checksum matches, the in-memory manifest is updated, an informational warning is logged, and the download is accepted without compromising verification safety. `refresh_online_catalog{id}` reads each vendor's public release feed and keeps the result in memory only. Apache Lounge publishes Windows x64 binaries under `/download/VS18/binaries/` along with `.txt` checksum sidecars; `linked_download_url` extracts the full `.zip` archive URL from anchor `href` attributes, ignoring 32-bit `win32` archives and non-zip links, while `parse_apache_sha256` reads the SHA256 line from `<url>.txt` (sending the required Referer via `download_referer`). PostgreSQL's EDB feed is the one HTML page among them: it is parsed per `Binaries from installer` block, taking the version that follows the `Version` label (React puts a `<span>` and a `<!-- -->` comment between them, so the two are never adjacent) and the href of the `alt="Windows x86-64"` anchor in that block, never the first `getfile.jsp`, which is often Mac OS X. Absolute `sbp.enterprisedb.com` hrefs are used as given, and a version with no Windows anchor is not offered. The href is a redirect, so `resolve_online_manifest` resolves the final `get.enterprisedb.com` URL over a ranged GET; the page carries no checksum, so the download digest is recorded, and the built-in 17.6 pin keeps its self-pinned hash. A transfer that ends early is rejected rather than cached: the byte count is compared against the advertised Content-Length and a short file is deleted, because for a vendor that publishes no checksum (postgres, nginx) the cache-hit test trusts *any* existing file — a truncated archive would be reused forever and surface much later as `invalid Zip archive: Could not find EOCD`, naming neither the cause nor the fix. For the same reason a cached zip is only reused when its end-of-central-directory record is present (`zip_has_eocd`); a non-archive runtime such as composer.phar has no EOCD and is trusted as-is. MariaDB's rest-api is keyed by **branch**, not by full version — `mariadb_branch` cuts `13.1.1` to `13.1`, because `/rest-api/mariadb/13.1.1/` answers 200 with a `release_data` document that has no `releases` map, which made every 13.x install fail as unavailable; the branch's published SHA-256 is still required before the archive is accepted.

- `tasks.rs`: Purpose: background work the user starts and watches (§164). A task is a `TaskView` plus a thread, not a future the UI polls a closure for: `start(kind,title,target,total,work)` returns the id to watch it by and `work` receives a `TaskHandle` that names the step it begins (`begin_step`/`end_step`/`fail_step`), reports items (`advance`, throttled to 200ms), collects what each item contributed (`result`) and what could not be done (`problem`, never raised — one bad database must not cost the user the rest of an export), and closes itself (`succeed`/`fail`/`finish_cancelled`). Every mutation publishes the **whole** view, so a UI renders straight from the event and never reconciles a delta. A `FinishGuard` fails a task that neither succeeded nor stopped, so a panicking worker cannot leave a spinner on the page forever. `cancel` sets a flag the worker checks *between* items and `command.rs::report` turns the resulting error into `Cancelled` rather than a failure, because a stop the user asked for is deliberate. `dismiss`/`clear_finished` drop finished tasks only; the 200-entry cap trims the oldest finished first; a running one is never dropped. `set_phase(step,total)` opens a new phase with its own denominator — it opens the step and resets `done`/`bytes` — for work whose units change halfway (an export reads one item per site, then writes one per file); one denominator for both would either stall at the site count or finish long before the writing is done, which is what a bar that sits still and then jumps is. In memory only — a task interrupted by a crash is reported by the Journal instead, which is the record that survives a restart.
- `crypto.rs`: Purpose: the password on a site bundle (§165). Argon2id (19 MiB / 2 passes / 1 lane, the OWASP parameters, deliberately identical on every machine so a bundle written on one opens on another) turns the export password into a key; ChaCha20-Poly1305 seals each entry under it. Per entry, not per zip, because the zip crate's own AES scheme is ZipCrypto-derived and weak, and because a reader can then unlock exactly the entry it needs. The key is derived **once per bundle** (salt in the manifest, fresh 96-bit nonce per entry): per-file derivation would cost ~60 ms times the file count for no extra safety, while a reused nonce under one key would break the cipher outright. `open` returns `Unseal` for both a wrong password and a damaged file, and the error says so — an AEAD cannot tell them apart, so the message must not claim to.
- `sitebundle.rs`: Purpose: exporting and importing whole sites, in one file, on purpose (§165). `BundleOptions{settings,env,databases,files}` is the selective choice (settings and `.env` on by default — small, and what "the site's configuration" means to most people; data is asked for) and an all-off selection is refused rather than written as a zip holding nothing but a manifest. Sites are **grouped by the project behind them**, so exporting `shop.test` and `blog.test` of one project gives one entry with two sites and imports back as one project, not two; a site with no project has nothing to describe and is reported, never exported half-way. The manifest stores each site's configuration as a `SnapshotContent` with `env_files` cleared and every `dump` set to `None`, so the manifest itself never holds a secret (DDNS credentials are removed by `snapshot_content` through `ddns_keyring::without_credentials`, and a restore onto an existing site keeps that site's own); `content_of` puts both back on read, so every import path downstream is the code a snapshot restore already runs. Only `.env` files and database dumps are sealed — the two places passwords live; project files and settings stay readable so the bundle can still be reviewed, and the dialog says which is which. `preview` reads only the manifest and reports, per site, which hostnames already exist and which free name a rename would take, so the update/rename choice is made on facts. `import_bundle` with `OnConflict::Update` finds the project owning the first colliding site, **takes a snapshot of the current state first** (label `Before import`, named in the result, so the update is reversible rather than a leap of faith) and applies the bundle on top; with `Rename` it registers a new project folder and adjusts everything the collision would have made ambiguous — hostname, database, port — through the same `Adjust` a clone uses. A site that fails lands in `problems` and never aborts the batch. Names a bundle supplies never choose where a file is written: `apply_config` skips a manifest file whose name is not a plain file name (`is_plain_file_name`), and `restore_dumps` refuses an engine or database name that is not `is_safe_identifier` before writing its temporary dump (Windows collapses `..` in a path without checking the folders exist). An import that keeps a project's own name keeps its hostname: `rename_host` rewrites a label equal to the old slug for the new one, and with the two the same the rewrite came out unchanged and fell through to the prefix branch, so importing `wordpress-test` under its own name created a second site `wordpress-test.wordpress-test.local` beside the real one. Progress is counted in the units the work is made of — the export counts sites while it gathers and then, through `set_phase`, zip entries while it writes; the import counts, per site, the files, `.env` files and dumps the manifest already declares, and reports bytes as `extract_files` copies, because the zip knows every entry's uncompressed size before the first byte is written. Counting sites alone left the bar at one step through a whole file copy or database restore. A database an import is about to load a dump into is moved to `<name>_bkp` first (`_bkp-2`, `_bkp-3` if those are taken) rather than merged into: a dump says nothing about tables it does not mention, so loading over a live database leaves something that is neither the bundle nor the old site, and the moved copy is still there to look at. The move is `ServiceManager::rename_database`, and on MariaDB it is **not** a statement — `RENAME DATABASE` and `RENAME SCHEMA` are MySQL-only and the server answers `ERROR 1064`, so that path is a dump-and-copy (`dbbackup::dump_to`, `load_into`, then `DROP DATABASE`), while PostgreSQL keeps `ALTER DATABASE ... RENAME TO`.

### Tauri / CLI / Helper
- The tray has one dynamic Start all / Stop all item. Dashboard, tray and CLI use the same `ServiceAggregate` for the running count and enabled Start all targets: configured autostart services (resolving `web` to the default server), or all installed services if none are configured. The count covers running web servers, databases and services; tunnels and workers are excluded from that service count, but `StopAll` still stops them. Tray Stop all asks through the preloaded, hidden, app-themed `TrayConfirmationWindow` when `tray.stop_all.confirmation.enabled` is true (default); turning it off dispatches the same StopAll action directly. Exit from the tray, UI exit action, or main-window close asks only when `exit.confirmation.enabled` is true (default); these preferences are independent. The main window remains hidden while the separate confirmation appears. Its opaque, rounded, borderless surface uses the same `--app-background` token as the main UI; its entrance animation starts after the native window is shown, and its opening, confirm, and cancel sounds match the synthesized sounds in `ignored/nileask.cs`. Only approval dispatches `CoreCommand::StopAll` or begins shutdown. Dashboard Stop all and CLI Stop all dispatch directly. The tray keeps the toggle handle in managed state, updates it on service-state events, and rebuilds submenu dots/counts from one aggregate snapshot. The Web submenu also uses one Start/Stop toggle and keeps Reload separate. The Quick App submenu lists favorite recipes only as direct Create actions; selecting one sends its id and name so the wizard can show the correct recipe immediately while loading details. With no favorites, it says so; Browse all always opens the full catalog.
- Deferred Settings, Resources, Web config, and site-settings forms share `useDirtyForm` and one `DirtySaveBar`: a fixed bar slides in only when the current snapshot differs from the saved one, reserves bottom content space, stays right of the app or dialog sidebar, and offers Save and Discard. Save errors render in the bar; Ctrl+S saves dirty forms; beforeunload and guarded app/modal navigation warn before discarding. Instant-apply toggles, service actions, and explicit actions such as “Back up now” are not registered; the General card's confirmation and diagnostics switches are registered, so they save through the bar rather than on toggle. Site-dialog placement uses `--dialog-surface`, matching the modal surface. - The export dialog's destination defaults to `paths.backups_dir` — the app's own `<root>/backups`, resolved by the core (`GetSetting{key:"paths.backups_dir"}`, computed like `paths.sites_dir` and never stored, so a moved or portable install is followed rather than guessed) — and is prefilled rather than left blank, with the same path as the placeholder and a link back to it if the user browses elsewhere. A field that opens asking "where?" for a choice that has a right answer is a question, not a setting. It is filled **once** per open, so clearing the box to retype a path does not snap the default back under the cursor.
- The Sites table tabs begin with **Enabled** (selected by default, green check icon) and **Disabled** (red disabled-circle icon), followed by the available website-type filters and **All** last with a sky-blue list icon. Projects without a domain display a subtle `FolderCode` icon in both their group tab and row subline rather than the bright HTML5 icon. Enabled/Disabled filters include only actual sites; project-only rows remain available under their type filter and All. Counts follow the current search, bulk enable/disable updates the displayed rows optimistically, and an individual enable/disable refreshes the list alongside applying the web configuration so the row moves to the matching status tab immediately.
- `TasksPanel` (Background tasks page): merges task-manager jobs from `list_tasks` and `task-event` with persisted UI command history. User operations show in a five-column table (task, site/target, status and details, updated time, actions), newest first, paginated at 10 rows by default with 10/25/50/100 row sizes. The horizontally scrollable table works in narrow windows. User operations remain after restart; runtime/service start, restart and reload actions are excluded. Progress bars, steps, results, problems and failure Diagnostics remain available for registered task-manager jobs; user-requested cancellation is badged "Stopped". Stop remains immediate; removing one finished task (including grouped repeats) or clearing all finished tasks asks for confirmation. Clearing history leaves running tasks active.
- The Add Site project picker uses the selected project's detected document root instead of always serving the project folder. This applies to every supported project type with a detected root; when detection reports none, the project folder remains the root. Choosing a folder manually afterward keeps that folder.

## 5. Business Rules

### Page scrolling (one scroller per page)
- Window and app shell (`App.tsx` root `h-screen overflow-hidden`, `<main>` `flex min-h-0 flex-1 flex-col overflow-hidden p-6`) never scroll. Only one region per page scrolls.
- Every page renders `ui/src/components/PageLayout.tsx` with `header` (title, description, primary actions), optional `toolbar` (search, tabs) and optional `footer`, all `shrink-0`. Modes: `list` (content is a `ScrollableList`, which owns the scroller; table header sticky via `<TableHeader sticky>` + `Table wrapperClassName="overflow-visible"`), `scroll` (content region scrolls as one, class `ols-scroll`), `fill` (content fills the height and scrolls internally, e.g. Logs).
- `ols-scroll` (index.css): `overflow-y:auto`, `overscroll-behavior:contain`, `scrollbar-gutter:stable`, thin themed scrollbar. Content region keeps `min-h-[240px]`; on very short windows the PageLayout wrapper scrolls instead. `resetKey` resets scrollTop on search/tab changes, not on row updates.
- Sites/Projects bulk bar and pagination live in the `ScrollableList` footer so rows never shift. Overlays use z >= 60, above sticky headers (z-10).
- Classification: list = Sites, Projects, Runtimes; scroll = Dashboard, Services, Plugins, Profiles, Tunnels, Tasks, Processes, Databases, Docker, Commands, Config, WebServer, QuickApps, Settings; fill = Logs.
- Runtimes "Add a runtime" panel is one `@container` row: Scan folder, divider (@2xl), runtime select + Version (w-44 at @2xl) + Locate.
- A user-visible file name is safe to rename; an addressing key is not. The app ships as `OLS.exe`, the setup as `OLS-<version>-setup.exe`, the zip and the SHA256SUMS file to match, and the Inno `AppName` is `OLS` — while `AppId` (`dev.openlocalserver.app`), `DefaultDirName` (`C:\OpenLocalServer`), `C:\Program Files\OpenLocalServer\`, the `openlocalserver.exe` daemon, the `OpenLocalServerHelper` service and pipe, the hosts markers, the NRPT comment, the keyring service, `.openlocalserver/` and `openlocalserver.test` all stay exactly as they are. The distinction is what the name *is used for*: a file name is looked up on disk and nothing reads it back as an identifier, whereas a registry value, service name, pipe name or domain is an addressing key, and renaming one orphans live state with no recovery path (`docs/BRAND.md` §4.3). The one rename that would have been unsafe without code is the file lock on upgrade, which is why the old exe name is carried through every "is it running?" check and the old file is pruned at install time. The app resolves its own path with `std::env::current_exe()` rather than a literal, so no Rust code changed for the rename.
- An update that reports success has to have replaced the binary. Windows locks a running image, so an installer started while the app is alive cannot overwrite `OLS.exe`: the old version survives and the user is told it updated. The rule is enforced on both paths, because either one alone leaves the other broken. `updater::install_update` spawns the verified installer and then exits the process on a short timer, so the file lock is gone before the installer reaches `[Files]`. Run by hand, the installer closes it itself, and the `[Code]` section is the half that matters: it asks once, with an explanation, then stops the images that actually hold a file in the destination folder, matched by PATH rather than by name. `CloseApplications` / `RestartApplications` are the Restart Manager backstop for anything that missed, and `CloseApplicationsFilter=*.exe|*.dll` covers `ols-helper.exe` and `cpulimit.exe`, which ship beside the app and are not in the app's single-instance mutex. **The rename makes the name check load-bearing in a second way**: `AppExe` is `OLS.exe` and the pre-rename `LegacyAppExe` is checked beside it everywhere — `RegisteredDir`, `AnyAppRunningHere`, `InitializeSetup`, `PrepareToInstall` — because an install made before the rename is still running under the old name and holds the exact file `[Files]` writes. `PruneUnshippedFiles` omits `LegacyAppExe` from the shipped list, so the old exe is deleted at `ssPostInstall`, after `PrepareToInstall` has confirmed the image is closed. `scripts/build-installer.bat :app_running` applies the same three-name rule (shipped, legacy, cargo bin `openlocalserver.exe` for a dev build) before it stages anything. A second launch after the install is harmless because the app is single-instance. Related and separately fatal: `build-installer.bat inno` recompiles nothing, so an installer that is older than the source is a stale `target\release`, which is why that mode now prints each staged file's timestamp before shipping it.
- A rename that a fresh install honours is not necessarily a rename an upgrade honours. The Inno `DefaultGroupName` is `OLS`, but a machine that already has the pre-rename build keeps a Start Menu folder named `Open Local Server` after upgrading, and the new shortcut is written *inside* it, because an upgrade takes the group name from the previous install's uninstaller rather than from `[Setup]` — the old uninstaller has to be told which folder to clear, so that folder's name is data, not configuration. No setting in `[Setup]` can change it. `MigrateLegacyStartMenuGroup` closes it at `ssPostInstall`: `.lnk` entries move into the current group folder, a name that already exists there is deleted rather than overwritten (that copy is the one `[Icons]` just wrote), and the legacy folder is removed only when it ends up empty and never recursively, so anything the user filed in there survives. Every failure is logged rather than raised — an install that installed correctly must not be reported as failed over a Start Menu folder.
- A CPU limit is a real cap, or it is refused. §129 caps a service through the `cpulimit` utility (`cpulimit <percent> <program> <args>`, a Windows job object with a hard CPU rate), so a wanted cap whose utility is not installed fails the start with the way to install it — a service that quietly runs uncapped under a UI that says "limited" is the failure this rule exists to prevent. The utility is **vendored, not downloaded**: `vendor/cpulimit/cpulimit.exe` (kz370/win-utils, MIT) with a pinned SHA-256 in `vendor/cpulimit/README.md` and `CPULIMIT_SHA` in the build script, checked on the source and again on the staged copy, so a tampered or corrupted copy cannot reach an artifact. The installer places it next to `OLS.exe` and `find_cpu_limiter` looks **there first** — before any path saved in settings — which matters because the settings database is shared between a dev build and an installed one: a path saved while running from `target\` would otherwise leave an *installed* app pointing at that dev machine's folder forever. A configured path is the fallback for when the app has no sibling copy, which is the only case the Resources card offers that field. A configured path that is not a file is skipped rather than ending the search, so a stale setting cannot disable the cap in an otherwise correct install. A dev build from `target\` has no installed sibling, so it falls back to the repo's own `vendor/cpulimit/cpulimit.exe` (reached through a compile-time `CARGO_MANIFEST_DIR`, which does not exist on a user's machine) rather than to a stray `%LOCALAPPDATA%` install that has nothing to do with the checkout — so the card reports the binary this build actually shipped, in the dev build as well as after installing. The percentage is a share of *every* core, not of one, and the UI says so and offers threads instead, converted against `available_parallelism` and rounded up so "1 thread" is never under the core asked for. `cpu_percent` and `cpu_threads` are mutually exclusive: two ways to state the same limit is a setting the user has to reconcile, not one the app guesses at. The cap lives as long as the service, since `cpulimit` stays in the process tree and exits with the program's own code, so stop/restart/crash recovery are unchanged.
- A loading state is never a terminal state. Any read whose result gates rendered content is deadline-bounded (`runCommandWithin`) and its failure is stated as a Diagnostic with a Retry, because the alternative is a page that says "Reading the project…" forever and blames the user. `get_project_detail` for a project that is no longer registered is a stated failure ("This site has no project any more", with the re-register fix), not a silently dropped id.
- A site bundle carries what the user picked, and only that (§165). Four independent switches — settings, `.env` files, database, project files — because they differ by orders of magnitude and a "site export" that quietly includes a 4 GB `node_modules` is not an export anyone asked for. Settings and `.env` are on by default; data is asked for. An export with nothing selected is refused rather than written as a zip holding nothing but a manifest.
- A bundle is one file per export, keyed by project, and it never clobbers. Sites sharing a project travel as one entry, so they import back as one project rather than several one-site projects. The file is written through `<name>.part` and renamed on success, with the manifest **last**, so an interrupted export never leaves something that claims to be complete. The name carries a millisecond stamp and takes a suffix rather than overwriting, because an export that destroys the previous one is not a backup.
- Passwords in a bundle are the user's decision, and the app never keeps the answer. The export offers to encrypt; when it does, the `.env` files and the database dumps — the two places passwords actually live — are sealed with a key derived from the export password (Argon2id, then ChaCha20-Poly1305 per entry, fresh nonce each). Project files and settings are **not** sealed, because they are source code and configuration the user can read anyway and sealing them would make the bundle impossible to review; the dialog says which is which rather than implying the whole file is protected. The password is never stored, never logged and never recoverable, which is why the generated one is shown once, in monospace, next to a "write it down" hint, and why losing it is stated as the consequence rather than discovered at import. The manifest is never sealed, so a reader can see what a bundle holds without the password — and cannot see a single secret value in it, because the `.env` contents and dump names are stripped out of the stored configuration document and listed separately. A wrong password and a damaged file are indistinguishable to an AEAD, so the error says both instead of guessing which it was.
- Importing onto an existing site is reversible by construction. A site name that already exists is not overwritten silently: the preview says which hostnames clash and which free name a rename would take, and the user chooses — update the existing site, or create a new one under a different name. An update **takes a snapshot of the current state first**, labelled "Before import", and names it in the result, so "update" is a step the user can undo rather than a leap of faith. A rename adjusts everything the collision would have made ambiguous — hostname, database, port — through the same machinery a clone uses, so both copies run. One site failing never aborts the rest of a batch: failures are collected and reported per site, because an export of twenty sites must not cost the user all twenty because one database was down.
- Work the user does not wait on is work the user can watch (§164). An export or an import answers immediately with a task id instead of blocking on the answer, and the task carries its own steps, its own progress and its own report, so a long job is never a frozen button. A bar with no known total is indeterminate rather than full, a problem is collected rather than raised, and a stop the user asked for is reported as a stop — never as a failure, because it was deliberate. Cancelling happens between items, so a half-written project is never left registered.
- A site export is available from the row, not only from a selection. A single site's `⋯` menu carries "Export to bundle…", because the common case is one site and making the user first tick a checkbox to export it is a step that exists only to satisfy the bulk path. Both entry points drive one dialog rendered once on the page, and both hand the started task off to the Processes page, which is where it is watched.
- Resolution manifest > detected > global; global never overrides explicit.
- Downloads require HTTPS + SHA256; mismatch aborts; catalogs minisign-verified each load.
- A runtime download in flight is the user's to control: `pause_runtime{id,version,paused}` holds the transfer where it is (the socket is not drained, the partial file is kept, and resuming continues the same transfer) and `cancel_runtime{id,version}` stops it — the partial download is deleted, nothing is extracted or installed, and the outcome is a `Cancelled` event, not a failure. Verification and extraction are not pausable, so a stop lands at the next stage boundary and the runtime is never renamed into place after one. Addressing an install that is not running is refused by name.
- Web ownership Managed/Advanced/Manual; drift preserved + flagged; invalid keeps old.
- Safe move to `ols_excluded_sites` on deletion. Deleting a site or project moves its directory into an `ols_excluded_sites/` folder in the same directory (with automated collision resolution: `-1`, `-2`, etc.) rather than permanently deleting it. Certificates are revoked and the domain and project entries are removed from the database. `ols_excluded_sites` is always ignored during scans and syncs, and cannot be renamed or removed in Settings.
- Hide/Exclude preserves files on disk. The existing deletion method that removes records from the list and skips them in scans without touching files on disk is labelled **Hide/Exclude** (in Sites row actions, bulk actions, and Settings). Removing a site or a project records it in an exclusion history (settings `projects.removed` for folders, `domains.auto_skip` for automatic sites), each entry carrying the time it was recorded. Settings → **Hide/Exclude** groups legacy automatic-domain entries with hidden folders using the existing folder-name slug and `domains.default_tld` hostname rule; unmatched sites remain standalone. A project row confirms once before clearing its folder and grouped domain values through the existing `forget_deleted_item` command, while a site chip confirms before clearing only its hostname; successful restores invalidate the persistent Sites page `web_domains` and `web_projects` caches. **Clear all** still clears the complete stored history behind its existing confirmation. Clearing never touches files and never re-adds anything by itself — the next folder scan or automatic-domain sync picks it up, which is why the row button says "can be scanned again" rather than "restore".
- Configurable ignored folders. Users can configure extra folder names the app should ignore; `projects.ignored_folders` defaults to `["ols_excluded_sites"]` and always includes that required name, including when older/custom settings are read. The required folder is not editable or deletable, and backend commands reject attempts to remove or rename it. The project scanner (`scan_for_projects_with_ignored`) and auto domain sync skip these folders so their contents are never read or registered. In Settings → Ignored folders, users can add, remove, rename, or reset other folders; renaming an ignored folder updates the setting and renames matching folders across all configured project roots on disk.
- A destructive confirmation names its subject. The site or project name is the dialog title and the destructive button repeats the action ("Delete site", "Hide/Exclude") instead of a generic "Yes, continue", so the dialog never asks about something the user cannot see.
- Signing in to WordPress never needs, shows or changes a password. A project whose folder holds a WordPress install (`wp-config.php`, `wp-admin/index.php`, or `wp-includes`+`wp-content` — checked on disk, never guessed from the name) gets a **WP Admin** action in its Sites row menu. Clicking it writes one must-use plugin into `wp-content/mu-plugins` holding a 128-bit random token and a 5-minute expiry (clamped to at most 15), removes any earlier bridge so a project never has two live links, and opens `{site}/?ols_signin=<token>`. WordPress itself turns that token into a session cookie for the administrator the user picks, then the file deletes itself; the same token is refused on a second use and after it expires. Three refusals are stated as they happen, each with a fix: web server stopped, project has no domain to open, folder is not WordPress. Nothing in this path reads `wp-config.php`, a `user_pass` hash or any database credential, and no password is stored in settings or the keyring — the temporary file *is* the capability, so cancelling the link ("Cancel pending WP sign-in") is a file delete, and any bridge left behind by a crash is swept on the next listing, along with any bridge whose expiry cannot be parsed. The link URL carries the token and is never logged. The one screen the user sees outside the app reuses the app's theme tokens (light and dark) rather than WordPress' own pages, because a sign-in screen in a foreign design language is what a phishing page looks like. The colourway follows the app, not the browser: the click passes the app's resolved theme into the page as `data-theme`, and the `prefers-color-scheme` rule is suppressed when the app says light, so an app in light mode on a dark-mode machine opens a light page instead of the other way round.
- Deleting must not feel like a click that did nothing. The row leaves the list at once (optimistically), dims and shows a spinner while the command runs, and the slow half — re-rendering every config, the server's own validator, the reload — runs behind it with an "Updating the web-server configuration…" status. A failure always re-reads the store: a refused command puts the row back, a failed apply leaves the row gone and shows the Diagnostic, because the domain *is* deleted either way.
- The web apply must not own the domain store while it works. Rendering files, running `nginx -t` and (re)starting a server can take seconds; the store mutex is held only to take a snapshot, the apply runs against that snapshot, and generated-config hashes are committed afterwards under the lock again. `list_domains` runs on the UI's 4s poll and takes the same store (after the project store), so holding it across an apply made every status refresh in the app wait — and the reverse lock order would deadlock. A change made during an apply is picked up by the next one.
- Reading a project must not own the settings or custom-install store while it works, for the same reason. `build_detail` reads the project's files and spawns version probes, so a project on a dead network mount blocks there for minutes; the stores are cloned and their guards dropped first, so one unreachable folder cannot stall every other command behind it.
- Domains any name, default `<project>.<tld>` where tld comes from `domains.default_tld` setting (default: `local`; presets local|test|localhost or custom); wildcard via local DNS+NRPT; conflict detect; reverse proxy to any host/port; static index.php still runs PHP.
- New sites/clones/imports/QuickApps default to `<install>\sites` (writable) else user Sites; `quickapps.projects_dir` override wins, blank falls back; absolute path required, parent auto-created, non-empty target refused; per-dialog folder name/location editable; Git clone supports SSH auth with dropdown auto-detecting keys from %USERPROFILE%\.ssh, dynamic refresh button, and file-picker browse fallback.
- Local CA trusted once to CurrentUser Root; wildcard certs; HTTP->HTTPS toggle; health 5-step chain.
- DB version isolation; safety backup before restore; secrets in keyring only; redaction everywhere.
- Creating a database asks who will own it, and a half-answer is refused. The bundled engines are provisioned with a passwordless superuser on loopback, so signing in as that account is a real option and the default. Choosing a password instead creates the database and the user together, makes the user its owner, and stores the password in the OS keyring — so the app connects as that user and never needs superuser rights. A user name without a password, or a password without a user name, is refused with a message naming what is missing: neither produces a database anyone can actually log into, and silently creating one would look like it worked.
- SQL backup/restore take the database name as a process argument, never as SQL text, so any real database name works: only names a Windows file cannot hold (`/ \ : * ? " < > |`, control characters, a leading dot, over 120 bytes) are refused, and that refusal names the database and says to rename it.
- Mailpit mandatory; .env diff preview; local mail never leaves machine.
- Tunnels default off, first start needs confirm_exposure, public badge, DB/mail/xdebug ports blocked.
- Imported quick-apps/plugins untrusted until approved; elevated steps separate confirm. Enabling a plugin shows `PluginConsentDialog` (`pluginConsent`), deriving an objective consent summary strictly from structured manifest contributes (`runtimes` with parsed download host/owner/repo or prefix, verified SHA-256 requirement, optional size; `detections` with marker filenames and read-only guarantee; `quick_apps`; `health_checks`) and raw permissions in a details row, ignoring author free-text to prevent deceptive summaries. Features a single "Allow and turn on" confirm action with `<SaveButton>` feedback and no redundant consent switch. Modals and dialog panels render fully opaque solid surfaces (`--dialog-surface`, `--dialog-card`) across all themes and presets, layered below the z-[100] titlebar.
- Diagnostics {problem,cause,fix}; safe auto-fix attempted once per persistent finding (`auto_fix_attempted`; ids of findings that disappear are forgotten so a recurrence is fixed again, a fix that leaves the finding in place is not retried until restart); service start/restart fixes never run in background; auto-fix runs on startup, project/runtime changes and when the setting is enabled, plus a 30-minute fallback timer (no fixed 5-minute loop); destructive asks.
- A service action reports what actually happened: `start_service` waits for the spawn to be decided and fails with the OS reason if the process never started, `stop_service` waits for exit and fails if a kill was ignored, and `restart_service` fails on either half rather than reporting a bounce that did not happen. A process that never spawned has no output buffer to read, so the reason is kept per service and `read_log{source:"service:<id>"}` returns it instead of an empty list. Every widget on a page runs its action through that page's `useAction`, so the error reaches an ErrorCard instead of state nobody renders.
- Workers/schedulers run while app/daemon open; memory caps next restart; k6 VU cap 200.
- Snapshots zip skips node_modules/vendor/.venv; import renames domains/DBs/ports/certs.
- Backups happen without being asked for, and only automatic ones are ever deleted. §130 takes project snapshots and database dumps on a schedule (`auto_backup` in settings), on the same clock the scheduler uses, so they run while the app or `ols daemon` is open and are off by default. Five rules make it safe. **The period, the keep count and the choice of what gets copied belong to the site, not to the app — unless the app covers everything.** Under the "chosen sites" scope each site sets its own frequency, its own keep count and its own three copy answers (project files, `.env` files, databases) on its own Backups page, because a busy site wants an hourly backup and a forgotten one wants a monthly one, and because one site's `.env` files are not every site's business — a site can be backed up as code and configuration while its neighbour's data is dumped too. Under the "everything" scope the app-wide set is what runs, and every per-site value is *dropped on save* rather than stored: a control that saves a value nothing reads is worse than no control, and the site page says "Managed by Settings" instead of pretending. A site with no value of its own follows the plan, and every site is reported with its own values, the values in force, and whether the plan owns them, so no screen ever shows an edit that would not be read. A site switched on with all three copy answers off is refused with the way out, because a configuration-only snapshot every period is not a backup; leaving an answer unset is not the same thing, since unset means "follow the plan". **Scope is the user's, either way round:** the whole app (every project, and every database in MariaDB and PostgreSQL, plus every registered SQLite file) or a chosen set of sites — and a site is covered through the project behind it, because a snapshot records the project, so three sites in one project are one backup. Two sites of one project that ask for different periods, keep counts or contents run at the first one's, and the disagreement is reported in that pass's problems rather than resolved in silence — a snapshot holds the whole project, so the choice cannot be split between them. A SQL server that is not running is started first (a dump needs one); one that is not installed is reported as a problem, not skipped silently. **Retention counts what it wrote and nothing else.** Every file a pass produces is recorded by bucket (one project, one SQL database, one SQLite file) in `auto_backup_state`, and only recorded paths are deleted when the count passes "keep" — a backup the user took by hand, however old, is never touched, and the same files land where the manual ones already do, so the existing lists, restore dialogs and delete buttons find them unchanged. **A pass that partly failed says so.** Per-item problems are collected into `AutoBackupRun.problems` in words that name what was skipped and how to include it, and the run still counts as a pass: one database refusing a dump must not cost the other projects their backups. A site that belongs to no project yet is named in the same place rather than quietly counted. A second pass never overlaps a running one — the clock and the "Back up now" button share one flag — and a pass takes its own thread, so a slow dump cannot delay scheduled tasks. The project page that holds the snapshots is called Backups, not Snapshots: a database dump belongs next to the snapshot that records the database it belongs to, and hiding one behind a different name is how someone backs up configuration and then loses data.

- A `localhost/<name>` route reaches the site's vhost that *serves* it, not the one that redirects. A site with TLS and "Redirect to HTTPS" on answers its plain-HTTP vhost with a single 301 to `https://<its own hostname>` and nothing else, and the prefix route names the site as `Host` on the way in — so proxying to the HTTP port answered every prefixed request with a redirect to the site domain, and the localhost route was unreachable for exactly the sites most likely to want one. Such a site is therefore proxied to over its HTTPS vhost (with SNI, so the right `server` block answers), and the route sends `X-Forwarded-Prefix` so an application that strips the prefix can still rebuild URLs that carry it. A site without TLS is unaffected and still takes its HTTP vhost.

- "Stop all" has to mean all, and mean the same thing wherever it appears. The mark is red once nothing is running, so any process that survives a Stop all keeps the tray and the taskbar green while the user is looking straight at the button they just pressed — the mark stops being information and becomes decoration. "Stop all" existed twice with two different scopes, which is the actual defect: the tray menu stopped the web stack and services and missed tunnels and workers, and the Dashboard stopped only the auto-startup set and missed Mailpit, any worker, and the web stack. A missing entry is still left missing: autostart is never turned on behind the user's back. Push, never fetch: `ols:status-icon` has no current-value query, so it is emitted on every reveal as well as every repaint, and a webview that mounts later is not left showing a mark the app already left behind. A mark is only claimed once it is known — a missing core reads as "running", not "red".

- Open a site on your phone (§178, `lan.rs`, `lan_share.rs`): `Domain.lan` (default false), `Domain.lan_ip` (computed), `Domain.lan_port` (picked when sharing is turned on, cleared when it is turned off) and `Domain.lan_http` (default false). The web configuration gets one more listener per shared site (`SiteSpec.lan: Option<LanListen{port, https}>`): nginx a `server` block with `listen 0.0.0.0:<port>[ ssl]` and no `server_name`, Apache `Listen 0.0.0.0:<port>` plus `<VirtualHost 0.0.0.0:<port>>` in the site file, Caddy `https://:<port>` / `http://:<port>`; the block never redirects to HTTPS or to the .test name, and a site without `lan` renders byte for byte as before. `https` is true when the site has a certificate and `lan_http` is off; then `certs::names_for` adds the LAN IP and `CertificateAuthority::issue_for` writes it as an IP-address SAN (`SanType::IpAddress`), so the certificate is reissued; plain HTTP adds nothing. `get_lan_info` and the minute tick follow a changed LAN address and give a port to a site shared by an earlier build (whose `lan_alias` sslip.io name is ignored on load). `set_site_lan_http{hostname,http}` switches the phone link between HTTPS and plain HTTP. OLS does not change the firewall; `get_lan_info` warns when Windows calls the active network Public. The certificate page (`start_ca_share`) listens only on the private LAN address and a random port, for 10 minutes or 50 requests, behind a random 128-bit token in the first path segment; routes: the instructions page, `ols-ca.crt` (DER), `ols-ca.mobileconfig` (unsigned iOS profile, `com.apple.security.root`). It receives the public certificate's PEM text only and never opens the CA key. QR codes come from the `qrcode` crate (MIT or Apache-2.0) and are shown as an image from a data URL, never as HTML. UI: `PhoneSection` (share switch, Use HTTPS switch, QR cards, certificate dialog only for HTTPS; both directions of the share switch ask for confirmation) lives in the site's Domains tab and in `PhoneShareDialog`, a dedicated window opened from the Sites page (row phone button, right-click item, "On your network" link). The Sites header shows a counter chip "N shared on network" that lists them. Sharing never outlives a run or the thing it needs: `lan::stop_all(inner, apply)` turns every share off when the core starts (a crash or kill leaves `lan` saved as on), on app exit (`shutdown` in src-tauri), on the daemon's exit, and on `StopWeb` / stop-everything; `lan::reconcile(inner)` turns off every share whose site is disabled or gone or whose web server is not running, from `GetWebStatus` (the UI polls it), `StopService` of a web server, `set_domain_enabled(s)` with `enabled=false`, and the minute tick. Sites: the grey phone button and the right-click item ask for confirmation, share at once and then open the sharing window (no switch to flip); the green button asks and stops sharing; the bulk bar has Share (n) and Stop sharing (n) for the selected sites (one confirmation, one result report). Not on the HTTP API (`get_lan_info` is in the API `NEVER` list), no MCP, no CLI.

- Services sleep when unused (§179, `idle.rs`): setting `services.idle` = `{service id: {enabled, minutes 5-240 (default 30), wake_on_connect (default true)}}`, empty by default; only `mariadb`, `postgres`, `redis`, `mongodb`, `memcached`. The scheduler's minute tick calls `idle::tick`, which returns at once unless a listed service is enabled and running; then it runs `netstat -ano -p TCP` once (5 s timeout), counts established connections by local port and refreshes `last_active`. If the output has no TCP line the tick is skipped (logged once). A service quiet for its minutes is stopped, marked `sleeping` in `ServiceStatus`, and announced by a short task `idle-sleep`. With wake on connect a thread `ols-wake-<id>` binds `127.0.0.1:<port>` (never `0.0.0.0`), waits for the first connection (plus 200 ms of more), frees the port, starts the service through `start_service_and_wait` and forwards the waiting clients; if the start fails the clients are closed. Manual `start_service`, `stop_service`, `restart_service` and `stop_all` first call `IdleState::release`, which stops the listener and waits until the port is free, so a service the user stopped never auto-wakes; app exit releases every listener. Known limit: the first connection waits for the start, and only `127.0.0.1` wakes a service. Not on the HTTP API (operate) or MCP.

## 7. Flows
- Register -> detect -> resolve -> plan -> apply (journal) -> domain -> cert -> render -> validate -> backup -> reload -> DNS/hosts/NRPT -> services/workers/scheduler -> health. See `diagrams/dataflow.mmd`.
- Site bundle export: pick sites (grouped by project) -> choose what goes in -> optionally seal the .env/dumps under an export password -> gather (config document, env, dumps, files) -> write `<name>.part` -> manifest last -> rename. Each site is a step; each item an `advance`. The command answered with the task id before any of it ran.
- Site bundle import: read the manifest (refusing a future format) -> derive the key if encrypted -> per site: `preview` reported which hostnames clash -> update (snapshot "Before import" first, then unpack project files, apply config/env/dumps) or rename (new project folder, files unpacked, hostname/db/port adjusted) -> per-site report with the safety snapshot named. **Both conflict modes honour `options.files`.** Update mode once unpacked nothing: settings, `.env` and the database were written while the project's own files were left at whatever the previous copy held, so a WordPress import reported a finished task and the site kept its old content. The bar's step count already included `file_count`, which is why it completed in seconds — the work it counted was never done.
- Tunnel: create (untrusted token via env) -> confirm_exposure -> start supervised proc -> inspector proxy -> public badge.
- QuickApp: schema validate -> answers -> plan (review + masked secrets) -> approve source -> run background (cancel flag) -> notify.
- Doctor: diagnose -> explain -> propose CoreCommands -> confirm destructive -> re-diagnose.
- CLI offline: call -> NotRunning -> spawn daemon detached -> 30s pipe wait -> send.

## Site reconciliation

Inner::reconcile computes whether a stored site is active from its domain record, the hidden-sites list (domains.auto_skip), and folder markers. `.ols_ignore_me` hides the project and site; `.ols_ignore_site` hides/deactivates the site while keeping its project visible. Marked site records remain stored but are omitted from Sites and excluded from vhost rendering. Reconciliation synchronizes the OLS-managed hosts block to active enabled domains and applies/reloads generated configs when a web server is running. Domain and project list reads are read-only apart from checking for writes by another process; they do not perform hosts-file elevation or web config reload on each poll. Startup synchronization, folder scans, marker changes, and mutations that affect serving state trigger or schedule reconciliation. RemoveSiteFromList removes only the selected domain and keeps or registers its project as standalone; it leaves project files untouched. SitesPage refreshes both lists immediately, then requests reconciliation asynchronously and displays an updating status. The separate move-to-excluded action moves the project folder to ols_excluded_sites and removes both records. Other .ols_ignore_me markers hide discovered paths. Removing a site marker or clearing a hidden-site entry reactivates the retained record on the next reconciliation. ListProjects marks each returned project with a transient `auto_discovered` value based on configured discovery roots for the Sites row label.
The Projects page receives transient `site_ignored_project_ids` with its list response. For those projects, the Create site from project action becomes Unignore site; the command removes `.ols_ignore_site`, reconciles the retained domain, and refreshes Projects and Sites.

Web apply feedback: `useWeb.apply` and `useWeb.reconcileSites` publish a timed success notification with per-server action and written-file details only when an apply wrote config, started or reloaded a server, or updated the hosts file; an unchanged apply stays quiet. `SyncHosts` returns the `ApplyReport` values produced during reconciliation so remove-site-only changes can show the servers that actually reloaded. Drifted config still opens the confirmation dialog.

The Sites row actions are Hide, Remove from list, and Move to excluded folder. The move action uses a neutral tooltip, amber icon/title, and a confirmation naming the project, source path, excluded destination and Undo notification. On success, an Undo notification restores the moved folder and captured site/project records for the current app session.
