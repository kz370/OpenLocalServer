# OLS — Full Documentation

## 1. Introduction
OLS is a Windows-local development environment manager. It downloads and runs PHP, Node, databases, caches, mail, and web servers, gives each project isolated runtimes plus own `.test` domain with trusted local HTTPS, without manual system edits. Pre-release, stage 15/20. Portable `data/` beside exe; `OLS_HOME` overrides paths.

Scope: runtimes (PHP/Node/Python/Composer), databases (MariaDB/Postgres/Mongo/Redis/SQLite), web (Nginx/Apache/Caddy), projects (detect/setup/env/git/workers/scheduler/snapshots), domains + TLS + DNS, tunnels, diagnostics/doctor, plugins, quick-apps/commands, AI assist, local API, CLI, updater.

Version: 1.0.0 (workspace `Cargo.toml` and `src-tauri/tauri.conf.json`; release notes in `release-notes/v1.0.0.md`, change summary in `CHANGELOG.md`). `ui/package.json` stays at 0.0.0 — it is a private workspace root and never shipped.

## 2. Architecture
One core, many front doors. `ols-core` holds all logic behind `Core::dispatch(CoreCommand)`. Tauri shell exposes single IPC `run_command`; CLI talks over named-pipe control channel (auto-spawns daemon); HTTP API posts same JSON to `127.0.0.1:7420/v1/command`.

See `architecture_overview.md` and diagrams:
- `diagrams/architecture.mmd` — system context
- `diagrams/dataflow.mmd` — setup-to-healthy flow
- `diagrams/classes.mmd` — core classes
- `diagrams/sequence.mmd` — domain + apply sequence

State: `Arc<Inner>` shared across threads; lock order domains-first. ProcessSupervisor owns Tokio runtime + all children. Managers communicate via broadcast events (`process-event`, `terminal-event`, `runtime-event`). Core state locks are taken through `app::lock`, which recovers a poisoned guard instead of unwrapping it: a `std::sync::Mutex` stays poisoned for the process after any panic while held, so the old `.lock().unwrap()` turned one failure into every later read panicking too — and a page waiting on such a read waits for the rest of the session. No store lock is held across blocking work; `project_detail` clones the settings and custom-install stores and drops the guards before `build_detail` does its file I/O and version probes.

Privilege model: main app never elevated. `ols-helper` closed set (hosts-apply/remove, nrpt-add/remove, install-service) via UAC or LocalSystem pipe service with SDDL lock.

Helper pipe calls are bounded: a request waits at most 10s for the service's reply, then falls back to running the change un-elevated/elevated. A wedged or killed `ols-helper` must never block the caller indefinitely — `apply_web` waits on the helper, and an unbounded wait there froze the web state lock and with it every command in the app.

## 3. Modules
### 3.1 System core
Dispatch, state, IPC, infra. `lib.rs` re-exports; `app.rs` Inner + all command impls; `command.rs` ~150-variant dispatcher; `control.rs` named-pipe RPC with token; `api.rs` localhost HTTP with bearer + allowlists; `paths.rs` resolution; `settings.rs` atomic JSON; `secrets.rs` keyring; `process.rs` supervisor; `port.rs` conflict reporter; `exec.rs` capture helper; `error.rs` Diagnostic shape; `logging.rs` + `redact.rs`; `diagnostics.rs` findings engine; `repair.rs` doctor; `search.rs` global search; `support.rs` bundle; `network.rs` probe; `journal.rs` op log; `resources.rs` caps; `elevate.rs` helper runner (pipe reply bounded to 10s).

### 3.2 Runtime
`catalog.rs` pinned HTTPS+SHA256 manifests; `catalogs.rs` minisign-signed remotes; `runtime.rs` download-verify-extract + probe; `php.rs` per-version php-cgi pools + extensions; `nodepm.rs` lockfile/corepack; `composer.rs` reader; `venv.rs` finder; `custom_install.rs` pinned paths win; `resolver.rs` manifest>detected>global; `detection.rs` marker scan; `plugin.rs` declarative plugins (wasm refused); `updater.rs` signed self-update.

### 3.3 Services
`service.rs` DB/cache/mail lifecycle + TCP probe; `custom_service.rs` user procs (custom- prefix, no shell); `dbtools.rs` external GUI detect; `mail.rs` per-framework Mailpit planner with diff; `monitor.rs` sysinfo rollup + site cost; `workers.rs` up to 16 copies; `scheduler.rs` 1-min cron tick, no overlap. Start/stop are verified, not fire-and-forget: `start` waits for the spawn to be decided (`ProcessSupervisor::wait_for_spawn`) and returns the OS error if the process never existed, keeping the reason in `start_failures` so it survives the dead process record; `stop` waits for exit and says so when a kill was ignored. Every service start goes through `ServiceManager::start_capped`, which is where the Resources CPU cap (§129, `resources.rs`) is applied; web servers are capped the same way in `web/manager.rs`. Auto-start reads one list (`startup.autostart_services`) for every service, web servers included, and applies a web server's config before starting it rather than only spawning the process.

### 3.4 Web
`web/mod.rs` trait + SiteSpec; `web/manager.rs` render-validate-backup-apply-reload-health + rollback + drift; `web/nginx.rs`, `web/apache.rs` (foreground httpd, no service), `web/caddy.rs` (auto-HTTPS off, local CA); `domain.rs` validation; `ca.rs` deterministic root 2024-2044 via rcgen; `certs.rs` per-domain reuse unless SAN/<30d; `hosts.rs` idempotent block; `dns.rs` UDP wildcard; `health.rs` 5-step chain; `tunnel.rs` provider abstraction + confirm gate + port blocklist; `inspector.rs` forwarding proxy, 500 req, redacted. Each renderer also emits the per-server `localhost/<prefix>` routes file, one block holding a proxy location per routed site.

### 3.5 Data
`dbbackup.rs` mysqldump/pg_dump with safety copy; `sqlite.rs` WAL-safe .backup + integrity_check; `migrate.rs` Laragon/XAMPP/Wamp live-dump importer.

### 3.6 Project
`project.rs` registry ID=sha256[..16]; `project_tools.rs` wrappers; `manifest.rs` strict YAML; `profiles.rs` templates; `setup.rs` 14-step pipeline + lock file; `snapshots.rs` zip + clone; `envfile.rs` lossless editor; `command_catalog.rs` Symfony/artisan/npm discovery; `git.rs` real binary + ASK_PASS + ~/.ssh key detection (list_ssh_keys); `shortcuts.rs`; `editors.rs`; `terminal.rs` pty max 8; `shell_menu.rs` HKCU, CLI-only (ols-cli.exe, never the running image); `procfile.rs`; `loadtest.rs` k6 VU cap 200; `xdebug.rs` trigger-default; `quickapp/*` schema->plan->run.

### 3.7 CLI / Helper / Shell / UI
CLI `ols` never manages directly; daemon mode runs core headless + scheduler clock. Helper validates ip=127.0.0.1/::1 and suffix leading-dot. Tauri shell builds tray from domains/services, single-instance, close-to-tray. Status icon: the official mark is the green 3D server-stack tile (`src-tauri/icons/*`, generated from `src-tauri/icons/source/icon-green.png`); the red twin (`src-tauri/icons/red/`) is painted on the tray icon, the main window (taskbar) and the in-app sidebar mark whenever no service and no supervised process is running, and forced while the app is shutting down. The decision lives in `status_mark` (lock-only checks, no port probes) and is applied by `sync_status_icon` after every IPC command, from the tray menu, on every process event, after autostart, and on a 2s clock so `ols stop` over the control channel, the scheduler and crashes are covered too. `status_mark` asks `ServiceManager::any_running` and then `ProcessSupervisor::is_alive` per snapshot record — the same rule `any_running` and `prune_finished` use, because a hand-written `Running | Starting` filter disagreed with `is_alive` on `Restarting` and so could call a process both alive and dead in the same tick. `Mutex<Option<bool>>` makes it repaint only on a real change, but the state is cached *after* the repaint is confirmed rather than before: a mark that raced the tray's own creation (the process-event subscriber is registered before `build_tray`) is retried by the next 2s tick instead of being frozen for the session, and every `set_icon` error is logged rather than dropped. It is emitted to the UI as `ols:status-icon` (ui `useServerStopped`) on every repaint *and* on every `show_main_window` reveal, because that channel is push-only and a webview mounting after the last state change would otherwise never learn the mark. `ui/public/favicon-stopped.svg` is the in-app red twin of `favicon.svg`. UI `core.ts` sole IPC wrapper; no router, page state + `ols:navigate` events; `Sidebar` provides persistent navigation with static non-collapsible category groups; `useWeb` shared poll 4s; pages per concern (see catalog.txt).

## 4. File Analysis
### Rust core essentials
- `lib.rs`: Purpose: crate root + re-exports. Key exports Core/CoreCommand/CoreResponse. Depends on command/paths/process/project/runtime/service/settings.
- `app.rs`: Purpose: shared Inner state + command impls. Holds supervisor/runtimes/services/certs/php/web/terminals/journal/workers/tunnels/api/ai. Lock order domains-first; every core lock goes through `lock()` (poisoned guards recovered) and is released before any blocking I/O.
- `command.rs`: Purpose: single dispatcher. ~150 variants covering processes/runtimes/projects/services/web/DB/quickapps/AI/tunnels. Input CoreCommand JSON, output CoreResponse or Diagnostic.
- `control.rs`: Purpose: named-pipe RPC. control.json {pipe,token,pid}. Token-gated JSON lines. Handles shutdown handover.
- `api.rs`: Purpose: localhost HTTP. Port 7420, bearer SHA256, Origin reject, read_only vs operate lists, 1MB cap.
- `paths.rs`: Purpose: OLS_HOME > debug repo/data > exe data > OS app-data. migrate_legacy once.
- `process.rs`: Purpose: supervise all children. Tree-kill taskkill /T /F, 500-line ring, restart policy, broadcast.
- `runtime.rs`: Purpose: verified installs only. Zip root-strip, PATH probe 60s cache, temp version probe, broadcast Installed/Failed. One `InstallControl` per in-flight `id@version` carries the pause/cancel flags the Runtimes page drives; `install_one` returns `InstallOutcome::{Done,Failed,Cancelled}` so a user stop is never reported as an error, and the control is dropped with the install so a late pause cannot address a finished one. `refresh_online_catalog{id}` reads each vendor's public release feed (nodejs.org, downloads.php.net, nginx.org, apachelounge, getcomposer, downloads.mongodb.org, enterprisedb, api.github.com for redis-windows/memcached-windows/axllent-mailpit, downloads.mariadb.org) and keeps the result in memory only; ids with no feed (`git`, `k6`, `caddy`, `sqlite`, `python`) are refused by name. The Runtimes page gates on the same id set in `ui/src/pages/Runtimes.tsx` (`ONLINE_CATALOGS`) and re-verifies on dialog open, since its localStorage cache outlives the daemon's in-memory list. Mailpit builds its archive URL from the `v<version>` tag and carries no SHA-256 (the publisher ships none), so the download digest is recorded rather than compared, like nginx. PostgreSQL's EDB feed is the one HTML page among them: it is parsed per `Binaries from installer` block, taking the version that follows the `Version` label (React puts a `<span>` and a `<!-- -->` comment between them, so the two are never adjacent) and the href of the `alt="Windows x86-64"` anchor in that block, never the first `getfile.jsp`, which is often Mac OS X. Absolute `sbp.enterprisedb.com` hrefs are used as given, and a version with no Windows anchor is not offered. The href is a redirect, so `resolve_online_manifest` resolves the final `get.enterprisedb.com` URL over a ranged GET; the page carries no checksum, so the download digest is recorded, and the built-in 17.6 pin keeps its self-pinned hash. A transfer that ends early is rejected rather than cached: the byte count is compared against the advertised Content-Length and a short file is deleted, because for a vendor that publishes no checksum (postgres, nginx, apache, mailpit, redis, memcached) the cache-hit test trusts *any* existing file — a truncated archive would be reused forever and surface much later as `invalid Zip archive: Could not find EOCD`, naming neither the cause nor the fix. For the same reason a cached zip is only reused when its end-of-central-directory record is present (`zip_has_eocd`); a non-archive runtime such as composer.phar has no EOCD and is trusted as-is. MariaDB's rest-api is keyed by **branch**, not by full version — `mariadb_branch` cuts `13.1.1` to `13.1`, because `/rest-api/mariadb/13.1.1/` answers 200 with a `release_data` document that has no `releases` map, which made every 13.x install fail as unavailable; the branch's published SHA-256 is still required before the archive is accepted.
- `php.rs`: Purpose: FastCGI pools. One pool/version, auto curl/mbstring/pdo/openssl/opcache, zend for opcache/xdebug.
- `service.rs`: Purpose: DB/mail lifecycle. Reuses runtime + supervisor, TCP probe, no dep-ordered start yet. `is_running`/`any_running` first prune entries whose supervisor process is gone, so a service that exits or crashes on its own never stays "running" (§122).
- `web/manager.rs`: Purpose: safe apply pipeline. Archive replaced, rollback on validator fail, drift flag, manages pools/hosts/DNS.
- `domain.rs`: Purpose: domain data + sanitize. Proxy host/port checks, upstream_url, ownership gates.
- `ca.rs`/`certs.rs`: Purpose: local PKI. Deterministic CA rebuildable, 397-day leaves, reuse unless SAN/expiry, revoke=delete dir.
- `setup.rs`: Purpose: reproducible env. Order runtimes->pm->DB->domain->DNS->SSL->mail->workers->scheduler->tunnel. Journal-wrapped, rollback safe reverses, writes lock.
- `quickapp/schema.rs`/`plan.rs`/`run.rs`: Purpose: recipe safety. Strict types + regex + show_if; Minijinja strict; masked secrets in review; 4000-line log, 30-min step timeout.
- Remaining files follow same pattern: pure purpose, explicit errors, no silent fallback. Full per-file table in analysis agents; one-line index in `catalog.txt`.

### Tauri / CLI / Helper
- `src-tauri/src/lib.rs`: Tauri shell, tray, shutdown 30s wait, auto-fix loop 300s, quick-app finish poll 2s, and `reveal_window_on_ui_ready` — the main window is configured `visible: false` (the app window is transparent, so a window shown before the webview paints is an empty see-through frame); the UI emits `ols:ui-ready` after two animation frames and the window is shown then, with a 5s fallback timer and a `MAIN_WINDOW_REVEALED` guard so the app is never left running with no window. A launch that starts hidden skips both paths, leaves the window in the tray, and notifies after 2s that it is running there — the tray icon can sit in the Windows overflow area, and a launch with no window and no word reads as a failed start. `status_mark` / `apply_status_icon` / `sync_status_icon` own the mark (see §3.7); `show_main_window` is the resync point for it, since a window opened from the tray has no `ols:ui-ready` to resync against, and a `stop` that fails is now surfaced instead of being dropped — a service that stayed up is exactly why the mark would stay green. `set_theme_icon` handles the other half of the pair: the UI emits `ols:theme` with the resolved theme (the native side cannot read `localStorage`) and the tray, taskbar and window repaint in the matching colourway, seeded from `Window::theme()` at setup.
- `crates/ols-core/src/app.rs` `should_start_hidden` + `migrate_startup_entry`: The `startup.minimized` preference alone decides startup visibility, on every launch, so the toggle in Settings does what it says when the user opens the app themselves and not only at login. `--minimized` is retained as a force flag for scripts and hand-made shortcuts. The startup entry no longer carries the flag — an old entry that still did would hide the window against the user's later choice, so it is rewritten once at startup.
- `src-tauri/src/main.rs`: windows_subsystem hide console in release.
- `ols-cli/src/main.rs`: clap CLI, Ctx::call over pipe, daemon spawn detached on NotRunning, table/diag printers.
- `ols-helper/src/main.rs`: validated hosts/NRPT only; exit 5 on AccessDenied triggers UAC retry.
- `ols-helper/src/service.rs`: LocalSystem pipe, SDDL SY+BA full / IU RW, 64K line JSON.

### Frontend
- `core.ts`: only IPC caller. `runCommand` is the bare `invoke`; `runCommandWithin(command, ms)` is the same call with a deadline that rejects with a Diagnostic naming the command, for the reads that gate a page. `App.tsx`: page state router. `main.tsx`: ThemeProvider mount, then emits `ols:ui-ready` after two `requestAnimationFrame`s so the native window is only shown once React has presented its first frame, then registers a `window.unhandledrejection` logger. `index.html`: a blocking inline script applies the stored theme (or the system one) to `<html class="dark">` before the first paint — the ThemeProvider effect runs after the first frame, so without it a dark-theme start flashes white on the way to dark.
- A rejected `runCommand` is not self-healing and must never be left unhandled: `runCommand` rethrows, and a page whose content is gated on that promise (its loading state *is* "no data yet") otherwise waits forever with no stated reason. Two rules follow, and both are load-bearing:
  - every read that gates rendered content goes through `runCommandWithin` with a deadline, and catches into a `Diagnostic` the page renders in an `ErrorCard` (SiteDialog's `get_domain`/`get_project_detail` use 20s);
  - every other call site either routes through `useAction`'s `run` (which owns the error state) or ends in an explicit `.catch`. Best-effort reads that leave the UI merely less decorated (the runtime catalog, unmanaged PHP versions, the domain autofill) catch and drop on purpose — but on purpose, not by omission.
  The `unhandledrejection` listener in `main.tsx` is the last net: it logs, it does not recover.
- A window that has not painted is never shown, and a window that has not painted is never *transparent* either: the native window is transparent, so revealing it before the first frame is what produces a blank/see-through window on launch. The UI signals `ols:ui-ready` after two animation frames and the shell reveals the window then, with a timed fallback so a UI failure cannot leave the app with no window at all. That fallback is the gap the boot background closes: `index.html`'s pre-paint script adds `booting` to `<html>` and `index.css` paints that with `--background` until `main.tsx` drops the class on the first presented frame, so whichever path reveals the window — event or timer — it shows the app's own background, never an empty frame.
- Pages: Dashboard (3s poll get_dashboard; a failed poll shows its Diagnostic in an ErrorCard rather than leaving the Web server / Services cards on "Loading…" forever; Services widget row = a 5-track grid (logo 1.25rem, name 1fr, port 5.5rem, state, controls) over all 9 built-ins in fixed order; the card lives in the right half of a 2-column grid under the Web server card and stretches to the same height as Overview; below lg that wrapper is `display: contents` and the three cards carry order 1/2/3 — Web server, Overview, Services — so a windowed app leads with server state instead of the load graphs; the row is fluid at every width and the controls are the one thing that never gives way: below `lg` (single column, full width) and from `xl` up (the two-column grid is wide enough again) it is one line ending in the controls, and between `lg` and `xl` — where one line cannot hold the logo, name, port, state and five controls, and the name, being the only flexible field, was truncated to nothing — it becomes two lines with the controls on their own line under the name (`lg:col-start-2 lg:row-start-2 lg:col-span-3`, back to `col-start-5 row-start-1` at `xl`); the card and both grid children carry `min-w-0` so nothing in the chain can push the controls out of a fixed-height card, and the state keeps its dot, word and tooltip at every width; its row controls are colour-coded per action (start emerald, stop destructive, restart amber, reload sky, logs violet) at reduced opacity, and an action unavailable right now renders flat grey with no hover response), Sites (merge domains+orphans, group/search; ports tab rows are a fixed 4-column grid [minmax(0,1fr) 5.5rem 5.5rem 7rem] with 6-character-wide port inputs and an h-9 note cell, and a status badge in a row-layout CardHeader is shrink-0 + whitespace-nowrap so it cannot wrap and stretch the header), Config (ownership + DiffView), Tunnels (exposure confirm + Inspector), Databases (per-engine tools + backup-before-restore; the SQL database list is a dense one-line-per-database block — name plus Back up at h-7, then two icon-only buttons: an Info button that toggles a "Connection details" panel under its own row (host, port, user, database, file, the URI and a Copy URI button, fetched when it opens) and the Open button, which shows only the external-link icon and names the chosen tool in its title/aria-label ("Open <db> with HeidiSQL") rather than in a label that had to be truncated; the per-engine tool Select is labelled "Open with" and sits once in the card header, because a Select per row overflowed the table cell in windowed mode; the user/password/database form is a container query on the Users card itself (`@container` + `@lg:grid-cols-3`), not a viewport breakpoint — the card is only half the page grid at lg, so a viewport `lg` fired at ~480px of card and squeezed three inputs into ~145px each; below that the form is three labelled rows), Services (3s poll), Runtimes (runtime-event + version compare), Profiles/Plugins/Logs (1.5s poll + severity regex)/Processes (2s stats)/Settings.
- TechIcon resolves IDs to brand marks where available and generic glyphs otherwise; Memcached uses the symbol-only form of its supplied logo, while Redis keeps its own brand mark. An id with no brand and no drawn mark falls through to the generic file glyph, which is why the GUI tools each got one: `pgadmin` is drawn as a stroked elephant head inside a desktop window — a Postgres *client*, told apart from the `postgres` runtime's wordmark by the window frame — while `heidisql`, the other tool, is a plain disc filled with the brand's green-to-white gradient and no glyph inside it, so the two never read as one mark; `tinyrdm` is a drawn Redis-client window and `mailpit` a filled envelope, for the same reason. `nosqlbooster` and `dbbrowser` have no mark yet and still fall through.

- Components: SiteDialog (big tabbed editor; the two reads that gate it — `get_domain` and `get_project_detail` — are deadline-bounded and surface their Diagnostic instead of holding "Reading the site/project…" forever, and the project id comes from the `get_domain` answer rather than racing the caller's guess), ProjectImports (Git clone modal with auto-detected ~/.ssh keys dropdown, refresh button, fallback browse, and import env), Terminal (xterm bridge), EnvEditor (lossless), CodeEditor (CodeMirror + diff), Diagnostics/Doctor, Release/SettingsExtras, CustomServices, PHP/Xdebug dialogs, Migrate, SystemMonitor, ui primitives (no IPC), including NumberInput: every number field in the app (web ports, PHP workers, DNS port, Xdebug IDE port, API port, custom-service port, resource limits) is a text input with inputMode="numeric" and the app's own up/down stepper — the native `type="number"` arrows are a browser widget that ignores the app's radius, border and dark palette and only paints on hover in Chromium. The selection is derived from the rows on screen, so it cannot outlive the rows it was made on. A batch that needs a site runs `sync_auto_domains` first and re-points the selection at the hostnames that appeared, which is what lets a no-domain row take part in the batch at all.

## 5. Business Rules
- A user-visible file name is safe to rename; an addressing key is not. The app ships as `OLS.exe`, the setup as `OLS-<version>-setup.exe`, the zip and the SHA256SUMS file to match, and the Inno `AppName` is `OLS` — while `AppId` (`dev.openlocalserver.app`), `DefaultDirName` (`C:\OpenLocalServer`), `C:\Program Files\OpenLocalServer\`, the `openlocalserver.exe` daemon, the `OpenLocalServerHelper` service and pipe, the hosts markers, the NRPT comment, the keyring service, `.openlocalserver/` and `openlocalserver.test` all stay exactly as they are. The distinction is what the name *is used for*: a file name is looked up on disk and nothing reads it back as an identifier, whereas a registry value, service name, pipe name or domain is an addressing key, and renaming one orphans live state with no recovery path (`docs/BRAND.md` §4.3). The one rename that would have been unsafe without code is the file lock on upgrade, which is why the old exe name is carried through every "is it running?" check and the old file is pruned at install time. The app resolves its own path with `std::env::current_exe()` rather than a literal, so no Rust code changed for the rename.
- An update that reports success has to have replaced the binary. Windows locks a running image, so an installer started while the app is alive cannot overwrite `OLS.exe`: the old version survives and the user is told it updated. The rule is enforced on both paths, because either one alone leaves the other broken. `updater::install_update` spawns the verified installer and then exits the process on a short timer, so the file lock is gone before the installer reaches `[Files]`. Run by hand, the installer closes it itself, and the `[Code]` section is the half that matters: it asks once, with an explanation, then stops the images that actually hold a file in the destination folder, matched by PATH rather than by name. `CloseApplications` / `RestartApplications` are the Restart Manager backstop for anything that missed, and `CloseApplicationsFilter=*.exe|*.dll` covers `ols-helper.exe` and `cpulimit.exe`, which ship beside the app and are not in the app's single-instance mutex. **The rename makes the name check load-bearing in a second way**: `AppExe` is `OLS.exe` and the pre-rename `LegacyAppExe` is checked beside it everywhere — `RegisteredDir`, `AnyAppRunningHere`, `InitializeSetup`, `PrepareToInstall` — because an install made before the rename is still running under the old name and holds the exact file `[Files]` writes. `PruneUnshippedFiles` omits `LegacyAppExe` from the shipped list, so the old exe is deleted at `ssPostInstall`, after `PrepareToInstall` has confirmed the image is closed. `scripts/build-installer.bat :app_running` applies the same three-name rule (shipped, legacy, cargo bin `openlocalserver.exe` for a dev build) before it stages anything. A second launch after the install is harmless because the app is single-instance. Related and separately fatal: `build-installer.bat inno` recompiles nothing, so an installer that is older than the source is a stale `target\release`, which is why that mode now prints each staged file's timestamp before shipping it.
- A rename that a fresh install honours is not necessarily a rename an upgrade honours. The Inno `DefaultGroupName` is `OLS`, but a machine that already has the pre-rename build keeps a Start Menu folder named `Open Local Server` after upgrading, and the new shortcut is written *inside* it, because an upgrade takes the group name from the previous install's uninstaller rather than from `[Setup]` — the old uninstaller has to be told which folder to clear, so that folder's name is data, not configuration. No setting in `[Setup]` can change it. `MigrateLegacyStartMenuGroup` closes it at `ssPostInstall`: `.lnk` entries move into the current group folder, a name that already exists there is deleted rather than overwritten (that copy is the one `[Icons]` just wrote), and the legacy folder is removed only when it ends up empty and never recursively, so anything the user filed in there survives. Every failure is logged rather than raised — an install that installed correctly must not be reported as failed over a Start Menu folder.
- A CPU limit is a real cap, or it is refused. §129 caps a service through the `cpulimit` utility (`cpulimit <percent> <program> <args>`, a Windows job object with a hard CPU rate), so a wanted cap whose utility is not installed fails the start with the way to install it — a service that quietly runs uncapped under a UI that says "limited" is the failure this rule exists to prevent. The utility is **vendored, not downloaded**: `vendor/cpulimit/cpulimit.exe` (kz370/win-utils, MIT) with a pinned SHA-256 in `vendor/cpulimit/README.md` and `CPULIMIT_SHA` in the build script, checked on the source and again on the staged copy, so a tampered or corrupted copy cannot reach an artifact. The installer places it next to `OLS.exe` and `find_cpu_limiter` looks **there first** — before any path saved in settings — which matters because the settings database is shared between a dev build and an installed one: a path saved while running from `target\` would otherwise leave an *installed* app pointing at that dev machine's folder forever. A configured path is the fallback for when the app has no sibling copy, which is the only case the Resources card offers that field. A configured path that is not a file is skipped rather than ending the search, so a stale setting cannot disable the cap in an otherwise correct install. A dev build from `target\` has no installed sibling, so it falls back to the repo's own `vendor/cpulimit/cpulimit.exe` (reached through a compile-time `CARGO_MANIFEST_DIR`, which does not exist on a user's machine) rather than to a stray `%LOCALAPPDATA%` install that has nothing to do with the checkout — so the card reports the binary this build actually shipped, in the dev build as well as after installing. The percentage is a share of *every* core, not of one, and the UI says so and offers threads instead, converted against `available_parallelism` and rounded up so "1 thread" is never under the core asked for. `cpu_percent` and `cpu_threads` are mutually exclusive: two ways to state the same limit is a setting the user has to reconcile, not one the app guesses at. The cap lives as long as the service, since `cpulimit` stays in the process tree and exits with the program's own code, so stop/restart/crash recovery are unchanged.

Any read whose result gates rendered content is deadline-bounded (`runCommandWithin`) and its failure is stated as a Diagnostic with a Retry, because the alternative is a page that says "Reading the project…" forever and blames the user. `get_project_detail` for a project that is no longer registered is a stated failure ("This site has no project any more", with the re-register fix), not a silently dropped id.

- A site can answer on its own domain and on `localhost/<name>`, and the second is the same site, not a copy. - A `localhost/<name>` route reaches the site's vhost that *serves* it, not the one that redirects. A site with TLS and "Redirect to HTTPS" on answers its plain-HTTP vhost with a single 301 to `https://<its own hostname>` and nothing else, and the prefix route names the site as `Host` on the way in — so proxying to the HTTP port answered every prefixed request with a redirect to the site domain, and the localhost route was unreachable for exactly the sites most likely to want one. Such a site is therefore proxied to over its HTTPS vhost (with SNI, so the right `server` block answers), and the route sends `X-Forwarded-Prefix` so an application that strips the prefix can still rebuild URLs that carry it. A site without TLS is unaffected and still takes its HTTP vhost.

- "Stop all" has to mean all, and mean the same thing wherever it appears. The mark is red once nothing is running, so any process that survives a Stop all keeps the tray and the taskbar green while the user is looking straight at the button they just pressed — the mark stops being information and becomes decoration. "Stop all" existed twice with two different scopes, which is the actual defect: the tray menu stopped the web stack and services and missed tunnels and workers, and the Dashboard stopped only the auto-startup set and missed Mailpit, any worker, and the web stack. Two commands named the same thing, neither meaning it. There is now one command, `StopAll`, covering tunnels, supervised workers, the web stack (servers and PHP pools) and every running service, then sweeping the supervisor and naming anything the OS would not kill. That last part is the honest boundary: a process the OS refuses to kill is reported rather than swallowed, because that is the one case where staying green is the correct answer. It is a core command rather than app-side logic so the tray, the Dashboard and the HTTP API cannot drift apart again. The tray dispatches it off the menu thread, since a stop waits up to 10s per service and the sweep waits again.
- Nothing outside the app folder may hold a hardcoded path to the app, because a user is entitled to move their own installation. The startup entry is the one the app writes itself, and it holds an absolute exe path — so it is rewritten at launch when that path no longer exists, pointing at the copy actually running. Renaming or moving the install folder used to leave a valid-looking `HKCU\...\Run` command pointing at nothing, and the app then simply never started by itself, saying nothing. A missing entry is still left missing: autostart is never turned on behind the user's back. The elevated helper is the one component that must *not* follow the app folder, and deliberately does not: a LocalSystem service executing a binary out of a folder the signed-in user can write is a privilege escalation, so the helper is copied into an admin-only folder and the service runs that copy. One definition of "alive": the mark uses `ServiceManager::any_running` and `ProcessSupervisor::is_alive` rather than a second, hand-written state filter, so no process can be counted alive by one check and dead by another in the same tick. A folder with nothing to serve in it is *named* in the result ("app2 has no index.html or project file to serve"), never dropped without a word.
- A site that does not resolve is not a working site. Creating an automatic domain writes the hosts entry as part of the same step, skipping names the built-in DNS already answers for and skipping the whole write when every name is already listed — so dropping a folder into a projects folder costs a file read in the common case and at most one elevation prompt across the entire install. This is why "the site is in the list but the URL does not open" was possible before: the site existed, the vhost was rendered, and nothing had asked for the name to resolve.
- A change written by another process is a change, not a restart. The app caches its stores in memory, but the Explorer right-click menu and the `ols` command line write the same database from a *separate process* — so a site added that way was invisible until the app was restarted, which made the menu look broken. Every commit records the writing process id (`db.last_writer`); listing sites or projects reads that one row and, when it names a different process, re-reads the stores and re-runs the automatic-domain sync, so the outside project arrives *with* its site rather than as a project row with no domain. The writer is a process id and not a file timestamp, because under WAL a commit lands in `app.db-wal` and a later checkpoint moves `app.db` again — comparing file times reported the app's own saves as outside changes and would have re-read the stores on every write.
