Functions / Classes / Modules / Components catalog (one-line each).

--- RUST ols-core ---
Core | Central dispatcher facade over Inner.
CoreCommand | Enum (~150 variants) covering all UI/CLI/API operations.
CoreResponse | Tagged response enum for every command.
CoreError/Diagnostic | User-facing error shape {problem,cause,fix}.
Inner | Arc-shared state holding all managers. State locks are taken through `app::lock`, which recovers a poisoned guard instead of unwrapping it — a `std::sync::Mutex` stays poisoned for the process after any panic while held, so unwrapping turned one failure into every later read panicking too. `project_detail` clones SettingsService/CustomInstallStore (both `Clone`) and drops the guards before `build_detail` does file I/O and version probes, so an unreachable project folder cannot stall other commands. Owns the deletion history (`list_deleted_items` / `forget_deleted_item` / `clear_deleted_items`) over the two skip lists `projects.removed` and `domains.auto_skip`: each entry is `{value, deleted_at}` on disk (older bare-string entries are read as entries with no date), merged newest-first for `list_deleted_items`. `skip_matches` normalizes the Windows `\\?\` prefix on both sides and compares a candidate against the stored value *and* its canonicalized form, so the watcher sync and the manual Scan judge a folder the same way and a path spelled through a short name, junction, mapped drive or `..` segment cannot slip past a skip. The same resolution runs the other way round, in `same_skip_entry`, for everything that reads or edits a list rather than testing one: `forget_deleted_item`/`clear_project_skip` (`remove_skip`), `push_skip` and the dedup in `edit_skip_entries`. Without it a stored entry stayed put when the caller handed back another spelling of the same folder — on a GitHub runner, where `%TEMP%` is `C:\Users\RUNNER~1\...` and `canonicalize` returns the long name, so Settings' "clear this entry" reported success, the history still listed the folder, and the next scan skipped it anyway. Resolution is gated on `is_path_like`, so a bare automatic-domain name (`app1.local`) is compared as a string and never resolved against the working directory, where a folder of that name would otherwise match it. `comparable_path` adds the fallback the clear specifically needs: when the leaf is gone from disk — the user removed the project, then the folder, then cleared it — a whole-path canonicalize fails on both sides and the two spellings would be compared raw again, so the parent is canonicalized and the file name reattached, which still collapses a short name at every level.
AppPaths | OLS_HOME-aware path resolver (certs/data/settings). Also owns the portable path form: `encode_root` writes a path inside the app (`sites/<name>`, `data/<name>`, forward slashes) instead of the absolute path it resolved to, and `decode_root` expands it again on load, so a renamed or relocated install keeps the folders and tools that belong to it. A path still stored absolute and no longer existing is re-anchored from its trailing `sites`/`data`/`home` segment when that folder exists under the current install, and left alone otherwise so a genuinely deleted site keeps reporting as missing. `join_relative` appends the stored form one segment at a time, because joining a forward-slash string onto a Windows base would leave a path spelled with two different separators. `CustomInstall.path` and the `quickapps.projects_dir` setting use this; `Domain.root` and `Project.path` are its other two users.
SettingsService | SQLite key-value store (app.db settings table). Cloneable so a read can release the store lock before doing slow work.
Db | Central SQLite store (app.db, WAL): settings table + generic docs collections for all Vec-stores.
Secrets | OS keyring wrapper (set/get/delete).
ProcessSupervisor | Owns child processes, tree-kill, output ring, restart policy. wait_for_spawn/wait_for_exit let a caller block until a spawn is decided or a process is gone; a spawn error is kept on the record and pushed into the output ring, so a process that never started still has a readable reason.
ProcessSpec/ProcessInfo/ProcessEvent | Process spawn descriptor, status, broadcast event.
PortChecker | Bind-probe + netstat/tasklist conflict reporter.
ExecCapture | Sync run-and-capture with timeout + CREATE_NO_WINDOW.
Logger | JSON daily rolling log with redaction.
Redactor | Regex secret scrubber (PEM/Bearer/URL creds/keys/cookies).
DiagnosticsEngine | Read-only findings with runnable fix_commands.
RepairPlanner | Doctor report + safe auto-repair planner.
GlobalSearch | Cross-entity prefix/word/substring search.
SupportBundle | Redacted zip exporter (summary/doctor/logs).
NetworkProbe | Parallel TCP 443 online check with cache.
Journal | Crash-safe operation log with retry/undo hints.
ResourceLimits | Optional memory, CPU and process caps applied at the next start. `cpu_percent` (1-100, a share of *all* cores) and `cpu_threads` (1..=logical cores, converted to a percentage and rounded up) are mutually exclusive; `cpu_limiter_path` overrides where `cpulimit.exe` is searched for. The cap is applied by wrapping the spawn in the `cpulimit` utility — `cap_process` returns Err naming the install when a wanted cap has no utility, so a start is refused rather than left uncapped. `find_cpu_limiter` order: **the running executable's own directory first**, then `cpu_limiter_path`, then OLS_CPULIMIT_PATH, then the repo's `vendor/cpulimit/cpulimit.exe` (dev builds only, via compile-time CARGO_MANIFEST_DIR), then %LOCALAPPDATA%\Programs\cpulimit, then PATH. The sibling comes first because that is the hash-checked copy the installer ships, and because the settings DB is shared between a dev build and an installed one — a path saved while running from target\ would otherwise keep an installed app pointing at that dev machine's folder. A configured path is the fallback for when there is no sibling, which is the only case the UI shows the field in; a path that is not a file is skipped, not treated as "no limiter anywhere", so a stale setting cannot disable the cap in a correct install. The repo copy comes before the machine's %LOCALAPPDATA% one so a dev build reports the binary this checkout shipped rather than a stray install that has nothing to do with it. `cpu_cap_status` / `CpuCapStatus` tell the UI whether a wanted cap can be applied and at what percentage.

VenvTools | Python venv finder + create-args builder.
CustomInstallStore | User-pinned exe paths winning over detection. Cloneable for the same reason as SettingsService. A pinned exe inside the app (a managed runtime under `<install>\runtimes`) is persisted relative and expanded to a full path on load, so a moved install keeps its own runtimes instead of reporting them as not installed; a tool the user installed elsewhere keeps its own path untouched.
Resolver | Version precedence manifest>detected>global.
Detector | Marker-file framework detection + workspace scan.
PluginManager | Declarative plugin.yaml installer/validator.
Updater | Minisign-signed self-updater (latest.json + SHA check). install_update spawns the verified installer and then exits the process on a 1.5s timer: Windows locks a running image, so an installer started while the app is alive cannot replace `OLS.exe`, and an update that reported success while the old process kept running changed nothing. The exit is what leaves the file lock behind; installer/open-local-server.iss CloseApplications is the second half of the same rule for a user who runs the setup exe by hand.
ServiceManager | DB/cache/mail lifecycle + TCP health; also lists/proxies the three web servers (kind web) without owning their processes. start() waits for the spawn to be decided and returns the OS error if the process never started, keeping that reason in start_failures (survives the dead process record) for read_log; stop() waits for exit and errors when a kill was ignored.
CustomServiceStore | User programs as supervised services (custom- prefix).
DbTools | External GUI tools detect + launch (HeidiSQL/pgAdmin/NoSQLBooster/Tiny RDM), plus the user-registered `ExternalTool{ id, name, engines, executable, args }` that lets **any** program act as a custom DB explorer (`custom_db_explorer` is the form's own example id, not a product). Each tool row renders its own `TechIcon` mark; `pgadmin` and `heidisql` have no simple-icons brand and so are drawn — pgAdmin as a stroked elephant head inside a desktop window in `currentColor`, HeidiSQL as a plain disc filled with the brand's green-to-white gradient (`#2fa24c` → `#ffffff`, a fixed gradient id so every instance paints the same ramp) with no glyph inside it, so two adjacent tools stay told apart by shape as well as by colour. `tinyrdm` is a drawn Redis-client window. `nosqlbooster` (Mongo leaf in a window), `dbbrowser` (database cylinder over a grid) and `compass` (needle) are drawn too, so no GUI tool falls through to the generic file glyph. **`ExternalToolStore::save` normalizes and validates**: id and name are trimmed, the id lowercased, engines trimmed/lowercased/de-duplicated, and every engine checked against `KNOWN_ENGINES` (mariadb, postgres, mongodb, redis, memcached, sqlite) — an id no page passes can never be reached, so accepting it would save a tool that silently never appears. The refusal is a `Diagnostic` naming the ids that work. Lookup (`for_engine`, `get`, `remove`) is case-insensitive on both sides. **An empty engine list means "offered on every engine", and that is a listing rule, not a preference rule**: `for_engine` — what "Automatic tool" resolves to — still skips it, so a catch-all cannot quietly displace HeidiSQL or pgAdmin.
MailPlanner | Per-framework .env Mailpit planner with diff preview.
Monitor | sysinfo CPU/mem/disk + per-PID rollup + site cost.
WorkerStore/WorkerProcesses | Queue workers registry + PID map.
ScheduleStore/TaskRuns | Cron tasks + 1-min ticker, no overlap.
WebServer trait | render_main/render_site/validate/start/reload/stop.
WebManager | Per-server render-write-validate-reload pipeline with rollback + drift detect; one Running entry per server, each startable on its own.
WebConfig | {default_server, servers:{id -> ServerPorts{http,https}}, php_workers, dns_port}; effective_ports(id) is 80/443 for the default and the stored pair otherwise.
ServerPorts | {http, https} - the stored pair one server keeps even while it is the default.
Server first-time ports | apache 8080/8443, caddy 8081/8444, nginx 8082/8445; two servers may never share a bound port (WebConfig::port_conflicts).
Nginx/Apache/Caddy | Server renderers + invocation builders. Each also renders the per-server `localhost/<prefix>` routes file (`_ols_paths.<ext>`): one server block holding a location per site that asked for a path route, each proxying to that site's own vhost with the prefix stripped and the site named as `Host`. All those requests share one `Host: localhost`, so they cannot be split across per-site files the way domains are — the first `server_name localhost` on the port would answer for all of them. Going through the real vhost means the prefixed URL is answered by exactly the config the site already has, instead of a second copy of the PHP/proxy/static logic that could drift from it. "The site's own vhost" is the one that *serves* it: a site with TLS and "Redirect to HTTPS" answers its plain-HTTP vhost with nothing but a redirect to `https://<its own hostname>`, so such a site is proxied to over its **HTTPS** vhost (nginx `proxy_pass https://` + `proxy_ssl_server_name`/`proxy_ssl_name`, Caddy `reverse_proxy <https port>` + `transport http { tls_server_name }`, Apache `ProxyPass https://` + `SSLProxyEngine on`) and a site without TLS still takes the HTTP vhost. Each route also sends `X-Forwarded-Prefix: /<prefix>`, because the prefix is stripped on the way in and an application would otherwise rebuild every absolute URL without it.
DomainStore | Domain data + validation (no rendering). `path_prefix` (the `localhost/<name>` route) is validated and checked for uniqueness here, not in the renderer. The store is the only writer of the `domains` collection, and it translates the root on the way in and out: a root inside the app is persisted relative (`AppPaths::encode_root`) and expanded back to a full path on load (`decode_root`), so nothing downstream — renderers, diagnostics, search, snapshots — ever sees a relative path. The built-in `openlocalserver.test` home site is re-anchored to `<data>/home` on every load: its folder is the app's own, never one the user picked, so a moved install must not report it as "folder does not exist" while its files sit in the current data dir. `write_home_page` never overwrites the *page*, so a hand-edited welcome page survives both the re-anchor and the re-seed. The seeded `logo.svg` / `logo-dark.svg` are the exception: they are generated bytes (`include_bytes!` of `ui/public/favicon*.svg`), so a stale copy is rewritten while the page is still the stock design this build ships, and left alone once the marker is gone. Otherwise a repaint would reach fresh installs and never reach existing ones, silently. The page itself is versioned by a `<!-- home vN -->` marker: `HOME_VERSION_MARKER` is what this build ships (v9) and `HOME_LEGACY_MARKERS` lists every older stock design, so a design change refreshes installs that never hand-edited the page and leaves a user's own page alone. v9 is what names the product in full — "Open Local Server" — in the header and footer brand, beside the mark, instead of a bare "OLS" the reader has to decode.

AutoBackup | §130 scheduled backups. `AutoBackupSettings{enabled,scope,schedule,keep,snapshots,include_env,include_files,databases}` in the `auto_backup` settings key is the app-wide plan; `AutoBackupSiteSettings{enabled,schedule,keep,include_files,include_env,databases}` per hostname in `auto_backup.sites` is each site's own, taken on its Backups page; `AutoBackupState{buckets,last_run}` in `auto_backup_state` records the file name of everything a pass wrote, bucketed `snapshot:<project>`, `sql:<engine>/<db>`, `sqlite:<path>`, and retention deletes only recorded paths. `AutoBackupRun{started_ms,finished_ms,created,removed,problems}` is one pass in words; `AutoBackupStatus{settings,description,next_run_ms,running,last_run,kept,sites}` is what the pages render. **The period, the keep count and the choice of what gets copied are the site's own when the plan is scoped to chosen sites**, because not every site is equally worth an hourly backup and one site's `.env` files are not every site's business, and the app-wide set when the plan covers everything -- per-site values kept in that case would be a second answer to a question the plan already answers, so all five are dropped on save rather than stored and ignored. Each site is reported with its own values, its *effective* values (its own, or the plan's) and `managed_by_plan`, which is what lets the site's page show the period, keep count and contents in force without offering an edit that does nothing. A snapshot holds a whole project, so two sites of one project run at the first one's settings and any disagreement -- period, keep count or contents -- is reported rather than resolved silently. A site switched on with all three copy answers off is refused, because a config-only snapshot every period is not a backup; `None` means "follow the plan", never "copy nothing". `clock_tick` checks every project against its own period, hands only the due ones to the pass, and does the work on its own thread behind a process-wide `RUNNING` flag, so a slow dump delays neither a scheduled task nor a second pass. Scope `app` = every project plus every MariaDB/PostgreSQL database and every registered SQLite file; `site` = the covered projects and the databases their manifests declare. A server that is installed but stopped is started first, because a dump needs one; one that is not installed becomes a problem in `problems`, never a silent skip.
ProjectStore | Folder registry, ID=SHA256(path)[..16]. A stored path is the canonical one with Windows' \\?\ prefix removed -- and for a share that means \\?\UNC\server\share becomes \\server\share, not UNC\server\share, which is not a path and could not be reopened by the Explorer menu, a site or the CLI.
ProjectTools | Composer/npm/venv/xdebug thin wrappers, plus the project Backups tab (`BackupsPanel`): the §130 automatic-backup plan for this project's sites, taking and restoring snapshots, exporting, and cloning the environment. Named Backups rather than Snapshots because a database dump belongs on the same page as the snapshot that records the database it belongs to, and hiding one behind a different name is how a user ends up backing up configuration and then losing data. When the app-wide plan is scoped to chosen sites, each site in the list carries its own "How often" (a preset or a custom cron field), "How many to keep" and a "What to copy" group (project files, .env files, databases); when the plan covers everything, those read "Managed by Settings" instead, because a control that saves a value nothing reads is worse than no control -- and the site's own switch is disabled in that case too (`rowLocked` = plan on and app scope), since a per-site `enabled` the app-wide plan overrides is the same second answer wearing a switch. The row still renders, greyed, so the user can see whether the site is covered; its hint names the way out (set the scope to chosen sites). With the plan *off* the switch stays live, because a plan that runs nothing is the user's to arm from either page. A write sends the whole site entry, not just the field that changed, because the command replaces it and editing the period must not quietly reset the contents back to following the plan.
Wordpress | WordPress detection and a one-time admin sign-in (`is_wordpress`, `issue`, `sweep`, `revoke`, `describe`). Detection reads `wp-config.php`, `wp-admin/index.php` or `wp-includes`+`wp-content`, so an install whose config file is missing (freshly cloned) is still recognized. `issue` writes ONE must-use plugin at `wp-content/mu-plugins/ols-wp-login-<token>.php` (creating `mu-plugins` when absent) carrying a 128-bit `getrandom` token, `OLS_SIGNIN_ISSUED`/`OLS_SIGNIN_TTL`, and answers with `{site_url}/?ols_signin=<token>`. Any earlier bridge is removed first, so a project never has two live links. Nothing here reads or stores a WordPress password: the generated PHP contains no `user_pass`/`wpdb`/`wp_set_password`, signs the chosen administrator in with `wp_set_auth_cookie`, and calls `unlink(__FILE__)` the moment it does. The sign-in screen is the one surface the user meets outside the app, so it carries the app's own theme tokens (`ui/src/index.css`: primary `oklch(0.6 0.135 168)` light / `oklch(0.75 0.14 168)` dark, card, border, muted-foreground, 8px radius, Inter stack) as a `prefers-color-scheme` pair with an explicit `html[data-theme=dark]` override — copied, not linked, because WordPress serves the page out of the project folder and cannot reach the app's stylesheet. `theme` (the colourway the UI was showing, passed through `wp_sign_in`) is written as `data-theme` on the root element, and the media query is suppressed by `html:not([data-theme=light])`, so an app in light mode on a dark-mode machine opens a light page; with no `theme` the attribute is absent and the browser decides. A sign-in screen in a foreign design language is exactly what a phishing page looks like. `sweep` (run from every listing) deletes any bridge past `issued + ttl + 60s` **and any bridge whose constants it cannot parse** — a file OLS cannot age out is a file it must not keep. `revoke` is the manual cancel. TTL clamps to 1..900s (default 300s).

TaskManager | §164 background task registry. A task is a `TaskView{id,kind,title,target,state,steps,progress,results,problems,error,started_ms,finished_ms,cancel_requested}` plus a thread; `start(kind,title,target,total,work)` returns the id to watch it by and `work` receives a `TaskHandle`. Linear in its steps (`begin_step`/`end_step`/`fail_step`/`skip_step`), so a caller describes what it is doing by naming the step it starts rather than maintaining a list of states. `advance`/`set_bytes` are throttled to 200ms — reporting per chunk froze the Runtimes page once already (`RuntimeManager::ProgressThrottle`) — while every step, result and problem publishes immediately, and **every event carries the whole view** so a UI renders from the event and never reconciles a delta. A `FinishGuard` in the spawned thread fails a task that neither succeeded nor stopped, so a panicking worker cannot leave a spinner on the page forever — the guard holds its **own** `TaskHandle` (one `Arc` clone via `TaskHandle::sharing`) rather than taking the worker's, because `work` receives the handle by value and a worker that unwinds or returns early never gives it back, so a guard emptied first has nothing to fail the task with. `cancel` sets a flag the worker checks *between* items, never mid-write; `report` (in `command.rs`) turns a worker error into `Cancelled` when a stop was asked for, because a deliberate stop is not a failure. `dismiss`/`clear_finished` drop finished tasks only — a running one is never dropped — and the 200-entry cap trims the oldest *finished* first. In memory only: a task interrupted by a crash is reported by the Journal instead, which is the record that survives a restart. `is_running`/`get` answer one task; the list is newest first.
BundleCipher | §165 password encryption for a bundle's secrets. Argon2id (19 MiB / 2 passes / 1 lane — the OWASP parameters, deliberately identical on every machine so a bundle written on one opens on another) turns the export password into a key; ChaCha20-Poly1305 seals each entry under it. Sealing is **per entry, not per zip**: the zip crate's own AES scheme is ZipCrypto-derived and weak, and a reader can then unlock exactly the entry it needs. The key is derived **once per bundle** — the random salt lives in the manifest and every entry carries its own fresh 96-bit nonce — because deriving per entry would cost ~60ms times the file count for no extra safety, while a reused nonce under one key would break the cipher outright. A wrong password and a damaged file are indistinguishable to an AEAD, so the error says both rather than guessing. Two length edges are deliberate: `open` refuses a blob shorter than `nonce(12) + tag(16)` and accepts exactly that, because a nonce and a tag with no ciphertext is what sealing an **empty** entry produces — an empty `.env` file has to survive a round trip — and `from_hex` refuses an odd-length string up front rather than leaving the one-character tail to `chunks(2)`, which would parse `"abc"` as `0xab 0x0c` and hand back bytes the caller never wrote.
SiteBundler | §165 site bundles: one zip holding any mix of settings, `.env` files, database dumps and project files for any number of sites. `BundleOptions{settings,env,databases,files}` (settings+env on by default — small, and what "the site's configuration" means to most people; data is asked for) and `OnConflict{Update, Rename}`. Sites are **grouped by the project behind them**, so exporting `shop.test` and `blog.test` of one project gives one entry with two sites and imports back as one project, not two; a site with no project has nothing to describe and is reported, never exported half-way. The manifest (`bundle.json`, format 1, written **last** through a `.part` file) lists each site's config as a `SnapshotContent` document with the `.env` contents and dump names removed, so **the manifest itself never holds a secret**; `content_of` puts them back on read and every import path downstream is then the one a snapshot restore already uses. Only `.env` files and database dumps are sealed — the two places passwords live; project files and settings stay readable so the bundle can still be reviewed, and the dialog says so. The import's `preview` reads the manifest and reports, per site, which hostnames already exist and which free name a rename would take, so the update/rename choice is made on facts. `Update` finds the project owning the first colliding site, takes a **"Before import" snapshot of the current state first** (the same rule `restore_snapshot` follows) and names it in the result, so the update is reversible; `Rename` registers a new project folder and adjusts everything the collision would have made ambiguous (hostname, database, port) through the same `Adjust` a clone uses. Per-site failures land in `problems` and never abort the batch — one bad database must not cost the user the rest of the export. Not reachable over the HTTP API (absent from the `operate` allow-list) and absent from the AI command allow-list.

ShellMenu | HKCU Directory\shell right-click installer. Its Icon is the app's icon.ico (shipped beside the CLI) rather than the program the entry runs, which is a console binary with no icon resource. Status checks what the entries point at, not just that the keys exist, so a menu that launches the app reads as not installed and the card offers Add again. It runs the CLI, never the app: find_cli looks for `olsc.exe` beside the app (or on PATH) and refuses the running executable, because the app ships as `OLS.exe` and Windows does not tell the two names apart by case -- a lookup for `ols.exe` found the app, and "Add to OLS" launched OLS instead of registering the folder. The installer ships `olsc.exe`, which is the command the docs use. There is no shim and no hand-over: `olsc` is its own program, and `ols` is the app, which is the only way the two can share one install folder on a filesystem that does not distinguish file names by case.

cli_dispatch | Makes the app answer for the command line (cli_dispatch.rs, wired in src-tauri/src/main.rs before anything starts). `ols` cannot be a separate program, because the app ships as `OLS.exe` and Windows does not tell two names apart by case, so a lookup for `ols.exe` finds the app; an `ols.cmd` shim in the same folder cannot win either, because `.EXE` comes before `.CMD` in PATHEXT — measured, not assumed: with both side by side `olsc --version` printed nothing and exited 0. A launch whose argument list is not an app launch (`is_app_launch` = no arguments, or exactly `--minimized`) is therefore handed to `find_cli()` and the process exits with the CLI's exit code. The allow-list is the app's own arguments, not the CLI's subcommands: a subcommand list would be a second copy of every command name that drifts silently, and a misspelled subcommand would open the app instead of printing `unrecognized subcommand`. `find_cli` compares canonical paths and refuses the running executable, the same guard ShellMenu uses.

HelperService | LocalSystem resident pipe server (SDDL locked). Installs a *copy* of the helper into an admin-only folder — deliberately not the app's own, because a LocalSystem service running a binary out of a user-writable folder is a privilege escalation — which means the two can drift apart. That is why the service answers `version` over its pipe: `elevate::service_version` compares it against the app and `HelperService.outdated` reports the difference, so an updated or moved app can say so rather than silently talking to an older elevated half. The copy's folder is resolved from `ProgramW6432` → `ProgramFiles` → `ProgramFiles (x86)` → the literal `C:\Program Files`, because a 32-bit process sees `ProgramFiles` redirected and would otherwise install to a different tree than the 64-bit service manager is told about. A missing helper is reported by `elevate::helper_missing`, not by a bare "not found": an installed build ships it beside the app, and only a development build has to run `cargo build -p ols-helper` first — which is the fix the message has to name, since without it the Update button fails with nothing the user can do.
TauriApp | Window+tray+single IPC run_command + event emits.

ApiCard (§137) states what the local API is, the port and mode fields, and the token; the endpoint contract, the mode allow-lists and the security rules live in docs/API.md, reached by a "Read the docs" button that calls the `open_url` command (a plain `<a target="_blank">` does nothing in the Tauri webview) — a settings card is the wrong place for a reference, and prose in one is prose every user scrolls past.
ExcludedSitesCard | Settings → Excluded sites. Renders `list_deleted_items` newest-first as one `divide-y rounded-lg border` list (dense `py-2` rows, capped at the 200 newest with a "showing N of M" note) inside the usual `max-w-3xl` Card, with a count + `Clear all` toolbar above and a plain inline empty state below. Each row is the value (`text-sm font-medium truncate`, full path in `title`) over `timeAgo` + a `Badge` naming `site`/`folder`, so folders and sites read differently without a second column; nothing is coloured red, since a long history would otherwise be a wall of red — red appears only on the confirmed `Clear all`. Row actions clear one entry with no dialog (it is a history entry, reversible by re-deleting) and answer with the updated list so the row disappears without a re-read; `Clear all` asks first through `confirmAction`, naming the count and stating that files are untouched. Clearing never re-adds anything by itself — the copy says "can be scanned again", because the next scan or `sync_auto_domains` is what brings it back.

SettingsExtras | Resources card (CPU, database and application limits), the §130 Automatic backups card, + settings backup cards. The CPU section is a mode Select (No CPU limit / Percentage of the whole CPU / Number of threads) plus one NumberInput: percentage max 100, threads max the machine's logical cores, and the hint states the resulting percentage of all cores. When a cap is set the card either names the `cpulimit.exe` it found or warns that the cap cannot be applied yet and says how to fix it, from `CpuCapStatus`. The Automatic backups card saves each control on change (no separate Save button, so a half-typed cron expression is never persisted as a plan that cannot run) and renders the last pass verbatim: what was written, what was deleted past the limit, and one line per problem, because a backup that quietly covered less than the card says is the failure this feature exists to prevent. It owns the *plan* only: when the scope is chosen sites, the "How often" and "How many to keep" rows say "Set per site, on the site's Backups page" instead of offering a number that nothing reads, and the scope list reports the tally of which sites asked rather than a second list to tick.

vendor/cpulimit | The vendored CPU limiter binary (kz370/win-utils, MIT), its pinned SHA-256 and its provenance. Shipped by installer/open-local-server.iss into {app} next to the app exe, and hash-checked by scripts/build-installer.bat on the source *and* on the staged copy, so a tampered or corrupted copy cannot reach an artifact. `Get-FileHash` is not available in the build environment; hashing uses certutil, the same as the script's existing :show_hash.
installer/open-local-server.iss | Inno Setup script. AppId (dev.openlocalserver.app) and DefaultDirName (C:\OpenLocalServer) are frozen identifiers per docs/BRAND.md 4.3 (DaemonExe is no longer one: the daemon is the CLI, so it moved from openlocalserver.exe to olsc.exe with the rest of that rename); AppName, AppExe, OutputBaseFilename and the artifact names are OLS. AppExe is 'OLS.exe' and the pre-rename name is kept beside it as LegacyAppExe: every "is it running?" check in [Code] — RegisteredDir, AnyAppRunningHere, InitializeSetup, PrepareToInstall — asks about both, because a pre-rename install is still running under the old name and holds the very file [Files] writes; an install that reported success while the old exe stayed on disk is the exact failure this script exists to prevent. PruneUnshippedFiles deliberately does not list LegacyAppExe as shipped, so the old exe is deleted at ssPostInstall (after PrepareToInstall confirmed it is closed, so the delete cannot hit a lock) — leaving it would leave two app exes in one folder, the old one still holding the single-instance mutex. CloseApplications=force + RestartApplications=yes is the Restart Manager backstop for anything [Code] missed, and CloseApplicationsFilter=*.exe|*.dll covers ols-helper.exe and cpulimit.exe. [Files] ships olsc.exe because the Explorer right-click menu is written to run the CLI and find_cli looks beside the app -- without the CLI in the folder the menu could not be installed at all. It used to ship an `ols.cmd` shim as well; that is gone, because within one directory cmd resolves by PATHEXT and .EXE comes before .CMD, so `ols` in the install folder was the app every time, and a shim in an earlier PATH directory would have been a second spelling of one command that only works in some folders. The app now answers for the command line itself (see `cli_dispatch`), so one name, one command, and nothing to uninstall from PATH. [Run] launches {app}\OLS.exe, not a shortcut, so the copy that just installed is the one that opens; a second launch is harmless because the app is single-instance. It builds and stages olsc.exe next to the app and fails with a Diagnostic when the CLI is missing from target\release, because [Files] ships it and ISCC has no skipifsourcedoesntexist on it -- a build that passed the app and helper checks and then failed inside ISCC would name the wrong problem. scripts/build-installer.bat `inno` mode stages target\release without recompiling and now prints each staged file's timestamp for exactly this reason — an installer that looks older than the source is a stale target\release, not a broken updater. DefaultGroupName is OLS but does not reach an upgraded machine: an upgrade takes the Start Menu group name from the *previous install's uninstaller*, so the pre-rename "Open Local Server" folder survives the rename and the new shortcut lands inside it. MigrateLegacyStartMenuGroup fixes it at ssPostInstall: .lnk entries are moved into the current group folder (a colliding name is deleted, since [Icons] just wrote this installer's copy) and the legacy folder is removed only if it ends up empty, never recursively — anything the user filed in there is left alone, and every failure is logged rather than raised so a cosmetic cleanup can never fail an install that otherwise succeeded.
.github/workflows/ci.yml | Three jobs in ONE workflow: `test` (windows-latest, `cargo test -p ols-core -p ols-helper`), `build` (`needs: test`) which runs `scripts\build-installer.bat full` — the same script, same stages and same SHA-256 artifact verification as a local release — and `publish` (`needs: build`, `if: startsWith(github.ref, 'refs/tags/v')`) which uploads a GitHub release. Build and publish were two workflows sharing a `v*` tag trigger and that was wrong: two workflows on one tag start at the same instant, so the publisher either races the builder (failing, because the artifacts are not there yet) or has to poll the API for a run it did not start. As jobs of one workflow `needs` *is* the ordering, the artifacts come from the run already in progress via `download-artifact`, and there is no race to handle and no second build path. **One tag trigger, not two.** Triggers are `workflow_dispatch` (build and verify, publish nothing — there is no version to publish) and `push` on `v*` (test -> build -> publish). Nothing runs on a master push: a full build is ~20 minutes and was being spent re-verifying commits that changed a paragraph, so a red suite is now found when you ask or when you tag rather than the moment you push; `pull_request:` is the trigger to add back if that trade is wrong, because PR builds catch problems *before* the tag. `concurrency` groups both workflows' runs per ref with `cancel-in-progress: false` — two overlapping runs would build the same release into the same folder, and a *cancelled* publish can leave a release created with no assets on it. `publish` is the only job with `permissions: contents: write`; `test` and `build` keep the read-only default, so a compromised build step cannot publish. Inno Setup is installed first (`choco install innosetup`) so the installer stage runs rather than silently degrading to portable-only. `BUILD_JOBS` uses the whole runner (the script otherwise caps itself at half the threads, sized for a desktop the user is also working on) and `CACHE_LIMIT_GB` is lowered so a cache wipe does not eat a full rebuild on a small runner disk. The uploaded artifact is `release/*/*` — everything the script staged, because `publish` builds the portable zip from it and the side-by-side DLLs are part of that zip; `*.exe` alone produced an artifact the portable package could not be made from. `cargo fmt --check` and `cargo clippy` stay as their own step ahead of the build: they are seconds of work against a multi-minute build, so failing on them first is the cheap ordering. The tests stay on Windows and stay a separate job rather than folding into the build, because they are Windows tests — temp-path spellings, the hosts file and file locks are what they are there to check, and a Linux runner would pass the cases that broke the release. The UI lint job is gone because `build-installer.bat` stage 1 runs `npm run build` (`tsc -b && vite build`) over the same sources on the same runner; `npm run lint` is a local gate, not a build gate.
.github/workflows/ci.yml :publish | guards | the tag must agree with the version in `Cargo.toml` — the build names artifacts from `Cargo.toml`, so tagging v1.2.0 on a 1.1.0 tree would publish a binary labelled as a version it is not, and `updater::newer` is a plain greater-than, so every install would be offered an "upgrade" that is older than what it replaced. It re-checks the setup exe, helper and cpulimit after `download-artifact` because the staging the build job verified is not the staging this job received, and `upload-artifact` flattens to the common ancestor of what it matched, so the version folder arrives as `<version>/` and is moved back under `release\<version>\` to keep the paths build-installer.bat and upload-release.bat use. Builds the portable zip from the app exe + helper + DLLs (one app exe, never the setup beside it, never both app names), writes `OLS-<version>-SHA256SUMS.txt`, and creates or updates the release with notes from `release-notes\<tag>.md` or GitHub's generated notes — the same rule upload-release.bat uses. `latest.json` is written and minisign-signed only when the `OLS_MINISIGN_KEY` base64 secret is present, and the key is written to the runner temp and removed in a `finally`: a signing key left on a hosted runner is a signing key on somebody else's disk. Without the secret the release still ships and the step warns that the in-app updater will not see the version, because an unsigned manifest is worse than none — the updater would 404 on it, or serve one that no signature check can vouch for.

Ui primitives | button/card/dialog/input/form/table/menu/switch/badge/checkbox/pagination (Tailwind/Radix, no IPC). Pagination draws the page controls for a long table (row count, rows-per-page dropdown, page x of y) but owns none of the state: the caller holds `page`/`perPage` and the slice. It clamps the page number for the caller on read, because a filter or a delete can leave the reader past the last page and that would draw an empty table with no explanation. Dialog sizes default/form(max-w-2xl shared form-modal)/wide; FormSection shared headers; Field errors with icon, hint swap no-shift; Field takes an optional className for the wrapper. NumberInput (input.tsx) | number field with an app-styled stepper: text input + inputMode="numeric" + role="spinbutton" + two ChevronUp/ChevronDown buttons (size-3.5, rounded-[4px], text-muted-foreground/80, hover:bg-muted, active:bg-accent, disabled:opacity-30, tabIndex -1, onMouseDown preventDefault so the caret is kept). Native type="number" is not used anywhere: its arrows are a browser widget that ignores the app radius/palette and only paints on hover in Chromium. min/max clamp both typing and stepping; value is `number | null` (null = empty); ArrowUp/ArrowDown step by 1 while focused; the raw text is held locally while the field is focused so a half-typed number is not rewritten under the cursor, but a step (arrow key or chevron) also rewrites the text from the new value, so the box always shows the number the app holds; a step starts from the number on screen (not the value prop) and is clamped+truncated before display.
