Functions / Classes / Modules / Components catalog (one-line each).

--- RUST ols-core ---
Core | Central dispatcher facade over Inner.
CoreCommand | Enum (~150 variants) covering all UI/CLI/API operations.
CoreResponse | Tagged response enum for every command.
CoreError/Diagnostic | User-facing error shape {problem,cause,fix}.
Inner | Arc-shared state holding all managers. State locks are taken through `app::lock`, which recovers a poisoned guard instead of unwrapping it — a `std::sync::Mutex` stays poisoned for the process after any panic while held, so unwrapping turned one failure into every later read panicking too. `project_detail` clones SettingsService/CustomInstallStore (both `Clone`) and drops the guards before `build_detail` does file I/O and version probes, so an unreachable project folder cannot stall other commands. Owns the deletion history (`list_deleted_items` / `forget_deleted_item` / `clear_deleted_items`) over the two skip lists `projects.removed` and `domains.auto_skip`: each entry is `{value, deleted_at}` on disk (older bare-string entries are read as entries with no date), merged newest-first for `list_deleted_items`. `skip_matches` normalizes the Windows `\\?\` prefix on both sides and compares a candidate against the stored value *and* its canonicalized form, so the watcher sync and the manual Scan judge a folder the same way and a path spelled through a short name, junction, mapped drive or `..` segment cannot slip past a skip.
AppPaths | OLS_HOME-aware path resolver (certs/data/settings). Also owns the portable path form: `encode_root` writes a path inside the app (`sites/<name>`, `data/<name>`, forward slashes) instead of the absolute path it resolved to, and `decode_root` expands it again on load, so a renamed or relocated install keeps the folders and tools that belong to it. A path still stored absolute and no longer existing is re-anchored from its trailing `sites`/`data`/`home` segment when that folder exists under the current install, and left alone otherwise so a genuinely deleted site keeps reporting as missing. `join_relative` appends the stored form one segment at a time, because joining a forward-slash string onto a Windows base would leave a path spelled with two different separators. `CustomInstall.path` and the `quickapps.projects_dir` setting use this; `Domain.root` and `Project.path` are its other two users.
SettingsService | SQLite key-value store (app.db settings table). Cloneable so a read can release the store lock before doing slow work.
Db | Central SQLite store (app.db, WAL): settings table + generic docs collections for all Vec-stores.
Secrets | OS keyring wrapper (set/get/delete).
ProcessSupervisor | Owns child processes, tree-kill, output ring, restart policy. wait_for_spawn/wait_for_exit let a caller block until a spawn is decided or a process is gone; a spawn error is kept on the record and pushed into the output ring, so a process that never started still has a readable reason.
ProcessSpec/ProcessInfo/ProcessEvent | Process spawn descriptor, status, broadcast event.
PortChecker | Bind-probe + netstat/tasklist conflict reporter.
ExecCapture | Sync run-and-capture with timeout + CREATE_NO_WINDOW.
Logger | JSON daily rolling log with redaction.
Redactor | Regex secret scrubber (PEM/Bearer/URL creds/keys/cookies).
DiagnosticsEngine | Read-only findings with runnable fix_commands.
RepairPlanner | Doctor report + safe auto-repair planner.
GlobalSearch | Cross-entity prefix/word/substring search.
SupportBundle | Redacted zip exporter (summary/doctor/logs).
NetworkProbe | Parallel TCP 443 online check with cache.
Journal | Crash-safe operation log with retry/undo hints.
ResourceLimits | Optional memory, CPU and process caps applied at the next start. `cpu_percent` (1-100, a share of *all* cores) and `cpu_threads` (1..=logical cores, converted to a percentage and rounded up) are mutually exclusive; `cpu_limiter_path` overrides where `cpulimit.exe` is searched for. The cap is applied by wrapping the spawn in the `cpulimit` utility — `cap_process` returns Err naming the install when a wanted cap has no utility, so a start is refused rather than left uncapped. `find_cpu_limiter` order: **the running executable's own directory first**, then `cpu_limiter_path`, then OLS_CPULIMIT_PATH, then the repo's `vendor/cpulimit/cpulimit.exe` (dev builds only, via compile-time CARGO_MANIFEST_DIR), then %LOCALAPPDATA%\Programs\cpulimit, then PATH. The sibling comes first because that is the hash-checked copy the installer ships, and because the settings DB is shared between a dev build and an installed one — a path saved while running from target\ would otherwise keep an installed app pointing at that dev machine's folder. A configured path is the fallback for when there is no sibling, which is the only case the UI shows the field in; a path that is not a file is skipped, not treated as "no limiter anywhere", so a stale setting cannot disable the cap in a correct install. The repo copy comes before the machine's %LOCALAPPDATA% one so a dev build reports the binary this checkout shipped rather than a stray install that has nothing to do with it. `cpu_cap_status` / `CpuCapStatus` tell the UI whether a wanted cap can be applied and at what percentage.
ElevateRunner | Privileged ols-helper invoker with UAC fallback.
Catalog | Built-in runtime pins (URL+SHA256, HTTPS enforced).
CatalogSources | Signed remote catalogs (minisign, re-verified each load).
RuntimeManager | Download-verify-extract + version probe + events + per-vendor online version feeds (node, php, nginx, apache, composer, mongodb, postgres, redis, memcached, mailpit, mariadb). Per-install pause/cancel controls; a stop is a Cancelled outcome, not a failure.
PhpPools | Per-version php-cgi FastCGI pools + extension management.
NodePm | Lockfile/packageManager detector + corepack switch.
ComposerReader | composer.json/lock merger, vendor/scripts reporter.
VenvTools | Python venv finder + create-args builder.
CustomInstallStore | User-pinned exe paths winning over detection. Cloneable for the same reason as SettingsService. A pinned exe inside the app (a managed runtime under `<install>\runtimes`) is persisted relative and expanded to a full path on load, so a moved install keeps its own runtimes instead of reporting them as not installed; a tool the user installed elsewhere keeps its own path untouched.
Resolver | Version precedence manifest>detected>global.
Detector | Marker-file framework detection + workspace scan.
PluginManager | Declarative plugin.yaml installer/validator.
Updater | Minisign-signed self-updater (latest.json + SHA check). install_update spawns the verified installer and then exits the process on a 1.5s timer: Windows locks a running image, so an installer started while the app is alive cannot replace `OLS.exe`, and an update that reported success while the old process kept running changed nothing. The exit is what leaves the file lock behind; installer/open-local-server.iss CloseApplications is the second half of the same rule for a user who runs the setup exe by hand.
ServiceManager | DB/cache/mail lifecycle + TCP health; also lists/proxies the three web servers (kind web) without owning their processes. start() waits for the spawn to be decided and returns the OS error if the process never started, keeping that reason in start_failures (survives the dead process record) for read_log; stop() waits for exit and errors when a kill was ignored.
CustomServiceStore | User programs as supervised services (custom- prefix).
DbTools | External GUI tools detect + launch (HeidiSQL/pgAdmin/NoSQLBooster/Tiny RDM). Each tool row renders its own `TechIcon` mark; `pgadmin` and `heidisql` have no simple-icons brand and so are drawn — pgAdmin as a stroked elephant head inside a desktop window in `currentColor`, HeidiSQL as a plain disc filled with the brand's green-to-white gradient (`#2fa24c` → `#ffffff`, a fixed gradient id so every instance paints the same ramp) with no glyph inside it, so two adjacent tools stay told apart by shape as well as by colour. `tinyrdm` is a drawn Redis-client window. `nosqlbooster` and `dbbrowser` still have no entry and fall through to the generic file glyph.
MailPlanner | Per-framework .env Mailpit planner with diff preview.
Monitor | sysinfo CPU/mem/disk + per-PID rollup + site cost.
WorkerStore/WorkerProcesses | Queue workers registry + PID map.
ScheduleStore/TaskRuns | Cron tasks + 1-min ticker, no overlap.
WebServer trait | render_main/render_site/validate/start/reload/stop.
WebManager | Per-server render-write-validate-reload pipeline with rollback + drift detect; one Running entry per server, each startable on its own.
WebConfig | {default_server, servers:{id -> ServerPorts{http,https}}, php_workers, dns_port}; effective_ports(id) is 80/443 for the default and the stored pair otherwise.
ServerPorts | {http, https} - the stored pair one server keeps even while it is the default.
Server first-time ports | apache 8080/8443, caddy 8081/8444, nginx 8082/8445; two servers may never share a bound port (WebConfig::port_conflicts).
Nginx/Apache/Caddy | Server renderers + invocation builders. Each also renders the per-server `localhost/<prefix>` routes file (`_ols_paths.<ext>`): one server block holding a location per site that asked for a path route, each proxying to that site's own vhost with the prefix stripped and the site named as `Host`. All those requests share one `Host: localhost`, so they cannot be split across per-site files the way domains are — the first `server_name localhost` on the port would answer for all of them. Going through the real vhost means the prefixed URL is answered by exactly the config the site already has, instead of a second copy of the PHP/proxy/static logic that could drift from it. "The site's own vhost" is the one that *serves* it: a site with TLS and "Redirect to HTTPS" answers its plain-HTTP vhost with nothing but a redirect to `https://<its own hostname>`, so such a site is proxied to over its **HTTPS** vhost (nginx `proxy_pass https://` + `proxy_ssl_server_name`/`proxy_ssl_name`, Caddy `reverse_proxy <https port>` + `transport http { tls_server_name }`, Apache `ProxyPass https://` + `SSLProxyEngine on`) and a site without TLS still takes the HTTP vhost. Each route also sends `X-Forwarded-Prefix: /<prefix>`, because the prefix is stripped on the way in and an application would otherwise rebuild every absolute URL without it.
DomainStore | Domain data + validation (no rendering). `path_prefix` (the `localhost/<name>` route) is validated and checked for uniqueness here, not in the renderer. The store is the only writer of the `domains` collection, and it translates the root on the way in and out: a root inside the app is persisted relative (`AppPaths::encode_root`) and expanded back to a full path on load (`decode_root`), so nothing downstream — renderers, diagnostics, search, snapshots — ever sees a relative path. The built-in `openlocalserver.test` home site is re-anchored to `<data>/home` on every load: its folder is the app's own, never one the user picked, so a moved install must not report it as "folder does not exist" while its files sit in the current data dir. `write_home_page` never overwrites the *page*, so a hand-edited welcome page survives both the re-anchor and the re-seed. The seeded `logo.svg` / `logo-dark.svg` are the exception: they are generated bytes (`include_bytes!` of `ui/public/favicon*.svg`), so a stale copy is rewritten while the page is still the stock design this build ships, and left alone once the marker is gone. Otherwise a repaint would reach fresh installs and never reach existing ones, silently. The page itself is versioned by a `<!-- home vN -->` marker: `HOME_VERSION_MARKER` is what this build ships (v9) and `HOME_LEGACY_MARKERS` lists every older stock design, so a design change refreshes installs that never hand-edited the page and leaves a user's own page alone. v9 is what names the product in full — "Open Local Server" — in the header and footer brand, beside the mark, instead of a bare "OLS" the reader has to decode.
LocalCa | Deterministic root CA (2024-2044) + leaf issuance.
CertificateManager | Per-domain cert lifecycle (reuse unless SAN change/<30d).
HostsBlock | Idempotent BEGIN/END block transform.
DnsServer | UDP wildcard A->127.0.0.1 for suffix list.
HealthChecker | DNS->TCP->TLS->Cert->HTTP chain.
TunnelManager | Provider abstraction (cf/ngrok/lt) + confirm gate.
Inspector | Forwarding proxy + redacted traffic log (500 cap).
DbBackup | mysqldump/pg_dump backup/restore with safety copy; file name stem is the database name, so only names a Windows file cannot hold (/ \ : * ? " < > |, control chars, leading dot, >120) are rejected — `-`, `.`, spaces and non-ASCII back up fine.
SqliteStore | WAL-safe sqlite3 .backup + integrity_check registry.
Migrator | Laragon/XAMPP/Wamp scanner + live-dump importer.
ProjectStore | Folder registry, ID=SHA256(path)[..16]. A stored path is the canonical one with Windows' \\?\ prefix removed -- and for a share that means \\?\UNC\server\share becomes \\server\share, not UNC\server\share, which is not a path and could not be reopened by the Explorer menu, a site or the CLI.
ProjectTools | Composer/npm/venv/xdebug thin wrappers.
Manifest | .openlocalserver/*.yaml strict schema.
ProfileStore | Reusable env templates (laravel/node-api/python-api/full).
SetupPlanner | 14-step resolve-plan-apply with rollback + lock file.
SnapshotManager | Zip snapshots (manifests+sites+certs meta) + clone/import.
EnvFile | Lossless .env line editor preserving comments/order/CRLF.
CommandCatalog | Symfony/artisan/npm script discovery + signature parser.
GitTools | Real-binary git via PATH/portable + ASK_PASS creds + ~/.ssh key detection (list_ssh_keys).
Shortcuts | Jump-to places + open-with guard.
EditorRegistry | VSCode/Cursor/Zed/etc detect + resolve.
TerminalManager | portable-pty shells with runtime PATH-first (max 8).
ShellMenu | HKCU Directory\shell right-click installer. Its Icon is the app's icon.ico (shipped beside the CLI) rather than the program the entry runs, which is a console binary with no icon resource. Status checks what the entries point at, not just that the keys exist, so a menu that launches the app reads as not installed and the card offers Add again. It runs the CLI, never the app: find_cli looks for `olsc.exe` beside the app (or on PATH) and refuses the running executable, because the app ships as `OLS.exe` and Windows does not tell the two names apart by case -- a lookup for `ols.exe` found the app, and "Add to OLS" launched OLS instead of registering the folder. The installer ships `olsc.exe`, which is the command the docs use. There is no shim and no hand-over: `olsc` is its own program, and `ols` is the app, which is the only way the two can share one install folder on a filesystem that does not distinguish file names by case.
ProcfileImporter | Procfile.dev>Procfile web/worker splitter.
LoadTestRunner | k6 scripts runner with VU cap + JSON metrics.
XdebugConfig | Per-PHP ini block + IDE validator.
QuickApp Schema/Plan/Catalog/Run/Commands | Recipe validate->plan(review)->run(execute) + history.
cli_dispatch | Makes the app answer for the command line (cli_dispatch.rs, wired in src-tauri/src/main.rs before anything starts). `ols` cannot be a separate program, because the app ships as `OLS.exe` and Windows does not tell two names apart by case, so a lookup for `ols.exe` finds the app; an `ols.cmd` shim in the same folder cannot win either, because `.EXE` comes before `.CMD` in PATHEXT — measured, not assumed: with both side by side `olsc --version` printed nothing and exited 0. A launch whose argument list is not an app launch (`is_app_launch` = no arguments, or exactly `--minimized`) is therefore handed to `find_cli()` and the process exits with the CLI's exit code. The allow-list is the app's own arguments, not the CLI's subcommands: a subcommand list would be a second copy of every command name that drifts silently, and a misspelled subcommand would open the app instead of printing `unrecognized subcommand`. `find_cli` compares canonical paths and refuses the running executable, the same guard ShellMenu uses.

--- CLI / HELPER / TAURI ---
OlsCli | clap CLI sending CoreCommand over control pipe, auto-spawns daemon.
DaemonRunner | Background core + scheduler clock + graceful stop.
HelperMain | Elevated closed command set (hosts/nrpt/service).
HelperService | LocalSystem resident pipe server (SDDL locked). Installs a *copy* of the helper into an admin-only folder — deliberately not the app's own, because a LocalSystem service running a binary out of a user-writable folder is a privilege escalation — which means the two can drift apart. That is why the service answers `version` over its pipe: `elevate::service_version` compares it against the app and `HelperService.outdated` reports the difference, so an updated or moved app can say so rather than silently talking to an older elevated half. The copy's folder is resolved from `ProgramW6432` → `ProgramFiles` → `ProgramFiles (x86)` → the literal `C:\Program Files`, because a 32-bit process sees `ProgramFiles` redirected and would otherwise install to a different tree than the 64-bit service manager is told about.
TauriApp | Window+tray+single IPC run_command + event emits.
TauriApp status icon | One artwork in four colourways — light/dark theme × running/stopped — painted on the tray, the window (taskbar) and, through `ols:status-icon`, the in-app mark. Bytes: green `icons/{32x32,128x128}.png` (also the tauri bundle set), red `icons/red/*`, dark `icons/dark/*`, dark red `icons/dark/red/*`, all embedded with include_bytes!. `status_mark` decides red using ServiceManager::any_running plus supervisor `is_alive` per record — the same rule `any_running`/`prune_finished` use, so a process in `Restarting` is not counted by one check and dropped by the other. `apply_status_icon` paints first and caches second, and only caches after `set_icon` actually succeeded, so a mark that raced the tray's own creation is retried by the next 2s tick instead of freezing for the session. Every `set_icon` error is logged rather than dropped. The cache key is the pair `(red, dark)`, so a theme flip repaints without a service change and a service change repaints without a theme change. `ols:status-icon` is emitted on every repaint and on every `show_main_window` reveal, so a webview that mounts after the last state change is not left showing the wrong mark.
TauriApp theme icon | The theme is a UI-local setting (localStorage, no core counterpart), so the UI emits `ols:theme` with the *resolved* theme and `set_theme_icon` repaints the native marks to match. Seeded from `Window::theme()` at setup so a dark desktop is not painted light for a frame before the webview answers. Unknown payloads are ignored rather than treated as light.
scripts/build-app-icons.bat | The entry point for regenerating every icon: preflights the tools, forces UTF-8, then runs the ps1. Image work goes through whichever of ImageMagick (`magick`) or `ffmpeg` is on PATH, so a machine without ImageMagick still builds the same artwork; `-Tool magick|ffmpeg` on the ps1 pins one. Both backends were within 0.1 degrees of each other on the same master. Prints the follow-up (`cargo build`) because the tray and window marks are `include_bytes!`d, so a Rust rebuild is what carries the new bytes into the running app.
scripts/build-app-icons.ps1 | Regenerates every icon from assets/icon.webp, assets/stop-icon.webp and assets/icon-dark.webp: masters into `icons/source/`, the tauri bundle set, the three runtime size sets, and the four self-contained `ui/public/favicon*.svg`. The dark stopped master is derived by rotating the dark running master's plate hue onto the light red's, so the two pairs stay one artwork in two colourways instead of two hand-painted marks. The rotation is *measured* per run (a circular mean over the saturated pixels of a 96x96 downscale, not a hardcoded constant: the plate is a gradient so no colour is modal, the white "OLS" glyph wins any histogram, and hue is an angle, so a plain mean of degrees would average 350 and 10 into 180 and turn red into cyan). Nothing downstream is hand-edited.
ui/public/favicon*.svg | Four self-contained marks (light/dark × running/stopped), each the 128px PNG embedded as base64 so a file copied anywhere still renders. Selected in the UI by `useAppMarkPath` (theme + `useServerStopped`) so the sidebar, the titlebar and the About card can never disagree with the tray and the taskbar. favicon.svg is also the exact byte source the Rust welcome page seeds `logo.svg` from.
TauriApp window reveal | Main window configured visible:false (the window is transparent, so showing it before the webview paints is a blank see-through frame). `reveal_window_on_ui_ready` shows it on the UI's `ols:ui-ready` event (emitted from main.tsx after two rAFs) with a 5s fallback timer and a MAIN_WINDOW_REVEALED guard. `show_main_window` is also the resync point for the status mark, since a window opened from the tray never gets an `ols:ui-ready`.
TauriApp tray Stop all | Dispatches CoreCommand::StopAll, so the tray and the Dashboard mean the same thing by "Stop all". Runs on its own thread: the command waits up to 10s per service and sweeps for another 10s, which would otherwise freeze the window and the tray menu. Reports by name anything the command could not stop (the one case where the mark is right to stay green).
app::should_start_hidden | Startup visibility decision (app.rs). The `startup.minimized` preference is the whole answer and applies to every launch — manual, startup entry, or shortcut — so the toggle means what it says. `--minimized` only forces a hidden start when the preference is off. Pure function, covered by startup_visibility_tests.
app::migrate_startup_entry | Rewrites an existing `HKCU\...\Run` value that still carries the old `--minimized`, which would hide the window even with the preference off. Missing entry is left alone; failure is logged, never fatal.
ui/index.html | Blocking inline pre-paint theme script (stored `ols-theme`, else `prefers-color-scheme`) so a dark-theme start never flashes white. The same script also adds `class="booting"` to `<html>`, which `index.css` paints with `--background` (on `html`, so it propagates to the canvas) until `main.tsx` drops it on the first presented frame. Revealing the window can therefore never put a see-through frame on screen: either React has painted, or the boot background is still there.
ui/src/index.css | `html, body, #root` are `background: transparent !important` so the borderless window keeps its rounded corners; the `html.booting` rule above is the only opaque paint, and it is gone before the first frame the user sees.

--- FRONTEND pages ---
DashboardPage | Overview with health filter + stop-all. The Start all / Stop all button answers the live state, not the `startup.autostart_services` list: that list is empty on a default install, so keying off it left the button permanently disabled with nothing running, and a service started by hand (Mailpit is installed by default and almost never in that list) still read "Start all" while the Services card below showed it active. The label is Stop all when any service or the web stack is running (the web stack counts on its own — PHP pools and DNS are not services in the list, and Stop all stops them too) and Start all otherwise; disabled only while another command is in flight or when there is nothing to start and nothing to stop. Its two actions are one pair: Stop all is `stop_all` (everything), so Start all starts every installed service rather than the autostart subset, and it re-reads the service list first so a service started by hand since the last poll is not started twice. Web server + Services cards render from one `get_dashboard` poll; a failed poll surfaces its Diagnostic instead of leaving them on "Loading…". Services widget lists all 9 built-ins in fixed order (mailpit, mariadb, postgres, mongodb, redis, memcached, nginx, apache, caddy) and each row is fluid at every width: the controls never give way, and between `lg` and `xl` — the band where the card is half of the two-column grid and one line cannot hold logo, name, port, state and five controls — the row becomes two lines, with the controls on their own line under the name instead of the name being truncated to nothing. Below `lg` (single column, full width) and from `xl` up (room again) it is a single line ending in the controls; the state keeps its dot, word and tooltip at every width. Row controls (start/stop/restart/reload/logs) are colour-coded per action — start emerald, stop destructive red, restart amber, reload sky, logs violet — held at reduced opacity so the strip stays readable; an action the row cannot take right now (not installed, already in that state, no log source, another command running) renders flat grey with `disabled:opacity-100` and no hover response, so "unavailable" never looks like a live control. Card order flips by width: the two-column layout puts Overview in the left column and Web server stacked over Services in the right one, while the windowed/single-column layout leads with the Web server card, then Overview, then Services (`contents lg:flex` on the right-hand wrapper plus `order-1/2/3 lg:order-none`), so the narrow window answers "is the web server up?" before the load graphs. The Services widget takes the page's `run`, not a local useAction, so a failed start/stop/restart reaches the page ErrorCard.
SitesPage | Domains+projects merged table, group/search/duplicate, bulk selection and paging. Every row is pickable, site row or not: a checkbox that only appeared once the site existed would be useless for the folder the user just dropped in. The header checkbox covers the *page*, so when the filtered list is longer a "Select all N matching rows" link offers the rest. The bulk bar (Enable / Disable / Add auto domain / web-server dropdown + Move sites / Delete / Clear) exists only while something is picked; Enable and Disable are each disabled when they would change nothing, since a disabled button beside an enabled twin is a hint while an enabled button that does nothing is a lie. A batch that needs a site calls `sync_auto_domains` first and then re-points the selection at the hostnames that appeared, so a project row does not vanish out of the selection the moment it gains its `<folder>.<tld>`. Bulk delete splits the selection: site rows go through `deleteSites`, project rows through `removeProjectFromList`, and both leave project folders untouched. Every batch reports how many changed *and* which rows were left alone. Paging is a `Pagination` footer with a rows-per-page dropdown (10/25/50/100, default 25); the page number is clamped on read rather than corrected in an effect, and a new page size always returns to page 1. New Git clone / import / QuickApp defaults to <install>\sites (quickapps.projects_dir override); each dialog shows resolved path, folder name + location editable; Git clone supports SSH auth with ~/.ssh key detection dropdown, refresh button, and file-picker fallback. One removal action per row: a row with a domain offers "Delete site" (which also takes its project off the list when that was the project's last site), a row without one offers "Remove from list". The confirm dialog names the site or project in its title and the destructive button repeats the action. The row leaves the list immediately and dims with a spinner while `applying` reports the web-server update.
QuickAppsPage/Wizard | Recipe CRUD + compact responsive recipe grid (4-col xl, 3-col lg, compact cards) + 3-phase plan/run wizard.
CommandsPage | Discovered+custom commands runner with output ring.

WebServerPage | Server/ports/certs tabs. Each settings card owns its own Save and its own dirty state — `defaultDirty` (default_server, php_workers, dns_port) and `portsDirty` (per-server http/https pairs) — so an edit in one card never raises the other card's button, and each button writes only its own keys. Saves are settings-only and never call apply_web: php_workers is read only in apply_one and dns_port only in sync_dns, so both are inert until the server is started, and a save while stopped says so next to the header buttons. installer/open-local-server.iss | Inno Setup script. AppId (dev.openlocalserver.app) and DefaultDirName (C:\OpenLocalServer) are frozen identifiers per docs/BRAND.md 4.3 (DaemonExe is no longer one: the daemon is the CLI, so it moved from openlocalserver.exe to olsc.exe with the rest of that rename); AppName, AppExe, OutputBaseFilename and the artifact names are OLS. AppExe is 'OLS.exe' and the pre-rename name is kept beside it as LegacyAppExe: every "is it running?" check in [Code] — RegisteredDir, AnyAppRunningHere, InitializeSetup, PrepareToInstall — asks about both, because a pre-rename install is still running under the old name and holds the very file [Files] writes; an install that reported success while the old exe stayed on disk is the exact failure this script exists to prevent. PruneUnshippedFiles deliberately does not list LegacyAppExe as shipped, so the old exe is deleted at ssPostInstall (after PrepareToInstall confirmed it is closed, so the delete cannot hit a lock) — leaving it would leave two app exes in one folder, the old one still holding the single-instance mutex. CloseApplications=force + RestartApplications=yes is the Restart Manager backstop for anything [Code] missed, and CloseApplicationsFilter=*.exe|*.dll covers ols-helper.exe and cpulimit.exe. [Files] ships olsc.exe because the Explorer right-click menu is written to run the CLI and find_cli looks beside the app -- without the CLI in the folder the menu could not be installed at all. It used to ship an `ols.cmd` shim as well; that is gone, because within one directory cmd resolves by PATHEXT and .EXE comes before .CMD, so `ols` in the install folder was the app every time, and a shim in an earlier PATH directory would have been a second spelling of one command that only works in some folders. The app now answers for the command line itself (see `cli_dispatch`), so one name, one command, and nothing to uninstall from PATH. [Run] launches {app}\OLS.exe, not a shortcut, so the copy that just installed is the one that opens; a second launch is harmless because the app is single-instance. It builds and stages olsc.exe next to the app and fails with a Diagnostic when the CLI is missing from target\release, because [Files] ships it and ISCC has no skipifsourcedoesntexist on it -- a build that passed the app and helper checks and then failed inside ISCC would name the wrong problem. scripts/build-installer.bat `inno` mode stages target\release without recompiling and now prints each staged file's timestamp for exactly this reason — an installer that looks older than the source is a stale target\release, not a broken updater. DefaultGroupName is OLS but does not reach an upgraded machine: an upgrade takes the Start Menu group name from the *previous install's uninstaller*, so the pre-rename "Open Local Server" folder survives the rename and the new shortcut lands inside it. MigrateLegacyStartMenuGroup fixes it at ssPostInstall: .lnk entries are moved into the current group folder (a colliding name is deleted, since [Icons] just wrote this installer's copy) and the legacy folder is removed only if it ends up empty, never recursively — anything the user filed in there is left alone, and every failure is logged rather than raised so a cosmetic cleanup can never fail an install that otherwise succeeded.
