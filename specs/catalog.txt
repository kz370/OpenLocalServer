--- RUST ols-core ---
Core | Central dispatcher facade over Inner.
CoreCommand | Enum (~150 variants) covering all UI/CLI/API operations.
CoreResponse | Tagged response enum for every command.
CoreError/Diagnostic | User-facing error shape {problem,cause,fix}, including ProjectFolderMissing {name,path} for registered projects whose directory vanished.
Inner | Arc-shared state holding all managers. State locks are taken through `app::lock`, which recovers a poisoned guard instead of unwrapping it — a `std::sync::Mutex` stays poisoned for the process after any panic while held, so unwrapping turned one failure into every later read panicking too. `project_detail` clones SettingsService/CustomInstallStore (both `Clone`) and drops the guards before `build_detail` does file I/O and version probes, so an unreachable project folder cannot stall other commands. Implements `delete_site` / `delete_project` / `delete_sites`, which revoke TLS certs, restart web server if needed, remove domain and project from the store, and move the project folder to `<parent>/excluded_sites/<folder>` (collision-avoiding with numeric suffixes). Governs ignored folders (`ignored_folders()`, `rename_ignored_folder()`) defaulting to `["excluded_sites"]`, skipping them during project detection and auto domain sync. Owns the deletion history (`list_deleted_items` / `forget_deleted_item` / `clear_deleted_items`) over the two skip lists `projects.removed` and `domains.auto_skip`: each entry is `{value, deleted_at}` on disk (older bare-string entries are read as entries with no date), merged newest-first for `list_deleted_items`. `skip_matches` normalizes the Windows `\\?\` prefix on both sides and compares a candidate against the stored value *and* its canonicalized form, so the watcher sync and the manual Scan judge a folder the same way and a path spelled through a short name, junction, mapped drive or `..` segment cannot slip past a skip. The same resolution runs the other way round, in `same_skip_entry`, for everything that reads or edits a list rather than testing one: `forget_deleted_item`/`clear_project_skip` (`remove_skip`), `push_skip` and the dedup in `edit_skip_entries`. Without it a stored entry stayed put when the caller handed back another spelling of the same folder — on a GitHub runner, where `%TEMP%` is `C:\Users\RUNNER~1\...` and `canonicalize` returns the long name, so Settings' "clear this entry" reported success, the history still listed the folder, and the next scan skipped it anyway. Resolution is gated on `is_path_like`, so a bare automatic-domain name (`app1.local`) is compared as a string and never resolved against the working directory, where a folder of that name would otherwise match it. `comparable_path` adds the fallback the clear specifically needs: when the leaf is gone from disk — the user removed the project, then the folder, then cleared it — a whole-path canonicalize fails on both sides and the two spellings would be compared raw again, so the parent is canonicalized and the file name reattached, which still collapses a short name at every level. In `sync_auto_domains`, the `has_any_domain` guard skips creating the auto domain when any domain — any TLD — matches the project by `project_id`, by site folder/root path, or by a hostname containing the project name, so changing the default TLD never renames or shadows an existing site (prevents duplicate auto-domains such as `test366-local.local`), strips default tld suffixes before slugification, and auto-links project IDs to domains in `add_domain`. On adding a site (`add_domain`, not via Quick Apps or reverse proxy), ensures the document root directory exists and writes a responsive welcome page (`index.html` for static, `index.php` with a `?phpinfo=1` trigger for PHP) matching the Open Local Server welcome design when no index file exists.
Inner::start_projects_watcher | gates | automatic domain sync on a change to the set of immediate project-root directories; ordinary root filesystem events still refresh project subscribers but no longer run a full domain/project scan
AppPaths | OLS_HOME-aware path resolver (certs/data/settings). Also owns the portable path form: `encode_root` writes a path inside the app (`sites/<name>`, `data/<name>`, forward slashes) instead of the absolute path it resolved to, and `decode_root` expands it again on load, so a renamed or relocated install keeps the folders and tools that belong to it. A path still stored absolute and no longer existing is re-anchored from its trailing `sites`/`data`/`home` segment when that folder exists under the current install, and left alone otherwise so a genuinely deleted site keeps reporting as missing. `join_relative` appends the stored form one segment at a time, because joining a forward-slash string onto a Windows base would leave a path spelled with two different separators. `CustomInstall.path` and the `quickapps.projects_dir` setting use this; `Domain.root` and `Project.path` are its other two users.
SettingsService | SQLite key-value store (app.db settings table). Cloneable so a read can release the store lock before doing slow work.
Db | Central SQLite store (app.db, WAL): settings table + generic docs collections for all Vec-stores. `db.last_writer` records the pid of the last commit so the running app can detect an outside write (Explorer menu, CLI); `changed_externally` compares that pid and `adopt_ownership` restamps it with this process id. Before stores load, `migrate` checks `PRAGMA user_version`, backs up app.db and present WAL/SHM sidecars before each migration, and applies each version in a transaction. A failed migration rolls back, logs a Diagnostic, and leaves the old store usable. Migration 1 adds JSON `json_extract` read views and expression indexes; migration 2 and Journal retain only the newest 100 operations from 30 days and collapse consecutive identical failures. The `docs` and `settings` table definitions remain unchanged.

ResourceLimits | Optional memory, CPU and process caps applied at the next start. `cpu_percent` (1-100, a share of *all* cores) and `cpu_threads` (1..=logical cores, converted to a percentage and rounded up) are mutually exclusive; `cpu_limiter_path` overrides where `cpulimit.exe` is searched for. The cap is applied by wrapping the spawn in the `cpulimit` utility — `cap_process` returns Err naming the install when a wanted cap has no utility, so a start is refused rather than left uncapped. `find_cpu_limiter` order: **the running executable's own directory first**, then `cpu_limiter_path`, then OLS_CPULIMIT_PATH, then the repo's `vendor/cpulimit/cpulimit.exe` (dev builds only, via compile-time CARGO_MANIFEST_DIR), then %LOCALAPPDATA%\Programs\cpulimit, then PATH. The sibling comes first because that is the hash-checked copy the installer ships, and because the settings DB is shared between a dev build and an installed one — a path saved while running from target\ would otherwise keep an installed app pointing at that dev machine's folder. A configured path is the fallback for when there is no sibling, which is the only case the UI shows the field in; a path that is not a file is skipped, not treated as "no limiter anywhere", so a stale setting cannot disable the cap in a correct install. The repo copy comes before the machine's %LOCALAPPDATA% one so a dev build reports the binary this checkout shipped rather than a stray install that has nothing to do with it. `cpu_cap_status` / `CpuCapStatus` tell the UI whether a wanted cap can be applied and at what percentage.

PluginManager | Declarative plugin.yaml installer/validator.
Updater | Minisign-signed self-updater (latest.json + SHA check). `compare_versions` (SemVer) yields `UpdateStatus {development_version, up_to_date, update_available}`, stored on `UpdateInfo.status` and synced with the badge/banner/button state. install_update spawns the verified installer and then exits the process on a 1.5s timer: Windows locks a running image, so an installer started while the app is alive cannot replace `OLS.exe`, and an update that reported success while the old process kept running changed nothing. The exit is what leaves the file lock behind; installer/open-local-server.iss CloseApplications is the second half of the same rule for a user who runs the setup exe by hand.
ServiceManager | DB/cache/mail lifecycle + TCP health; also lists/proxies the three web servers (kind web) without owning their processes. Owns each service's `Starting|Stopping|Restarting|Running|Stopped|Error` lifecycle state and broadcasts batched status changes; transitions begin before the operation and finish in the actual resulting state. Operations are serialized per service id (`op_locks`) and concurrent `start()` requests join the in-flight start (`in_flight_starts` + `Condvar`) rather than spawning duplicate processes; starting an already-running-and-ready service is a no-op (`Ok(pid)`). Readiness polling (`track_start`) polls every 300ms (`SERVICE_READY_POLL_INTERVAL`) up to per-service timeout (`service_ready_timeout`: 45s for MariaDB/PostgreSQL, 30s default `DEFAULT_SERVICE_READY_TIMEOUT`) until the process is alive and listening on its port (`is_running_and_ready`), re-checking live readiness before recording any failure in `start_failures` and formatting port conflicts via `describe_port_conflict`. `stop()` waits for exit and up to 5s for the service port to be released. `service_aggregate()` is the shared source for the running count and Start all plan: configured autostart IDs (resolving `web` to the default server), or every installed service if no IDs are configured. rename_database/from,to moves a database under a new name and drop_database(name) removes one — the move is a statement only on PostgreSQL (`ALTER DATABASE ... RENAME TO`); MariaDB has no `RENAME DATABASE`/`RENAME SCHEMA` at all (they are MySQL's, and it answers ERROR 1064), so it is dump_to → create → load_into → DROP, which costs a full copy of the data and is the reason `free_name_among` picks the `_bkp` name before the move rather than after it. Implements `list_tables` and `run_sql_query` across MariaDB, PostgreSQL, and SQLite, with client binary resolution fallbacks (mariadb/mysql.exe, psql.exe, sqlite3.exe) and engine alias normalization (`mysql` -> `mariadb`, `postgresql`/`pgsql` -> `postgres`).

WebManager | Per-server render-write-validate-reload pipeline with rollback + drift detect; one Running entry per server, each startable on its own. Serializes operations per server id (`server_locks`), coalesces concurrent start requests (`in_flight_starts` + `Condvar` in `ensure_started`), treats starting an already-running-and-ready server (`is_ready`) as a no-op, registers `Running { process }` immediately upon spawn before polling readiness (`WEB_READY_POLL_INTERVAL = 300ms`, `DEFAULT_WEB_READY_TIMEOUT = 30s`), waits up to 5s for HTTP/HTTPS ports to release on stop/restart (`wait_ports_free`), and re-checks live readiness before surfacing any error. Caddy's localhost admin endpoint uses a stable port derived from its install prefix so another Caddy instance does not take a shared fixed port; start, reload and stop use the same address.
WebConfig | {default_server, servers:{id -> ServerPorts{http,https}}, php_workers, dns_port}; effective_ports(id) is 80/443 for the default and the stored pair otherwise.
ServerPorts | {http, https} - the stored pair one server keeps even while it is the default.
Server first-time ports | apache 8080/8443, caddy 8081/8444, nginx 8082/8445; two servers may never share a bound port (WebConfig::port_conflicts).
Nginx/Apache/Caddy | Server renderers + invocation builders. When `SiteSpec.missing_folder` is true (document root vanished on disk for non-proxy site), renders a safe 503 Service Unavailable stub with friendly HTML (`missing_folder_html`) instead of dead docroots, preventing web server config validation errors and crashes (Apache AH00112 warnings and .htaccess faults, Nginx 404s/FastCGI errors, Caddy missing root). Restores normal vhost automatically when folder reappears. Each also renders the per-server `localhost/<prefix>` routes file (`_ols_paths.<ext>`): one server block holding a location per site that asked for a path route, each proxying to that site's own vhost with the prefix stripped and the site named as `Host`. All those requests share one `Host: localhost`, so they cannot be split across per-site files the way domains are — the first `server_name localhost` on the port would answer for all of them. Going through the real vhost means the prefixed URL is answered by exactly the config the site already has, instead of a second copy of the PHP/proxy/static logic that could drift from it. "The site's own vhost" is the one that *serves* it: a site with TLS and "Redirect to HTTPS" answers its plain-HTTP vhost with nothing but a redirect to `https://<its own hostname>`, so such a site is proxied to over its **HTTPS** vhost (nginx `proxy_pass https://` + `proxy_ssl_server_name`/`proxy_ssl_name`, Caddy `reverse_proxy <https port>` + `transport http { tls_server_name }`, Apache `ProxyPass https://` + `SSLProxyEngine on`) and a site without TLS still takes the HTTP vhost. Each route also sends `X-Forwarded-Prefix: /<prefix>`, because the prefix is stripped on the way in and an application would otherwise rebuild every absolute URL without it.
DomainStore | Domain data + validation (no rendering). `path_prefix` (the `localhost/<name>` route) is validated and checked for uniqueness here, not in the renderer. Validates proxy site upstream ports (`check_upstream_port_taken`): prevents port collisions across proxy/app sites on 127.0.0.1 and rejects ports reserved for internal application services (web, databases, cache, mail, DNS via `reserved_app_port_label`). The store is the only writer of the `domains` collection, and it translates the root on the way in and out: a root inside the app is persisted relative (`AppPaths::encode_root`) and expanded back to a full path on load (`decode_root`), so nothing downstream — renderers, diagnostics, search, snapshots — ever sees a relative path. The built-in `openlocalserver.test` home site is re-anchored to `<data>/home` on every load: its folder is the app's own, never one the user picked, so a moved install must not report it as "folder does not exist" while its files sit in the current data dir. `write_home_page` never overwrites the *page*, so a hand-edited welcome page survives both the re-anchor and the re-seed. The seeded `logo.svg` / `logo-dark.svg` are the exception: they are generated bytes (`include_bytes!` of `ui/public/favicon*.svg`), so a stale copy is rewritten while the page is still the stock design this build ships, and left alone once the marker is gone. Otherwise a repaint would reach fresh installs and never reach existing ones, silently. The page itself is versioned by a `<!-- home vN -->` marker: `HOME_VERSION_MARKER` is what this build ships (v9) and `HOME_LEGACY_MARKERS` lists every older stock design, so a design change refreshes installs that never hand-edited the page and leaves a user's own page alone. v9 is what names the product in full — "Open Local Server" — in the header and footer brand, beside the mark, instead of a bare "OLS" the reader has to decode. Owns `ensure_site_dir_and_welcome_file`, `static_welcome_page`, and `php_welcome_page` for preparing document roots and initial welcome files.

Used only by CertificateManager::issue_lets_encrypt for public hostnames (validate_public_hostname); issued certs are recorded with provider `lets_encrypt` and a 90-day expiry.

AutoBackup | §130 scheduled backups. `AutoBackupSettings{enabled,scope,schedule,keep,snapshots,include_env,include_files,databases}` in the `auto_backup` settings key is the app-wide plan; `AutoBackupSiteSettings{enabled,schedule,keep,include_files,include_env,databases}` per hostname in `auto_backup.sites` is each site's own, taken on its Backups page; `AutoBackupState{buckets,last_run}` in `auto_backup_state` records the file name of everything a pass wrote, bucketed `snapshot:<project>`, `sql:<engine>/<db>`, `sqlite:<path>`, and retention deletes only recorded paths. `AutoBackupRun{started_ms,finished_ms,created,removed,problems}` is one pass in words; `AutoBackupStatus{settings,description,next_run_ms,running,last_run,kept,sites}` is what the pages render. **The period, the keep count and the choice of what gets copied are the site's own when the plan is scoped to chosen sites**, because not every site is equally worth an hourly backup and one site's `.env` files are not every site's business, and the app-wide set when the plan covers everything -- per-site values kept in that case would be a second answer to a question the plan already answers, so all five are dropped on save rather than stored and ignored. Each site is reported with its own values, its *effective* values (its own, or the plan's) and `managed_by_plan`, which is what lets the site's page show the period, keep count and contents in force without offering an edit that does nothing. A snapshot holds a whole project, so two sites of one project run at the first one's settings and any disagreement -- period, keep count or contents -- is reported rather than resolved silently. A site switched on with all three copy answers off is refused, because a config-only snapshot every period is not a backup; `None` means "follow the plan", never "copy nothing". `clock_tick` checks every project against its own period, hands only the due ones to the pass, and does the work on its own thread behind a process-wide `RUNNING` flag, so a slow dump delays neither a scheduled task nor a second pass. Scope `app` = every project plus every MariaDB/PostgreSQL database and every registered SQLite file; `site` = the covered projects and the databases their manifests declare. A server that is installed but stopped is started first, because a dump needs one; one that is not installed becomes a problem in `problems`, never a silent skip.
ProjectStore | Folder registry, ID=SHA256(path)[..16]. A stored path is the canonical one with Windows' \\?\ prefix removed -- and for a share that means \\?\UNC\server\share becomes \\server\share, not UNC\server\share, which is not a path and could not be reopened by the Explorer menu, a site or the CLI. Tracks ProjectHealth (Healthy, Missing, Offline) evaluated on load, on periodic watcher sweep, and on operation guard (ensure_project_available), persisting transitions and preserving original failure timestamps. Supports `relocate` to re-point moved/renamed projects and rebase associated domain roots.
ProjectTools | Composer/npm/venv/xdebug thin wrappers, plus the project Backups tab (`BackupsPanel`): the §130 automatic-backup plan for this project's sites, taking and restoring snapshots, exporting, and cloning the environment. Named Backups rather than Snapshots because a database dump belongs on the same page as the snapshot that records the database it belongs to, and hiding one behind a different name is how a user ends up backing up configuration and then losing data. When the app-wide plan is scoped to chosen sites, each site in the list carries its own "How often" (a preset or a custom cron field), "How many to keep" and a "What to copy" group (project files, .env files, databases); when the plan covers everything, those read "Managed by Settings" instead, because a control that saves a value nothing reads is worse than no control -- and the site's own switch is disabled in that case too (`rowLocked` = plan on and app scope), since a per-site `enabled` the app-wide plan overrides is the same second answer wearing a switch. The row still renders, greyed, so the user can see whether the site is covered; its hint names the way out (set the scope to chosen sites). With the plan *off* the switch stays live, because a plan that runs nothing is the user's to arm from either page. A write sends the whole site entry, not just the field that changed, because the command replaces it and editing the period must not quietly reset the contents back to following the plan.
Wordpress | WordPress detection, one-time admin sign-in (`is_wordpress`, `issue`, `sweep`, `revoke`) and missing core-file repair (`repair_missing_core`). `describe` returns the site's details for its Sites page card. `database(dir)` reads `DB_NAME` and `DB_HOST` from `wp-config.php`; WordPress has no `.env`, so this keeps database data in snapshots and bundles. Detection accepts `wp-config.php`, `wp-admin/index.php` or `wp-includes`+`wp-content`. `repair_missing_core` reads the version from `version.php`; when that is missing, it identifies a known maintenance release by checksum-matching surviving core files. It caches wordpress.zip and checksums.json at cache/wordpress-core/<version>/ for offline repair or manual placement, and only downloads on a cache miss. It checks each restored member against the official per-file MD5 digest before writing. Existing files and `wp-content` are untouched. The Sites action menu and WordPress project's Repair page expose this action. One-time sign-in writes a single temporary must-use plugin with a random 128-bit token; no WordPress password is read or stored. The token expires, is one-use and is removed when used or revoked; its screen follows the app theme and the temporary bridge is swept during project listing.

TaskManager | §164 live progress task registry. A task is a `TaskView{id,kind,title,target,state,steps,progress,results,problems,error,started_ms,finished_ms,cancel_requested}` plus a thread; `start(kind,title,target,total,work)` returns the id to watch and reuses an existing running task with the same kind and target, checking and inserting under one registry lock to prevent concurrent duplicates. `work` receives a `TaskHandle`. Linear steps, throttled progress, whole-view events, and `FinishGuard` preserve live reporting; `cancel` stops between items. Finished records have a 200-entry in-memory cap. The Background Tasks page combines these live jobs with persistent UI command history, marks persisted running records as interrupted/failed on startup, and merges consecutive identical finished operations into a counted row.
BundleCipher | §165 password encryption for a bundle's secrets. Argon2id (19 MiB / 2 passes / 1 lane — the OWASP parameters, deliberately identical on every machine so a bundle written on one opens on another) turns the export password into a key; ChaCha20-Poly1305 seals each entry under it. Sealing is **per entry, not per zip**: the zip crate's own AES scheme is ZipCrypto-derived and weak, and a reader can then unlock exactly the entry it needs. The key is derived **once per bundle** — the random salt lives in the manifest and every entry carries its own fresh 96-bit nonce — because deriving per entry would cost ~60ms times the file count for no extra safety, while a reused nonce under one key would break the cipher outright. A wrong password and a damaged file are indistinguishable to an AEAD, so the error says both rather than guessing. Two length edges are deliberate: `open` refuses a blob shorter than `nonce(12) + tag(16)` and accepts exactly that, because a nonce and a tag with no ciphertext is what sealing an **empty** entry produces — an empty `.env` file has to survive a round trip — and `from_hex` refuses an odd-length string up front rather than leaving the one-character tail to `chunks(2)`, which would parse `"abc"` as `0xab 0x0c` and hand back bytes the caller never wrote.
SiteBundler | §165 site bundles: one zip holding any mix of settings, `.env` files, database dumps and project files for any number of sites. `BundleOptions{settings,env,databases,files}` (settings+env on by default — small, and what "the site's configuration" means to most people; data is asked for) and `OnConflict{Update, Rename}`. Sites are **grouped by the project behind them**, so exporting `shop.test` and `blog.test` of one project gives one entry with two sites and imports back as one project, not two; a site with no project has nothing to describe and is reported, never exported half-way. The manifest (`bundle.json`, format 1, written **last** through a `.part` file) lists each site's config as a `SnapshotContent` document with the `.env` contents and dump names removed, so **the manifest itself never holds a secret**; `content_of` puts them back on read and every import path downstream is then the one a snapshot restore already uses. Only `.env` files and database dumps are sealed — the two places passwords live; project files and settings stay readable so the bundle can still be reviewed, and the dialog says so. The import's `preview` reads the manifest and reports, per site, which hostnames already exist and which free name a rename would take, so the update/rename choice is made on facts. `Update` finds the project owning the first colliding site, takes a **"Before import" snapshot of the current state first** (the same rule `restore_snapshot` follows) and names it in the result, so the update is reversible; `Rename` registers a new project folder and adjusts everything the collision would have made ambiguous (hostname, database, port) through the same `Adjust` a clone uses. `options.files` is honoured on **both** paths — update unpacks the bundle's project files over the existing folder, rename unpacks them into the new one; gating the unpack on `options.config` (or, in update mode, omitting it) made an update silently leave the site's own code behind. Per-site failures land in `problems` and never abort the batch — one bad database must not cost the user the rest of the export. Not reachable over the HTTP API (absent from the `operate` allow-list) and absent from the AI command allow-list.

.github/workflows/ci.yml | Three jobs in ONE workflow: `test` (windows-latest, `cargo test -p ols-core -p ols-helper`), `build` (`needs: test`) which runs `scripts\build-installer.bat full` — the same script, same stages and same SHA-256 artifact verification as a local release — and `publish` (`needs: build`, `if: startsWith(github.ref, 'refs/tags/v')`) which uploads a GitHub release. Build and publish were two workflows sharing a `v*` tag trigger and that was wrong: two workflows on one tag start at the same instant, so the publisher either races the builder (failing, because the artifacts are not there yet) or has to poll the API for a run it did not start. As jobs of one workflow `needs` *is* the ordering, the artifacts come from the run already in progress via `download-artifact`, and there is no race to handle and no second build path. **One tag trigger, not two.** Triggers are `workflow_dispatch` (build and verify, publish nothing — there is no version to publish) and `push` on `v*` (test -> build -> publish).
