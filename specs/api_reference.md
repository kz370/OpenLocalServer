# API Reference — OLS

Three front doors share one command model: Tauri IPC, CLI, HTTP API. All dispatch `CoreCommand` -> `CoreResponse`; errors shaped `{problem, cause, fix}`.

## Tauri IPC
Single command: `invoke('run_command', {command})` from `ui/src/core.ts` `runCommand(cmd)`.

`runCommand` rethrows: Tauri hands back the `Diagnostic` object as the rejection value. A rejected call therefore needs an owner for the error, and a caller that waits on one to render must not wait forever. `core.ts` exports `runCommandWithin(cmd, ms)` for that second case — the same call raced against a deadline that rejects with a Diagnostic naming the command and the seconds waited. It is the client-side half of a rule the core enforces on its side: no command is meant to block indefinitely, and a read that gates rendered content states its failure rather than holding a loading state. SiteDialog's `get_domain` and `get_project_detail` use a 20s deadline and show the Diagnostic with a Retry.

Core side of the same rule: `get_project_detail` clones the settings and custom-install stores and releases their locks before reading the project's files and probing runtimes, so a project on an unreachable mount blocks only itself. An unregistered project id is a stated failure (`"This site has no project any more."` + re-register fix), not a bare invalid-path error. A poisoned core lock is recovered rather than unwrapped, so one panic cannot make every later read panic too.

Events emitted: `process-event`, `terminal-event`, `runtime-event`, `task-event`, `projects-changed`, `service-status-event`, `ols:navigate`, `ols:status-icon` (payload `boolean` — true when nothing is running, so the UI shows the red mark). `service-status-event` carries `{services: [{id, state}]}` for service lifecycle transitions (`starting`, `stopping`, `restarting`, `running`, `stopped`, `error`); `ServiceManager` owns these states, and Tauri forwards them even when no window is open. The UI subscribes before fetching `list_services`, buffers events during the snapshot, then batches updates so a mount/reload cannot miss an in-flight transition. `ols:status-icon` is a push-only channel with no fetch-current counterpart, so it is also emitted on every `show_main_window` reveal; without that, a webview mounting after the last state change (window opened from the tray, reload) would keep the initial `useServerStopped` value of `false` and show the green mark while the tray is red. `task-event` (§164) carries a tagged `TaskEvent {kind: started|progress|finished, task: TaskView}` and **the whole task every time**, so a subscriber renders straight from the event and never reconciles a delta against what it already had; `progress` ticks are throttled to 200ms in the core because a database dump reports bytes and an event per chunk froze the Runtimes page once already.

Tray menu Quick App selections emit the existing `ols:navigate` event with payload `quick-app:<id>`; App routes to Quick Apps and the page opens the existing creation Wizard for that id. `quick-apps` still opens the catalog.

Event sent by the UI: `ols:theme` (payload `"light"` or `"dark"`, the *resolved* theme after the system preference is applied). The theme is a UI-local setting with no core counterpart, but the tray and the taskbar live outside the webview, so the UI reports it and `set_theme_icon` repaints the native marks in the matching colourway. Seeded from `Window::theme()` at setup, so a dark desktop is not painted light for a frame before the webview answers. A payload that is neither `"light"` nor `"dark"` is ignored rather than treated as light, and a repeated value is a no-op; the repaint cache keys on the pair `(red, dark)`, so either half can change without the other repainting. No command, payload or capability changes. The taskbar button is deliberately *not* part of this chain: an explicit AppUserModelID with its registered Start Menu shortcut is what the shell resolves the taskbar through, so the taskbar mark is a fixed artefact of that identity (see `TauriApp notify` in catalog.txt) and does not follow `ols:theme`. The tray, the window's own icon slots and the in-app mark do.

Event sent by the UI: `ols:ui-ready` (no payload). The main window is created hidden (`visible: false` in `tauri.conf.json`) because the app window is transparent — showing it before the webview paints puts an empty see-through frame on screen for the length of the bundle load. `main.tsx` emits `ols:ui-ready` after two animation frames, once React has actually presented the first frame, and `reveal_window_on_ui_ready` shows the window on it. A 5s fallback timer reveals the window anyway so a UI error can never leave a running app with no window; `MAIN_WINDOW_REVEALED` makes the two paths idempotent. That timer is the one path that can beat the UI, so the page is not left blank while it waits: the pre-paint script in `index.html` marks `<html class="booting">` and `index.css` paints that element with `--background` (which propagates to the canvas) until `main.tsx` removes the class on the first presented frame, so a reveal that happens before React has painted still shows the app's background rather than a see-through frame. No command, payload or capability changes.

Whether that happens is decided once, at startup, by `ols_core::app::should_start_hidden(start_minimized, args)`. The stored `startup.minimized` preference is the whole answer and applies to every launch — the user opening the app themselves, the Windows startup entry, or a shortcut — so the toggle means what it says. `--minimized` is a force flag on top: it hides the window when the preference is off and changes nothing when it is on. When the launch starts hidden, neither reveal path is registered, no `ols:ui-ready` listener exists, and the window stays in the tray until the user opens it; a desktop notification after 2s says the app is running, so a hidden launch cannot be mistaken for a failed one. A hidden window also has no taskbar entry, so the window icon is only observable once the user opens it — which is why `show_main_window` doubles as the mark resync point.
Example:
```ts
import { runCommand } from './core';
const res = await runCommand({ type: 'list_services' });
```

- Dashboard: `get_dashboard`, `get_system_stats`, `run_diagnostics`, `ignore_diagnostic`, `global_search`
- Projects: `register_project{path}`, `add_project{path,name?,project_type?,auto_site?}`, `inspect_project_folder{path}`, `list_custom_project_types`, `add_custom_project_type{name}`, `rename_custom_project_type{old_name,new_name}`, `remove_custom_project_type{name}`, `take_pending_add_project`, `update_project{id,name,icon,clear_icon,project_type,clear_project_type}`, `create_site_for_project{project_id}`, `open_project_terminal{project_id}`, `list_project_types`, `list_editors`, `add_editor{name,path}`, `update_editor{id,name,path}`, `remove_editor{id}`, `set_editor_hidden{id,hidden}`, `relocate_project{id,path}` (re-point project folder and update associated domain roots), `remove_project{id}` (hide/exclude), `delete_project{id}` (move to ols_excluded_sites), `rename_ignored_folder{old_name,new_name}`, `get_project_detail{id}`, `list_projects`, `scan_and_register_projects`, `plan_setup{project_id}`, `apply_setup{project_id,dry_run}`, `get_setup_progress`. `list_projects` includes optional `unconnected_project_ids` from the additive `projects_view` read model when it exists; clients can keep legacy domain matching when absent. `add_project.auto_site` defaults to false; when true, OLS tries to create a linked local site and marks the project non-standalone. When false, the project is standalone and automatic folder discovery cannot create a site for it. If the path is already registered, `add_project` reuses that row and applies the requested standalone preference instead of creating a duplicate. Explicit `register_project` and `scan_and_register_projects` mark projects site-eligible; folder discovery alone registers them standalone. `get_project_detail` clones the settings and custom-install stores and drops their locks before `build_detail` reads the project's files and probes runtime versions, so an unreachable project path cannot stall other commands; an id with no registered project returns a Diagnostic saying so and how to fix it. `relocate_project` validates that the new directory exists on disk, strips verbatim prefixes, updates `project.path`, resets health to `Healthy`, clears any skips on the new path, rebases all associated domain roots to the new directory, and triggers auto domain sync. `scan_and_register_projects` reads the skip list and `projects.ignored_folders` before taking the project store and compares each candidate against it by both its stored canonical path and the raw path the scan read, so folders the user hid or excluded stay excluded. `delete_project` moves the domain-less project's folder into `<parent>/ols_excluded_sites/<folder>` (with `-1`, `-2` suffix on collision) and unregisters it. `rename_ignored_folder` renames an entry in `projects.ignored_folders` and renames matching directories across all project root folders on disk; `ols_excluded_sites` is required and cannot be renamed. `add_project` validates that the directory exists on disk and canonicalizes/strips verbatim prefixes. It reuses an identical registered path and applies `auto_site` as the standalone preference, while folders with the same name at different paths remain distinct; new paths are registered with the supplied or detected type and name. It clears project skips and broadcasts project events. `inspect_project_folder` checks whether a path exists, whether it is a directory or file, detects duplicate registered paths via `same_path`, suggests folder name, and runs framework auto-detection. `list_custom_project_types` returns custom types merged from `projects.custom_types` setting and existing registered projects. `add_custom_project_type`, `rename_custom_project_type`, and `remove_custom_project_type` provide CRUD management for custom types; renaming updates all registered projects using that type, and removing resets projects to Auto. `take_pending_add_project` yields and clears any pending folder path passed via cold start or Windows context menu. `create_site_for_project` auto-detects or creates a linked virtual host domain. `open_project_terminal` spawns an external Windows Terminal (`wt.exe`) window in the project folder with PowerShell fallback. `list_editors` returns detected system editors and user custom editors. `open_in_editor` remains as a compatibility command and selects the first visible configured editor; `open_with{path,app}` selects an editor by ID. `set_editor_hidden` toggles whether an editor is hidden from menus.
- WordPress actions: `list_wp_projects`, `wp_sign_in{project_id,hostname,theme}`, `wp_sign_in_revoke{project_id}`, and `wp_core_repair{project_id}`. `list_wp_projects` answers `WpProjects{projects}` — one entry per registered project whose folder on disk is a WordPress install (`wp-config.php`, `wp-admin/index.php`, or `wp-includes`+`wp-content`), with the first enabled site behind it as `hostname`/`url` and `pending_until` set while a one-time link is still unused. It decides which rows get WordPress-only actions, based on files on disk rather than the project name. `wp_sign_in` writes a one-time bridge as documented above. `wp_core_repair` reads the version from `wp-includes/version.php` when available; if it is missing, it compares surviving core files to WordPress.org checksums for known maintenance releases and selects the best matching release. It reads/writes `wordpress.zip` and `checksums.json` under `cache/wordpress-core/<version>/`; matching cached repairs work offline, and users can place those two files there manually. On a cache miss it fetches checksums and downloads the archive only if files are missing. It verifies each restored core file against the published MD5 checksum and writes only absent files; it never replaces existing files or writes under `wp-content`. It returns `WpCoreRepair{version,restored}`. All four commands are local-only and absent from the HTTP `operate` allow-list and the AI command allow-list.
- Hide/Exclude (deleted items skip-list): `list_deleted_items`, `forget_deleted_item{value}`, `clear_deleted_items`. Represents the "Hide/Exclude" skip list history (`remove_project` and `remove_domain`). `list_deleted_items` returns `DeletedItem{value, deleted_at, kind}` for the two skip lists (`projects.removed` folders and `domains.auto_skip` automatic sites) merged and sorted newest-first; `deleted_at` is 0 for an entry stored before timestamps existed. `forget_deleted_item` removes that value from both lists and answers with the updated list, so the caller can replace its rows without a second read; a blank value is refused with a Diagnostic instead of quietly doing nothing. `clear_deleted_items` empties both lists and answers the same way. None of the three touch files on disk, and none of them re-register anything: the next scan or `sync_auto_domains` does. They are local-only commands and are deliberately absent from the HTTP `operate` allow-list.
- Editor open actions: `open_with{path,app}` launches the selected editor ID. Legacy `open_in_editor{path}` remains compatible by selecting the first visible configured editor; no default-editor setting is read after the one-time migration. `restore_excluded_site{hostname}` is local-only and restores a pending excluded-folder move from the current app session.
- Domains/Web: `add_domain{domain}`, `update_domain`, `remove_domain` (hide/exclude), `delete_site{hostname}` (move to ols_excluded_sites; returns `ExcludedSiteMoved{source,destination}` when a folder moved), `restore_excluded_site{hostname}` (session Undo restores its folder and captured site/project records), `set_domain_enabled`, `set_domain_icon{hostname,icon}`, `inspect_site_folder{path}`, `bulk_set_domains_enabled{hostnames,enabled}`, `bulk_remove_domains{hostnames}` (bulk hide/exclude), `bulk_delete_sites{hostnames}` (bulk delete to ols_excluded_sites), `bulk_set_domain_server{hostnames,server}`, `duplicate_domain`, `get_domain`, `list_domains`, `apply_web{overwrite}` (returns one `ApplyReport` per server), `stop_web`, `get_web_status`, `get_web_config`, `list_web_configs`, `read_web_config`, `write_web_config`, `validate_web`, `set_ownership`, `list_config_history`, `restore_config_history`, `health_check{hostname}`, `sync_auto_domains`. `Domain` carries an optional `server` (nginx|apache|caddy); null means the default server. `inspect_site_folder` inspects a directory for web project indicators (package.json scripts, virtualenvs, entry files, package manager lockfiles) and returns `SiteFolderInspection`. It also carries an optional `path_prefix`, which additionally serves the site at `localhost/<prefix>` on that server's HTTP port; `list_domains` reports it back per site with that server's `http_port` so the UI can build the URL. Config file, history and error-log commands resolve the server from the site, so each site's files are read under the server that renders it. `remove_domain` hides/excludes the site (files untouched, added to skip list). `delete_site` revokes TLS certificates, removes the site domain, unregisters the project if last domain, bounces the web server if needed, and moves the site project directory to `<parent>/ols_excluded_sites/<folder>` (collision-avoiding with numeric suffixes). `apply_web`/`apply_web_server` snapshot the domain store, run the render/validate/reload outside the store lock, and commit the generated-config hashes afterwards, so `list_domains` (and the UI poll that calls it) never waits on a multi-second apply; a change made during an apply is picked up by the next one.
- Site health progress: the UI uses `run_health_check{hostname,onProgress:Channel<HealthProgress>}` for the Sites modal. It sends `{name,step:null}` when a stage starts and `{name,step:HealthStep}` when it finishes, then returns the same `Health` report as `health_check`; ordinary `run_command` and non-UI callers continue to use `health_check{hostname}`.
- Site Icons: `set_domain_icon{hostname,icon}`, `set_site_icon_image{hostname?,folder?,webp_base64}`, `remove_site_icon_image{hostname?,folder?}`, `read_image_file{path}`, and `list_site_icon_library`. `set_domain_icon` updates or clears the site's Font Awesome icon, optionally colored as `name|color`. Manual images are saved as `ols_site_icon.webp` (or per-proxy images under `<data>/proxy-site-images`). `read_image_file` returns a base64 data URL. `list_site_icon_library` returns supported files under `<data>/icons` and one level of category folders, capped at 100 files of 256 KiB each. A file named `<type>_fallback.<ext>` in the root or a category folder is used automatically if the site has no manual image, favicon or explicit icon. `list_domains` includes `document_root` and linked `project_type`; icon images prefer manual files, then bounded favicon lookup in the document root and common static folders. Otherwise, the app uses a matching project-type brand icon, including WordPress when identified by core files.
- Bulk site edits: the `bulk_*` commands edit or delete many sites in one store write and answer `Bulk{changed,skipped}`. They are **partial, not all-or-nothing**: a hostname that is no longer in the store, and the built-in home site going off or being deleted, are named in `skipped` with the reason while the rest of the batch still lands — giving up on thirty changes because one row in the selection was stale would leave the user with nothing done. `skipped` is never dropped silently, because a batch that landed on twenty of twenty-five sites has to say which five it left alone. `bulk_set_domain_server` takes `server: null` to put the batch back on the default, and validates that id once for the whole batch, so a typo refuses every site *before* anything is written rather than after half of them are. `bulk_remove_domains` runs the single-site `remove_domain` (Hide/Exclude) path per hostname. `bulk_delete_sites` runs `delete_site` across each hostname, moving project folders to `ols_excluded_sites/`. Both are listed as destructive by `repair::is_destructive`. Each batch is followed by a **single** `apply_web` by the caller: forty sites re-render the config once, not forty times. All are local-only and absent from the HTTP `operate` allow-list; the delete variants are present in the AI command allow-list but flagged destructive, so they need a separate confirmation before running.

- Services/DB: `list_services` (includes nginx/apache/caddy with kind `web`, the port each binds, a TCP `healthy` probe, and `log_source` — the log source holding that service's own output), `get_service_aggregate` (one snapshot with `running`, `enabled_total`, and `start_service_ids`), `start_service{id}`, `stop_service{id}`, `restart_service{id}` (all three accept a web server id: start renders that server's sites, restart re-applies it, stop bounces only that server), and `stop_all`. The aggregate counts all running service rows; its start plan uses configured autostart services, resolving legacy `web` to the default server, or all installed services when none are configured. Dashboard, tray and CLI use this same plan; each Stop all path dispatches `stop_all`. All three of the per-id commands are verified, not fire-and-forget: `start_service` waits for the spawn to be decided and returns a `Diagnostic` naming the OS reason when the process never started; `stop_service` waits for exit and errors when a kill was ignored; `restart_service` fails on either half instead of reporting a bounce that did nothing.
- `stop_all` — stops tunnels, supervised workers, the web stack (servers *and* PHP pools) and every running service, then sweeps the supervisor with `stop_all_and_wait(10s)`. Answers `stopped_everything{still_running: [...]}`, where the list is empty in the only case where the status mark can reach red; anything the OS would not kill is named there rather than swallowed. It exists because "Stop all" existed twice with two different scopes: the tray menu stopped the web stack and services (missing tunnels and workers) and the Dashboard stopped only the auto-startup set (missing Mailpit, any worker, the web stack). Since the mark is red only when *nothing* supervised is alive, either version left the icon green immediately after the user asked for everything to stop. One command, one meaning — both buttons now call it. Added to the HTTP `operate` allow-list next to `stop_service`, since it is the same class of mutation.t happen, `get_connection_info{id}`, `list_databases{engine}`, `list_database_tables{engine,database}`, `execute_sql{engine,database?,sql}`, `create_database{engine,name,user?,password?}`, `list_db_users`, `create_db_user`, `list_db_backups`, `backup_database`, `restore_database`, `open_db_tool`, `list_external_tools`, `save_external_tool{tool}`, `remove_external_tool{id}`, `test_external_tool{id}`, `open_database{engine,database?,path?,tool_id?}`, `list_sqlite`, `detect_sqlite`, `associate_sqlite`, `check_sqlite`
  `create_database` takes either no credentials or both a user and a password. With none, it connects as the engine's superuser (the bundled servers are provisioned passwordless on loopback). With both, it creates the database and the user, makes the user its owner and stores the password in the OS keyring, so the app never needs superuser rights. A half-supplied pair is refused with a message naming what is missing rather than creating a database nobody can log into.
- Automatic backups (§130): `get_auto_backup` -> `AutoBackupStatus{settings,description,next_run_ms,running,last_run,kept,sites}`, `set_auto_backup{settings}` (validated; answers the same status), `set_site_auto_backup{hostname,site}` -> the same status (one site's own enabled/schedule/keep/include_files/include_env/databases, validated, and all five dropped when the plan covers everything so nothing stores a value the plan overrides) and `run_auto_backup` -> `AutoBackupRun{created,removed,problems}`. `run_auto_backup` is the same routine the clock runs, so the "Back up now" button cannot drift from the schedule; it refuses with a Diagnostic when a pass is already going rather than doubling one. `description` is the schedule in words ("daily at 00:00", or "each site's own period") and `next_run_ms` is null whenever the plan is off, and the soonest of the sites' own next runs under the site scope, so no screen states a next run it will not honour. `get_auto_backup`, `set_auto_backup`, `set_site_auto_backup` and `run_auto_backup` are local-only and absent from both allow-lists — a plan, a retention count and a bulk dump are the user's own decisions. `create_snapshot`, `backup_database`, `restore_database`, `restore_snapshot`, `import_sites` and `set_env_value` remain in the AI allow-list; the last five are flagged destructive and need a separate confirmation before running.
- Site bundles & background tasks (§164, §165): `export_sites{hostnames,options,dest,password}` -> `TaskStarted{id}`, `preview_site_bundle{source}` -> `SiteBundlePreview{preview}`, `import_sites{source,password,on_conflict,name,options}` -> `TaskStarted{id}`, `list_tasks` -> `Tasks{tasks}`, `cancel_task{id}`, `dismiss_task{id}`, `clear_finished_tasks`. The Background Tasks page also persists user-operation history, deduplicates identical in-flight UI commands and groups consecutive finished repeats; service/runtime start, restart and reload actions are excluded. `TaskManager::start` reuses an existing running task with the same kind and target. **The two heavy bundle commands answer with a task id rather than a result**. `options` is `BundleOptions{settings,env,databases,files}`, the selective choice, with `BundleOptions.is_empty` refused rather than written as a zip holding nothing but a manifest. `dest` is a folder, defaulted by the UI to `paths.backups_dir` and written as a `.part` file renamed on success. `password` seals the `.env` files and the database dumps under `BundleCipher`; the app never stores it. `preview_site_bundle` reads only the manifest and reports per site which hostnames already exist and which free name a rename would take, so the update/rename choice is made on facts and a damaged or future-format bundle is refused before anything is created. `import_sites` with `on_conflict:{type:'update'}` takes a snapshot of the current state first and names it in `BundleSiteResult.safety_snapshot`; `{type:'rename'}` registers a new project and adjusts hostname, database and port through the same `Adjust` a clone uses. A wrong export password and a damaged file are indistinguishable to an AEAD, so the Diagnostic says both rather than guessing. `cancel_task` and `dismiss_task` report a stated failure rather than doing nothing in silence; `dismiss`/`clear_finished_tasks` never drop a running task. `repair::is_destructive` reports an `update` import as destructive so a confirmation can be required. All are local-only: absent from the HTTP `operate` allow-list and the AI command allow-list.

The bare `web:error` / `web:access` ids still read the default server. `read_log{source,max_lines}`, `clear_log{source}`, `export_log{source,dest}` accept all of them.

`list_migration_sources` returns detected MySQL/MariaDB sources; `inspect_migration_source{path}` validates a selected data folder and locates matching binaries nearby. The Databases import dialog compares canonical folder paths and selects an existing source instead of adding a duplicate. These commands are local Tauri IPC operations.

## HTTP API
Disabled by default. Enable via Settings -> Local API or `olsc api enable`. Binds `127.0.0.1:7420` only. Auth `Authorization: Bearer ols_...` (only hash stored). Rejects `Origin` header and non-loopback Host. Body cap 1MB. Read-only mode allows `list_*/get_*/check_*`, diagnostics, git status/log, read_log. Operate mode adds start/stop/apply/install/register/snapshot/backup.
```bash
curl -H "Authorization: Bearer ols_..." http://127.0.0.1:7420/v1/ping
curl -H "Authorization: Bearer ols_..." -H "Content-Type: application/json" \
  -d '{"type":"list_services"}' http://127.0.0.1:7420/v1/command
```
Success `{"ok":true,"result":{...}}`. Fail `{"ok":false,"error":{problem,cause,fix}}` with 4xx.

## Model Context Protocol (MCP — `ols-mcp`)
Exposes local OpenLocalServer capabilities over JSON-RPC 2.0 stdio to AI assistants and agents (Claude Desktop, Cursor, Antigravity, etc.).
- Authentication: Opt-in bearer token (`--token <token>` or `OLS_MCP_TOKEN`). Stored in OS keyring.
- Exposed tools:
  - Sites & Domains: `ols_get_sites_dir`, `ols_list_domains`, `ols_get_domain`, `ols_add_domain`, `ols_update_domain`, `ols_remove_domain`, `ols_delete_site`, `ols_inspect_site_folder`, `ols_restart_site_app`
  - Projects: `ols_list_projects`, `ols_add_project` (with auto-detection and duplicate protection), `ols_update_project`, `ols_inspect_project_folder`, `ols_list_project_types`, `ols_add_custom_project_type`, `ols_rename_custom_project_type`, `ols_remove_custom_project_type`
  - Editors & Tools: `ols_list_editors`
  - Databases: `ols_list_databases`, `ols_create_database`, `ols_list_tables`, `ols_execute_sql`
  - Services & Runtimes: `ols_list_services`, `ols_start_service`, `ols_stop_service`, `ols_restart_service`, `ols_list_runtimes`, `ols_install_runtime`, `ols_refresh_runtimes`
  - Web & Tasks: `ols_apply_web`, `ols_validate_web`, `ols_list_tasks`, `ols_run_command` (raw CoreCommand dispatcher)

## Errors
All layers return Diagnostic: `problem` (short), `cause` (root), `fix` (actionable, often runnable CoreCommand). UI renders ErrorCard with Fix/Details. CLI prints aligned problem/cause/fix. Never expose secrets, keys, tokens, or absolute home paths (masked + redacted).

## Reconciliation

remove_domain adds the hostname to domains.auto_skip and retains its record. remove_site_from_list removes only the selected site record, preserves or registers its project row, and marks that project standalone so automatic domain sync does not recreate the site; project files stay on disk. delete_site moves the site folder to ols_excluded_sites and removes its site/project records. `.ols_ignore_me` hides both the project and site; `.ols_ignore_site` hides/deactivates only the site while keeping the project visible and its domain record. Both markers are watched; deleting `.ols_ignore_site` syncs discovery/reconciliation and restores the site. Inner::reconcile filters inactive rows from list results and vhost generation and synchronizes the managed hosts block. ListDomains/ListProjects stay read-only apart from external-change reloads; reconciliation runs on startup sync, scans, and mutations. The UI's remove_site_from_list flow refreshes both lists immediately, then invokes SyncHosts asynchronously while showing an updating status. SyncHosts returns `Applied { reports }` from any web config reload performed during reconciliation, allowing the UI to notify users which servers reloaded; no report means no notification. forget_deleted_item clears a hidden-site entry; the next reconciliation restores the retained site unless a marker remains. ListProjects adds the transient auto_discovered flag based on configured roots for the site-row label.
